# 解析の層 — Frame / Stack / Series 解析の型付け (#48)

> **状態: 仕様(層の割り当てと、型付けの規則)。**
> Frame 層はユーザー決定 (2026-08-04, #48)で**確定済み**。Stack / Series 層の
> 中身と型付けの仕組みは本書の提案で、末尾の**判断リスト (§10)** に諮る。
> 個々の推定量の数式・補正・表示の細部はここでは決めない (§8 —
> [flat-field-stats.md](flat-field-stats.md) は叩き台のまま、#57 の凍結解除後の話)。

## 0. なぜ層か

正典 ([terminology.md](terminology.md)) は「**σ_t は stack の属性。frame の属性
として出力しない**」を不変条件に持ち、操作マトリクスの測定 (analyzer) 行は既に
層で分かれている (frame = 現在の frame + ROI / stack = 集計系 / series = 掃引系 /
batch = —)。ところが**解析の側にはこの区別を言う場所が無い**:

- プラグイン ABI は `analyze(const psFrame* in, …)` の1枚受け取り
  ([ps_plugin.h](../include/ps/ps_plugin.h))。つまりプラグインは書ける限り全部
  frame 解析で、stack から欠陥マップを作る解析は**表現できない**。
- stack の σ_t は Temporal パネル、series の線形性は Linearity パネルに内蔵で、
  外から書けない。
- 「PRNU」を名乗る数が frame 層に2つあり (#66)、本物 (dark を引いた測定) には
  住所が無い。

層を型にすると「σ_t は stack の性質」という中心規則が API とメニューの形になり、
**間違った測定が表現できなくなる**。[stats-taxonomy.md](stats-taxonomy.md) の
入力クラス (S1 / TN / LM) を、実装が強制できる形に落とす、と言ってもよい。

## 1. 定義 — 解析の層とは何か

**解析の層 = その解析の入力が丸ごと必要とする最小の層。** そしてそれは
**結果が属性として付く層**と常に一致する。σ_t は stack 全体が要り、出てきた数は
stack の性質。linearity の傾きは series 全体が要り、出てきた数は series の性質。
入力の広がりと結果の帰属がずれる解析は存在しない — ずれて見えるときは
名前が間違っている (frame 行に σ_t を書く、が正にそれ)。

[stats-taxonomy.md](stats-taxonomy.md) の入力クラスとの対応は 1:1:

| 層 | taxonomy クラス | 入力 | 結果が付く先 |
|---|---|---|---|
| **frame 解析** | S1 | 1枚 (+ROI) | その frame |
| **stack 解析** | TN | 同一条件の N 枚 | その stack |
| **series 解析** | LM | 条件を振った並び | その series |
| batch | — | — | **解析は無い**(構造を主張しない入れ物に測る量は無い。正典どおり) |

`+meta / +ref / +cal` は層ではない。**層は「入力がどの広がりを持つか」、
修飾子は「その層で他に何を持ち込むか」**(照度値、dark 参照、校正器材) で、
直交する。dark stack を参照する PRNU は「stack 解析 +ref」であって
第4の層ではない。

全層に共通する規則は3つ。以降の全節はこの3つの適用にすぎない:

1. **結果は自分の層を名乗る。** provenance (§7) が層と対象
   (どの frame / どの stack n/N / どの series) を言う。
2. **層を下げた代用値は、修飾された別の名前を持つ。裸の名前は本物に予約する。**
   1枚から出した固定パターンの proxy が裸の `PRNU` を名乗った結果が #66 である。
3. **前提のうち機械が確認できるもの (層そのもの・枚数・単位) は強制し、
   確認できないもの (平坦・静止・未飽和) はツールチップで言う。**
   [measure-ux.md](measure-ux.md) の既存原則をそのまま層に適用する
   (ホストが嘘の判定をするくらいなら実行してエラーを見せる)。

## 2. Frame 解析 — 確定 (再掲)

ユーザー決定 (#48):

> Frame解析の層は必ず必要になるので，ここは確定しよう．で，Frame解析は，
> 今と同じで，Histogram, Projection, ROIsで．

- **Histogram / Projection / ROIs** (ROIs は mean/std/`PRNU [σ %]`/min/max の表)。
- **アナライザプラグインも現状すべて frame 解析**。宣言したからではなく、
  シグネチャが1枚しか受け取れないから (§5)。
- **計算で作った frame も frame。** stack の frame 平均は結果が frame だから、
  Histogram / Projection / ROI がそのまま効く — 特別扱いするものが何も無い、
  というのが frame 平均を frame にした理由で (`0e4d4ec`)、stack 解析の出力が
  frame 層の入力になる、という層の合成がここに既に実装されている。

frame 層が正直に言えることの限界は
[flat-field-stats.md](flat-field-stats.md) (a) 節で確定済み:
1枚の空間σは常に `σ_t² + σ_fpn²` の合成で、**固定パターンとしては上界**に
しかならない。だから frame 層の非一様性の数は全部、規則2の「修飾された別名」側
(`PRNU [σ %]`、`prnu_pct`) に居る (§6)。

## 3. Stack 解析

時間軸が入って初めて意味を持つ・分離ができる解析。ここが本丸で、
現状「stack があるのに1枚分の情報しか使っていない」欠落の大半がここに落ちる。

| 解析 | 入力に要るもの | 出力 | 現状 |
|---|---|---|---|
| σ_t (plane 毎) | ≥2 枚 | sc (+将来 map) | Temporal パネル / `MOP_TEMPORAL_STATS` |
| σ_fpn (時間平均の空間σ) | ≥2 枚。平坦はシーンの前提 (規則3) | sc (+将来 map) | 同上 (−σ_t²/N 補正の要否は #57) |
| frame 平均 | ≥2 枚 | **frame** | `0e4d4ec` 済 |
| per-frame 表 (S1×N) | 常駐 frame | 表 / cv | [export-design.md](export-design.md) §3.3 |
| ドリフト / フリッカ | ≥2 枚 | cv (frame 軸) | Temporal のグラフ |
| frame 軸に対する monitor 曲線 (経過時間・温度) | frame 軸の宣言 (+meta) | cv | frame 軸は実装済 (export-design §8) |
| 行/列ノイズの固定・時間分離 | flat stack | sc | 未 (#57 の中身) |
| **DSNU [DN]** | **dark と宣言された** stack | sc (+map) | 未 |
| **PRNU (直接)** | **flat 宣言 stack + dark 宣言 stack 参照** (+ref) | sc (+map) | 未 |
| 欠陥画素 (正式) | dark (+flat) stack | sc + **map** | 未 (map の器は #49) |
| blink / RTS | 多数枚 (解析が最小枚数を宣言、目安 ≥50) | sc + **map** | 未 |

**DSNU は新しい計算ではなく、dark と宣言された stack の σ_fpn が名乗ってよい
名前である** (DN で出す場合。e⁻ 表記は K が要るので series 層 — §4)。
宣言 (dark / flat) の置き場所は判断4。**宣言であって推論ではない** —
「level 0 は dark」の既存則は linearity の後方互換に閉じ、新しい解析へは
広げない ([flat-field-stats.md](flat-field-stats.md) (c) 節で確定済みの原則)。

### 3.1 stack 解析の要件

- **最小枚数は解析が宣言する** (`min_frames`)。σ_t は 2、RTS は桁が違う。
  ホストは満たさないとき実行を**拒否**する — 理由1文つき (§5)。
- **n of N**: 部分ロードでも実行し、「何枚中何枚か」を**必ず**併記する
  (正典の不変条件そのまま)。数えるのは**実際に集計した枚数**で、
  常駐しているだけの preview や寸法違いは入れない (frame 平均の先例)。
- **ロード中は実行しない。** まだ枚が届いている stack への stack 解析は
  「クリック時点でたまたま届いていた枚数への答え」になる。
  `requestStackAverage` の先例どおり、**settle を待って実行**する
  (n/N が出るのは「ロードが本当にそこで止まった」= stack の事実のときだけ)。
- **NaN は画素ごとに除外して数える** — 分母に畳まない
  (`computeStackStats` / serve.cpp で確立済みの算術)。除外数は結果が運ぶ。
- **remote の stack 解析は画素の居る側 (peer) で走る。** `MOP_TEMPORAL_STATS` が
  先例で、未オープンの stack もサーバ集計でき、結果は `not opened` タグ付き
  (正典の Temporal 行)。プラグイン stack 解析の remote 実行は MEASURE op の
  拡張になる — 方向だけ確定し、細部は実装時 (§8)。

### 3.2 出力の形 — 数・曲線・frame・map

stack 解析の出力は4形: **sc** (plane 毎スカラ)、**cv** (frame 軸の曲線)、
**frame** (frame 平均のような導出画像)、**map** (σ_t map・欠陥 map のような、
画素の並びだが撮ったものではない画像)。

frame と map の違いは「画素が元と同じ量か」: frame 平均の画素は元と同じ DN で、
frame として開いてよい。σ_t map や欠陥 mask の画素は**別の量**で、これを frame と
呼ぶと [DN] が嘘になる — その語彙と器は #49 (仮称 map) が決める。
本書が確定するのは2点だけ:

- stack 解析は map を出力**する** (欠陥画素・RTS が要求する)。#49 は
  「あれば良い」ではなく、この層の完成に**必要**。
- 画像を出力する stack 解析はすべて**計算 frame の不変条件**に従う:
  由来を名前と note の両方に持ち、ファイルを持たず、セッションには
  レシピを書いて計算し直す (正典、`0e4d4ec` で確立)。

## 4. Series 解析

条件の軸 (パラメータ軸) が入って初めて意味を持つ解析。

| 解析 | 条件軸 | メンバに要るもの | 出力 | 現状 |
|---|---|---|---|---|
| linearity fit (感度・offset・LE max) | 光量 (単位必須) | stack 統計 (mean) | sc + cv | Linearity パネル |
| conversion gain K (PTC) | 光量 (値は不要: σ_t² vs mean) | stack 統計 | sc | Linearity パネル |
| read noise | — | PTC 外挿、または dark stack 実測 | sc | Linearity パネル |
| SNR カーブ | 光量 | mean + σ_t (素材は既に linearity の行にある) | cv | 未 |
| **DSNU / PRNU の分離** (σ_fpn² を μ² にフィット) | 光量 | σ_fpn per level + dark 宣言 | sc | 未 |
| DSNU [e⁻] / PRNU の EMVA 表記 | — | K (= PTC。だから series 層) | sc | 未 |
| ダイナミックレンジ | 光量 (+飽和定義 = meta) | | sc | 未 |
| 飽和容量 (full well) | — | K + 飽和レベル | sc | 未 |
| 暗電流 [DN/s] | **時間** (unit = s/ms) | dark 宣言 stack 群 | sc + cv | 未 (「横軸が時間になった linearity」) |

### 4.1 series 解析の要件

- **単位と値が無ければ fit しない。** 既に正典の不変条件
  (「空のままでは fit できない、が正しい振る舞い」「読めなければ未設定。0 ではない」)。
  層の型付けで新しく足すものは無い — 強制が series 層の入口検査になるだけ。
- **測定の種類 (kind) が fit の式を決める** (正典)。式の無い量を印字しない。
- **単調性は要求しない。** fit に順序は関係なく、温度は往復する
  (export-design §8 で確立済み: 非単調は正常)。同一レベルの重複メンバも合法 —
  それは同じ点の独立な測定であって、エラーではない。
- **series を編集したら計算済みの数値は破棄** (正典)。provenance が「いつ測ったか」
  を持つ理由でもある (§7)。

### 4.2 合成則 — series 解析はメンバの stack 解析結果から作る

**series 解析は、メンバ stack の stack 解析結果 (mean, σ_t, σ_fpn, …) を入力と
する。生画素からやり直さない。** `linRecompute` が既にこの形
(メンバごとに `computeStackStats`) で、これを規則に昇格させる。理由は3つ:

1. **数が食い違えない。** Temporal パネルの σ_t と PTC に入る σ_t が同じ
   蓄積器から出る — frame 平均が「絵の下の数と表の数が食い違えない」ために
   `computeStackStats` を共有したのと同じ理屈 (1つの計算、の原則)。
2. **remote と相性が良い。** stack 集計は画素の居る peer で走り (§3.1)、
   series の fit はスカラ列の上で手元で走る。回線を渡るのは数だけ。
3. **層の定義そのもの。** series の点は stack であり (正典: リニアリティ行
   「1 stack = 1 照度点」)、点の値は stack の属性である。

### 4.3 フレームリニアリティの型

暫定実装 (`frameLinCollect`、板の「フレームリニアリティ残」) は
「1つの stack の per-frame mean を、貼り付けた frame 軸に対してフィット」する。
frame が条件 (露光・照度) を振って撮られている場合の器だが、**条件を振った
並びは定義上 series である**。正典の series 定義は「条件を1つ振った
**stack / frame** の並び」— **frame をメンバとする series は最初から正典に
ある**。型としてはこれが最終形で、フレームリニアリティは
「メンバが1枚ずつの series に対する linearity fit」に落ちる
(判断7。今の stack + frame 軸という器は、そこまでの暫定として正当 —
自分でも interim と名乗っている)。

frame 軸そのものは stack のメタとして残る。ただし用途は**時間的な monitor**
(経過時間・温度ドリフトに対する mean の曲線 = stack 解析の cv 出力) で、
**条件掃引の軸としての利用は series への移行とともに引退**する。
条件が frame ごとに違う並びは「同一条件で撮られた frame の並び」ではない —
stack の定義を守るための引退である。

## 5. 型付けの仕組み — 宣言と強制

「enforceable, not advisory」の要求に対する答え。強制点は3つあり、
どれも**嘘をつける自由度を残さない**形を選ぶ。

### 5.1 プラグイン: シグネチャが層である — layer フィールドは持たない

**解析の層は登録シグネチャで表す。** frame 解析は今の
`analyze(const psFrame*, …)` のまま (V1/V2 は永久にロード可能 — ヘッダの約束)。
stack 解析は **ABI v3** の新しい登録型で、frame ではなく stack 記述子を受け取る:

```c
/* 方向を示す骨格。フィールドの確定は実装仕様で行う (§8) */
typedef struct psStack {
    uint32_t frames;            /* n: 実際に見せる枚数 */
    uint32_t expected;          /* N: stack の期待枚数 (n < N = 部分ロード) */
    /* pull 型アクセス: ホストが常駐/転送を管理でき、共有メモリ運搬層と同じ
       形に載る。全枚の配列を渡すと「全部メモリに居る」を ABI が約束して
       しまうので、それはしない */
    const psFrame* (*get_frame)(void* ctx, uint32_t index);
    void* ctx;
    /* … name, meta_json, reserved … */
} psStack;

typedef struct psStackAnalyzerV3 {
    uint32_t    abi_version;    /* = 3 */
    uint32_t    min_frames;     /* これ未満ならホストが実行前に拒否する */
    const char* name;           /* "category/name" */
    const char* version;        /* provenance 用 (#46)。V3 で新設 */
    const char* description;    /* 前提1行 (平坦・静止など機械に見えない前提) */
    int32_t (*analyze_stack)(const psStack* in, const psRect* roi,
                             const psAnalyzeSink2* sink, char* err, size_t err_cap);
    void*       reserved[4];
} psStackAnalyzerV3;
```

**layer フィールドという案は採らない** (判断1)。フィールドは
「stack と名乗って1枚しか見ない」を書けてしまい、ホストは検証できない。
シグネチャなら stack 解析は stack を受け取る以外に書きようがなく、
規則が**コンパイル時の事実**になる。1枚渡しの analyzer に layer=stack と
書かせない、ではなく、**書く場所が無い**。

series 層のプラグイン口は今回**作らない** (§8)。series 解析は当面
組み込み (Linearity パネルと §4 の表の拡張) が担う。§4.2 の合成則により、
series 層を外に開くときの入力は「メンバごとのスカラ列」であって画素ではない —
つまり将来の口は psFrame とは別物になり、急いで形を決める理由が無い。

### 5.2 ホスト: 層はメニューで gate する — 機械が確認できる前提だから

measure-ux.md の既存規則「満たせない前提はグレーアウト+理由。ただしホストが
機械的に判定できるものだけ」に、層は**完全に**該当する — ホストは今の対象が
stack の一員か、series があるかを正確に知っている。よって:

- stack 解析は、対象が stack でなければ**グレーアウト+理由1文**。
  `min_frames` 未満、settle 前も同じ (§3.1)。
- series 解析は、series が無い / 単位・値が未設定なら同様
  (Linearity パネルが既にそうしている)。
- パネルは構造で拘束済み (Temporal は stack しか受けない、Linearity は
  series しか fit しない)。変更なし。

### 5.3 下の層で実行しようとしたら: 拒否する。格下げしない

**stack 解析を単発 frame に掛けることはできない。1文の理由つきで拒否する**
(「1枚に時間軸はない」— 正典のマトリクスの言い回しそのまま)。

黙って格下げ (「1枚しか無いので空間σで代用しました」) は**しない**。
それは #66 を全解析で再生産する装置になる — 同じ名前の数が、入力次第で
別の量になる。**格下げ先が正当なら、それは最初から下の層に別名で存在している**
(σ_fpn の1枚版は `PRNU [σ %]` / `prnu_pct` として frame 層に既に居る)。
ユーザーは断られた場所で下の層の解析を選び直す — その1クリックが
「いま見ている数は弱い方だ」という自覚そのものである。

逆方向は自明に合法: frame 解析を stack の一員に掛けるのは、ただの frame 解析。
stack の**全**枚に掛けて並べたものが per-frame 表で、それは S1×N の
**見せ方**であって stack 解析ではない (stats-taxonomy §3 の確定事項)。

## 6. PRNU を名乗る数の住み分け — #66 の解

規則2 (裸名の予約) をこの4つに適用する:

| 量 | 層 | 名前 | 扱い |
|---|---|---|---|
| ROI の σ/mean (そのまま) | frame | `PRNU [σ %]` | **現名のまま** (ユーザー決定 #48/#65)。`[σ %]` という修飾とツールチップが層を言っており、規則2を満たす |
| 9×9 ローパス残差の σ/mean | frame | `uniformity/prnu-fpn` の `prnu_pct` | **現名のまま**。proxy と自己申告済み ([analyzers.md](analyzers.md))。改名は報告書の連続性を壊すだけ |
| dark を引いた flat stack の固定パターン | **stack** (+ref: dark 宣言 stack) | **裸の `PRNU`** (表示は層タグ必須: 例 `PRNU [%] — stack: flat n/N + dark n/N`) | 未実装。ここが「本物」の住所 |
| σ_fpn²(μ) フィットの傾き / 切片 | **series** | 裸の `PRNU` / `DSNU` (層タグ必須: `— series: <名>, M levels`) | 未実装。加法・乗法の**分離**はここでしかできない ([flat-field-stats.md](flat-field-stats.md) (c)) |

- **裸の `PRNU` / `DSNU` は dark 宣言を伴う stack / series 層の測定に予約する。**
  frame 層の2つは修飾名で残り、manual の相互注記も残る。数字だけが報告書へ
  行っても、層タグが provenance に居る (§7)。
- stack 層の直接推定と series 層のフィットは**推定量が違う**ので、層タグが
  そのまま区別になる。同じ表に並べるときは層タグを省略しない。
- **"EMVA 1288" の文字列は、規格原文と照合するまでどの画面にも出さない**
  ([flat-field-stats.md](flat-field-stats.md) で確定済みの規則の再掲。
  フレームリニアリティが「rev4-style / -style を必ず付ける」で守っているのと
  同じ線)。プラグインカテゴリ `emva1288/*` ([analyzers.md](analyzers.md) の

## 7. Provenance — 層ごとに結果が運ぶもの (#46)

measure-ux.md の原則 (出力はそれ単体で証拠になる) を層別に具体化する。
**結果が下の表の欄を運ばないなら、その結果は報告書に引用できない。**

全層共通:

| 欄 | 中身 |
|---|---|
| 量と単位 | 既存規則のまま (キー名 / dtype 由来。単位は宣言、推測しない) |
| 実行主体 | `[local]` / `[server <host>]` |
| 時刻・所要 | 既存の出所行のまま |
| 計算者 | viewer 版、または**プラグイン name + version + ファイル** (#46。version は ABI v3 の新設欄 §5.1、**dll パスはホスト側の帳簿で足りるので ABI を待たない** — 判断6) |
| 数値を変えるパラメータ | detrend の方式と窓など。「カットオフを必ず言う」(flat-field-stats) はこの欄の話 |

層ごとに足すもの:

| 層 | 追加で運ぶもの |
|---|---|
| frame | frame 名 (path)、領域 (whole / ROI 矩形)、dtype、CFA 解釈 |
| stack | stack 名 + **先頭フレームの path** (セッションを跨ぐ同定の既定 — series メンバと frame 平均レシピの先例)、**n of N**、除外した非有限サンプル数、領域、全画素かサンプリング格子か (export-design §3.1 の注記と同じ理由)、dark/flat 宣言と参照 stack (使ったなら) |
| series | series 名、kind、パラメータ名+単位、メンバ表 (stack・値・include)、fit の式 — **測定時点の series の中身**。series 編集で数値を破棄する規則 (§4.1) の裏面で、破棄せずに残る唯一のものが provenance の写しである |
| 画像出力 (frame / map) | 名前と note に由来、セッションにはレシピ (§3.2。`0e4d4ec` の不変条件) |

## 9. 正典 ([terminology.md](terminology.md)) への修正提案

本書の規則のうち3つは正典の不変条件に足すべきもの (判断8。追加であって
反転ではない):

1. **解析結果は自分の層を名乗る。** provenance が層と対象 (frame 名 /
   stack n/N / series 名) を運ぶ。運ばない数値は報告書に引用できない。
2. **層を下げた代用値は修飾された別名を持つ。裸の測定名は、その量を実測できる
   層に予約する** (例: `PRNU` は dark 宣言を伴う stack / series 測定のみ。
   frame 層の proxy は `PRNU [σ %]` / `prnu_pct` のような修飾名)。
3. **用途宣言 (dark / flat) は宣言であって推論ではない。** 宣言の無い stack を
   dark とみなして DSNU を出さない。0 で代用しない (「level 0 = dark」は
   linearity の後方互換に閉じる)。

## 10. 判断 — ユーザーに諮る項目

各項目に推奨を付す。番号で答えれば足りる形にした。

1. **層の宣言はシグネチャか、フィールドか。**
   推奨: **シグネチャ** (§5.1 — stack 解析は stack を受け取る登録型。
   layer フィールドは持たない)。
   別を選ぶと: フィールド+1枚渡しでは「stack と名乗って1枚しか見ない」が
   書けてしまい、検証がホストの実行時責務に戻る。型付けの目的
   (間違った測定が表現できない) の中心が落ちる。

2. **stack 解析を単発 frame に掛けたとき: 拒否か、格下げか。**
   推奨: **1文の理由つきで拒否** (§5.3)。格下げ先は下の層に別名で常設。
   別を選ぶと (自動格下げ): すべての結果名に常時層タグを義務化しないと
   同名別量が再発する — #66 の一般化を自分で作ることになる。

3. **裸名 `PRNU` / `DSNU` の予約と EMVA 表記のゲート** (§6 の表のとおり)。
   推奨: 予約する。ROIs 列・`prnu_pct` は現名のまま。"EMVA 1288" は
   規格原文照合まで出さず、それまでツール固有カテゴリ名で実装。
   別を選ぶと: frame 層の2つも改名するならユーザー決定 (#65) の巻き戻しに
   なる。EMVA を早く名乗りたいなら、規格照合の作業が先に立つ。

4. **dark / flat の用途宣言はどこに付くか。**
   推奨: **stack の属性** (宣言・編集可・セッション保存・推論しない)。
   dark であることは撮り方の事実で、掃引に属するかとは独立 — 単独の
   dark stack の DSNU [DN] に series の儀式が要らない。
   注: [flat-field-stats.md](flat-field-stats.md) (c) の括弧書きは
   「series の member 属性」を示唆していた。**本書はそこから変更を提案して
   いる** (あちらは叩き台。ただし黙って上書きしないためにここに明記)。
   別を選ぶと (series メンバ属性): 単独 dark stack を測るには1メンバ series を
   作る儀式が要る。series を跨いで同じ dark を参照する形は自然になる。

5. **部分ロード stack への stack 解析: n/N 併記で実行か、完全ロードのみか。**
   推奨: **実行して n/N を必ず併記** (正典の不変条件どおり) + 解析毎の
   `min_frames` + settle 待ち (§3.1)。
   別を選ぶと (完全ロードのみ): メモリ予算で切れた大 stack と remote stack が
   測定不能になる。正典の「何枚中何枚かを必ず併記」は実行を前提にした文言
   なので、正典の変更も伴う。

6. **provenance のプラグイン情報 (#46) の2段対応。**
   推奨: **dll パス+名前はホスト側の帳簿で即対応** (ABI 変更なし)、
   **version 欄は ABI v3 と同時** (stack 入口 §5.1 と同じ版上げに載せ、
   版上げを1回で済ます)。
   別を選ぶと (version だけ先行): v2.1 相当の版上げが1回増える。予約欄で
   運ぶ手もあるが、予約欄の流用は「ゼロ埋め約束」の上に意味を重ねる —
   正面から v3 でやる方が安い。

7. **フレームリニアリティの最終形。**
   推奨: **frame をメンバとする series** に移す (§4.3。正典の series 定義に
   最初から居る形)。今の stack + frame 軸は暫定の器として維持し、
   移行は板の「フレームリニアリティ残」の行で扱う。frame 軸は monitor 用途
   (stack 解析の cv) に純化する。
   別を選ぶと (現状を最終形に): 「同一条件で撮られた frame の並び」という
   stack の定義に、条件を振った stack という例外を書き足すことになる。

8. **正典への3行追記 (§9) の承認。**
   推奨: 追記する。いずれも既存規則の一般化で、反転する既存文言は無い
   (確認済み: 操作マトリクスの測定行・σ_t の不変条件・n/N 併記・単位宣言の
   いずれとも整合)。
   別を選ぶと: 本書の規則は analysis-layers.md ローカルの約束に留まり、
   正典と実装が食い違ったとき「バグ」と言い切る根拠を失う。
