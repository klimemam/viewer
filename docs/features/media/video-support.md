# 動画対応 — フレームの画素は何なのか、そして依存の代価

> **状態: y4m v1 実装済み。** ローカルと peer の両方で、progressive y4m の
> 8〜16 bit 輝度プレーンを 1 ファイル = 1 stack として読む。他の動画コンテナは、
> 画素値が測定値でなくなる理由と y4m への変換コマンドを示して拒否する。

[docs/features/media/media-support.md](media-support.md) §2 の続き。§2 は「動画 = 遅延デコードされる
stack」という層モデルの読みと、依存候補の比較までで止まっていた。**画素の意味**を
問うていない。本書はそこから始め、実測して、結論を出す。

このツールの正典は [docs/terminology.md](../../terminology.md) と
[docs/features/analysis/stats-taxonomy.md](../analysis/stats-taxonomy.md): **画素値は [DN]**
であり、**数値が製品**。
「デコードできた」は「その数値に意味がある」ではない。

---

## 結論(先に書く)

1. **v1 は y4m (YUV4MPEG2) の輝度プレーンだけを読む。** 非圧縮・ビット完全なので
   値は正真正銘 DN。1 ファイル = 1 stack、N フレーム、提示順。
2. **lossy な動画コンテナ(mp4/mov/mkv/avi/…)は名指しで拒否する。** 「開けません」
   ではなく、**形式名・拒否理由・正直に取り込む変換コマンド**を出す。
3. **FFmpeg (libavcodec 等) は v1 では採用しない。** 実測 95.6 MB / LGPL 義務 /
   3-OS CI の追加作業に対して、それが買えるのは**測定値ではない画素**である。
   採用条件は §6 に、変われば見直す。

一行でいうと: **libavcodec が開けるようにしてくれる形式は、まさにこのツールが
測定に使ってはいけない形式である。** 正直な部分集合は依存ゼロで届く。

## 1. 実測 — codec は測定値に何をするか

`ffmpeg` を**実行時依存としてではなく、この調査の測定器として**使った
(BtbN `ffmpeg-master-latest-win64-lgpl-shared`)。既知の合成センサ出力
(320x240, 24 frames, 8 段の平坦パッチ, 既知の時間ノイズ)を往復させ、
戻ってきた DN を真値と比較した。スクリプトは §7。

### A. ビット深度 — 16-bit センサ DN を 8-bit 動画に通す

| 量 | 値 |
|---|---|
| 既知の σ_t | **40.0 DN16** |
| 8-bit H.264 から回収した σ_t | **0.00 DN16** |
| 回収率 | **0.0000** |

σ_t = 40 DN16 は 8-bit スケールで 0.156 DN8 — **量子化ステップより小さい**。
劣化ではなく**消滅**する。もしこのツールが 8-bit 動画を黙って読んだら、
実ノイズのあるセンサについて「時間ノイズ ゼロ」と表示する。これが
「デコードした動画を黙って測定データとして出す」という、この repo が最悪と
する種類の誤りの、具体的な姿である。

### B. 8-bit で表現できるノイズを lossy に通す

A は「深度が足りない」だけとも言える。ではノイズを 8-bit で十分表現できる
大きさ (σ = 8.0 DN8) にしたら? — それでも合わない。

| 量 | 真値 | H.264 往復後 | 差 |
|---|---|---|---|
| σ_t (時間ノイズ) | 7.77 DN8 | **6.882 DN8** | **−11.4 %** |
| 空間 σ (平坦部) | 8.00 DN8 | **7.106 DN8** | **−11.2 %** |
| 最大絶対誤差 | — | **23 DN8** | 8-bit フルスケールの **9.0 %** |
| RMS 誤差 | — | 4.153 DN8 | |
| 平均バイアス | — | +0.084 DN8 | |

**系統的に 11 % 低く出る。** ノイズ測定としては使えない。

さらに悪いのは、その誤差が**フレーム番号に対して周期的**であること。GOP = 8 で
符号化し、GOP 内位置ごとに平坦部の空間 σ を平均すると:

| GOP 内位置 | 0 (I) | 1 | 2 | 3 | 4 | 5 | 6 | 7 |
|---|---|---|---|---|---|---|---|---|
| 空間 σ [DN8] | **7.345** | 7.032 | 7.068 | 7.035 | 7.109 | 7.046 | 7.116 | 7.094 |

**I フレームは P フレームより 3.9 % ノイズが残る。** 3 つの GOP すべてで
I フレームが極大。つまり per-frame の σ 表・σ プロットには **codec 由来の
周期的な鋸歯**が乗る。これを σ_t の時間変動として読めば、センサではなく
**符号化器の GOP 構造を測っている**。docs/terminology.md が σ_t を stack の
属性と定めた意味が、ここで効く。

### C. 可逆なら? — FFV1 16-bit gray

| 量 | 値 |
|---|---|
| ビット完全 | **true** |
| 最大絶対誤差 | **0.0 DN16** |
| σ_t 回収 | 38.94 DN16 (= 真値そのもの) |
| 圧縮 | 3,686,598 → 1,805,919 B (2.04:1) |

**可逆コーデックを通った値は測定値のままである。** つまり「動画だから測定に
使えない」は雑で、正しくは **「非可逆・低ビット深度・クロマ間引きだから使えない」**。
形式ごとに判定すべきで、拡張子で一括りにしてはいけない。

### D. 途中で切れたファイル

FFV1 を 50 % で切って復号 → **24 宣言に対し 11 フレーム**。
n of N を言う場面は実在する(§4)。

## 2. 問い 1 — 動画フレームの正直な地位

**答え: 「動画」という単位で決めてはいけない。二つの独立した軸で判定する。**

| 軸 | 問い | 決めるもの |
|---|---|---|
| **ビット完全性** | 表示している数は、書き込まれた数と同一か | 統計が **[DN] と名乗ってよいか** |
| **伝達特性** | その DN は光量に比例するか | **linearity / PTC の fit が意味を持つか** |

この二つを混ぜたのが従来の議論の誤りだった。**DN は「格納された数」であって
「光に比例する量」ではない。**(既存の正典どおり: f32 の .npy も DN である。)
だから:

- **ビット完全 = 値は DN**。これは主張してよい。
- **伝達特性が不明 = 線形とは絶対に名乗らない**。y4m はふつう伝達特性を書かない
  ので、**「宣言なし・仮定しない」と記録する**。§1 の montage 前例(値が DN で
  なくなるとき、名前・note・レンジの 3 か所で言う)と同じ強さで扱う。

v1 が採る形は、選択肢でいうと「**真に可逆な形式だけ読む**」。理由は §3 の
コストと合わせて初めて完全になるので、そこで述べる。

**強制のしかた(コードがこれを守る):**

1. 非可逆コンテナは**そもそもロードしない**(拒否。§5)。悪い値が入る経路が無い。
2. y4m でも**クロマ間引きから RGB を合成しない** — 輝度プレーンのみ 1ch で読む。
   4:2:0 の色は補間しないと作れず、補間した色は測定値ではない。
   (C444 でも同じ扱いにした。YUV→RGB は原色系を仮定する行列であり、
   y4m はそれを確実には宣言しないため。**仮定した行列で色を作るくらいなら
   色を出さない。**)
3. インターレース (`It`/`Ib`/`Im`) は拒否。1 フレームが 2 つの時刻の合成であり、
   σ_t の前提が崩れる。
4. 伝達特性・レンジは `note` に**宣言値かそれとも不明かを明記**して記録する。

### 「輝度だけ」は妥協ではないのか

妥協ではある。だが正直な妥協で、しかも測定用途では損失が小さい: IQ の測定量
(σ_t, FPN, PRNU, linearity, SNR) はすべて輝度面の量として定義されている。
色を返す方が「便利」だが、その色は**このツールが作った**もので、
ファイルにあった値ではない。

## 3. 問い 2 — 層モデルにおける動画

**1 ファイル = 1 stack、N フレーム、提示順。** これは §2 の読みのままで正しく、
[terminology.md](../../terminology.md) の順序付きデータ層
`frame ≼ stack ≼ series` にそのまま乗る。`≼` は集合包含ではなく、この場合は
frame が stack のメンバになるという許された向きだけを使う。
`.npy` の frame 軸 (F,H,W[,C]) が既に「1 ファイル = 1 stack」を実装しており
(`loadNpy`)、y4m はその 2 例目にすぎない。実装上も同じ経路を通す。

**帰結を画面で言うこと:**

- stack は**時間軸を持つ**ので σ_t / FPN 分離・per-frame 表が意味を持つ層である
  (terminology.md の表)。動画が stack になるということは、**σ_t が計算できて
  しまう**ということ。だから §1-B が致命的になる: 非可逆な stack の σ_t は
  センサと codec を**同時に**測っており、しかも GOP 周期の鋸歯が乗る。
  → v1 はそういう stack を作らせない(拒否する)ことで解決している。
- series には**しない**。1 本の動画は「条件を 1 つ振った並び」ではなく
  「同一条件の並び」。terminology.md の「series は自動で作らない」に従う。
- batch は 1 ファイル = 1 batch(npz の前例と同じ)。stack と各 frame はその
  batch に `managed-by` される。

### index → frame の対応と seek

y4m は**フレーム間予測を持たない**。全フレームが独立・同一バイト長で、
ファイル順 = 提示順。よって **index → frame は算術**で、seek は
`headerLen + index * (6 + frameBytes)` の一意な確定計算。**ずれようがない。**
これは v1 を y4m に絞ったことの副次的な利得である。

#### N はバイト数から導く — 宣言された枚数ではない

y4m は**ヘッダにフレーム数を書かない**。したがって N は
`(ファイルサイズ − headerLen) / (6 + frameBytes)` で**導出**する。
フレームが固定長なのでこれは厳密だが、**「元の撮影が何枚だったか」は
どこにも書かれていない**ことに注意する。

帰結: 5 フレームのファイルを半分に切ると、残ったバイトは
「完全な 2 枚 + 3 枚目の途中」を意味する。このとき正直な報告は
**「2 of 3」**であって「2 of 5」ではない。5 はファイルが持っていない数であり、
それを表示するのは**持っていないフレームを数えること**になる
(terminology.md の不変条件)。V24 がこの区別を固定している。

なお `FRAME` 行にパラメータが付く y4m(稀)ではフレーム長が可変になり、
この算術は狂う。実装はマーカーを毎回実際にパースして読み進めるので
**復号は正しく続く**が、N の予測だけがずれうる。その場合も短い読み取りで
停止して n of N を言うので、多く主張することはない。

B フレームを持つ codec(H.264/HEVC)を将来入れる場合、ここは自明でなくなる:

- **復号順 ≠ 提示順。** index は PTS で並べ直した後の順序でなければならず、
  `AVPacket` の到着順で数えると B フレームで入れ替わる。
- **seek は最寄りの keyframe にしか着地しない。** 目的の index までは
  そこから前進デコードするしかない(`avformat_seek_file` +
  desired PTS まで decode-and-discard)。
- **着地を誤ったときに黙って隣を出してはいけない。** 正典の
  「持っていないフレームを持っていると言わない」がここに効く。取得した
  フレームの PTS が要求と一致しない場合は、**そのフレームを返さず
  index とともに失敗を報告する**のが本ツールでの正しい振る舞い。
  「近いフレーム」を返す実装は、A/B 比較で無言の誤りを生む。

## 4. 問い 3 — 依存のコスト(実測、推測ではない)

### 4.1 この環境の事実

| 調べたもの | 結果 |
|---|---|
| `ffmpeg` / `ffprobe` が PATH にあるか | **無い** |
| MinGW/WinLibs に `libavcodec` ヘッダがあるか | **無い** |
| vcpkg | **無い** |
| pkg-config | **無い** |
| `nasm` / `yasm` / `make` | **すべて無い** |

→ **この環境で FFmpeg をソースからビルドするのは不可能。**(依頼文の予想どおり。)
評価できるのは「システムパッケージ」と「プラットフォーム毎の prebuilt」のみ。

### 4.2 バイナリサイズ(実測)

BtbN の LGPL shared ビルドを実際に落として測った(zip 67,396,105 B)。

| DLL | サイズ |
|---|---|
| `avcodec-63.dll` | **67.9 MB** |
| `avformat-63.dll` | 21.7 MB |
| `avutil-61.dll` | 2.8 MB |
| `swscale-10.dll` | 2.4 MB |
| `swresample-7.dll` | 0.7 MB |
| **必要な 5 つの合計** | **95.6 MB** |

比較対象:

| | サイズ | ビルド時間 |
|---|---|---|
| 現在の `viewer.exe` (MinGW/Ninja Release, 全 65 target) | **7.6 MB** (7,996,319 B) | **59 s** |
| 上に載る FFmpeg DLL 群 | **95.6 MB** | (prebuilt: ビルドしない) |

**アプリ本体の 12.6 倍**を配布物に足すことになる。しかも `.github/workflows/build.yml`
の `publish-binaries` は `binaries` ブランチを**毎回 force-push で作り直す**ので、
main への push ごとに 95 MB 級の blob を push することになる(履歴は置き換わるが
転送量は毎回かかる)。今の設計思想 —「ビルド環境の無いマシンが git だけで
最新を保てる、pull は小さい」— と正面から衝突する。

### 4.3 CI が 3 OS で必要とするもの

| OS | 入手方法 | 評価 |
|---|---|---|
| Ubuntu | `apt-get install libavcodec-dev libavformat-dev libswscale-dev` | 容易。既に `apt-get` ブロックがある |
| macOS | `brew install ffmpeg` | 容易だが brew の ffmpeg は**巨大な依存の塊**(既定で多数の外部ライブラリを引く)。ビルドキャッシュ次第で分単位 |
| Windows | **システムパッケージが無い** | prebuilt zip を CI 内で download + 展開 + `PATH`/`CMAKE_PREFIX_PATH` を通す自前ステップが要る。ハッシュ固定と供給元の信頼も自分の責任になる |

Windows が問題で、しかもこの repo の**主用途 OS が Windows** である
(exe アイコン・ショートカット・IME まで作り込まれている)。

### 4.4 ライセンス

- 復号だけなら **LGPL-2.1+** で足りる(GPL 部品 — x264/x265 等 — は encoder 側。
  実際 §1 の実測でも LGPL ビルドに libx264 は無く、代わりに Cisco の
  libopenh264 を使った)。
- **動的リンクなら LGPL は現実的**: DLL を差し替え可能な形で同梱し、
  ライセンス文と入手元を配布物に入れる。
- **静的リンクは義務が重い**: 利用者が FFmpeg を差し替えて**再リンクできる手段**
  (オブジェクトファイル一式か、それに相当するもの)の提供が要る。
  この repo は MinGW で `-static-libgcc -static-libstdc++` の**自己完結 exe**を
  売りにしている(CMakeLists.txt の MINGW ブロック)。FFmpeg を入れると
  その方針が崩れ、「exe 1 個 + plugins」だった配布物が
  「exe + 5 つの DLL + ライセンス文書」になる。

### 4.5 最小構成ビルドという中間案

`--disable-everything --enable-decoder=ffv1,rawvideo --enable-demuxer=matroska,yuv4mpegpipe`
で構成すれば、可逆形式だけを数 MB で得られる可能性がある。**これは魅力的で、
§6 の見直し条件の本命**。ただし:

- **本環境では検証できなかった**(nasm/make が無い。§4.1)。上の「数 MB」は
  **未実測の見積もりであり、根拠として使ってはいけない**。
- 代償は「prebuilt を使わず 3 OS でソースビルドする」こと。Windows では
  MSYS2 + nasm が要り、CI 1 回あたり十分〜数十分。キャッシュ設計が要る。

## 5. v1 が拒否するもの(名指しと理由)

「開けません」は禁止。形式名・**なぜ**・**どうすれば正直に取り込めるか**を出す。

拒否対象の拡張子: `.mp4 .m4v .mov .mkv .webm .avi .wmv .flv .mpg .mpeg .m2v
.ts .m2ts .mts .3gp .ogv .264 .h264 .265 .hevc .avc .vc1 .prores`

文言の形(実装は `videoRefusal`):

    MP4/H.264: lossy, 8-bit, chroma-subsampled - the pixels are display-referred,
    not DN (docs/features/media/video-support.md). Measured: a known sigma_t of 40 DN16 comes
    back as 0.00, and 8-bit noise is attenuated 11% with a GOP-periodic bias.
    Convert the frames you want to measure, then open the .y4m:
        ffmpeg -i "<file>" -pix_fmt gray16le -strict -1 out.y4m

y4m 内部でも、正直に読めないものは拒否する:

| 条件 | 理由 |
|---|---|
| インターレース `It`/`Ib`/`Im` | 1 フレームが 2 時刻の合成、σ_t の前提が崩れる |
| `C420*` / `C422*` の**色** | クロマ間引き。輝度は full-res なので**輝度は読む**、色は作らない |
| 未知の `C` タグ | プレーンの大きさが決まらない。推測しない |

**変換コマンドは実測で検証済み** — `-strict -1` は `Cmono16` が y4m 原仕様の
外(ffmpeg 拡張)であるため必要。ffmpeg の demuxer は読めるが muxer は
`-strict -1` 無しでは書かない(実際にエラーを確認した)。8-bit の
`-pix_fmt gray` なら `-strict -1` は不要。

## 5.5 実装(決定 → コードの対応)

**2026-08-09 更新**: 本文書が書かれた時点の実装は `core/main.cpp` に置く前提
だったが、分割(docs/background/project/split-plan.md)と `core/imagefile.h` の継ぎ目が先に着地した
ため、**置き場が変わった**。決定は 1 つも変わっていない。依存追加はやはりゼロ。

**y4m は `core/imagefile.h` の表の 1 行になった。** 一見おかしいが、§2 の問いを
通した後の y4m は**画像形式**である: テキスト 1 行 + 生プレーン、圧縮なし・
フレーム間予測なし。つまり 1 ファイル = **同じ形の絵が N 枚、順番付き**で、これは
複数ページ TIFF とまったく同じものであり、継ぎ目は既にその言葉を持っている
(名前の無い絵の並び = stack の frame、`core/imagefile.h`)。動画を別種の問題に
している要素 —— codec・GOP・間違った絵に着地しうる seek・提示クロック —— は
この形式には 1 つも無い。だから第二の扉も第二の語彙も遅延デコード機構も要らない。

| 決定 | コード |
|---|---|
| 非可逆コンテナは名指しで拒否 | `imagefile::videoRefusal(path)`(`core/y4mread.cpp`) — 拡張子 21 種を形式名で表引きし、理由(実測値)と変換コマンドを返す。`openPath` が raw ダイアログより**先に**これを見るので、H.264 のビットストリームを画素として解釈させる誘導が起きない。**表の行にはしない**: `Backend::absent` は「何かをリンクすれば読める形式」の状態で、ここでの答えはリンクしても変わらないため(理由が測定であって依存ではない)。表は**バイト**で判定し `dialogPattern()` を作るので、21 行足すと `*.mp4` が画像ダイアログに並ぶ |
| y4m だけ読む | `imagefile::y4mDecode`(`core/y4mread.cpp`)= 表の 1 行。`openPath` に `.y4m` 分岐は**無い** —— 既に `imagefile::forPath` に訊いているため |
| ヘッダ解析 | `Info` + `geometry()` — `C` タグからプレーン寸法。知らない値は**名前を出して**拒否 |
| インターレース拒否 | `y4mDecode` の `I.ilace` 判定 |
| 輝度のみ 1ch | luma プレーンだけを読む(クロマはフレーム長に数えるが変換しない) |
| 1 ファイル = 1 stack | `Image::member` を**空のまま**返すだけ。「名前の無い絵の並びは frame 軸」という継ぎ目の規則で `loadImageFile` が `App::SeqInfo` を組む —— TIFF のページと同じ 1 本の経路で、y4m 専用のコードは無い |
| n of N | バイト数から `declared` を導出(この形式はフレーム数をどこにも宣言しないので、**割り算が唯一の情報源**)。短い読み取りで停止し、`n of N` を全フレームの note に書く |
| 正直さの記録 | note に「bit-exact / values are DN as stored / **not assumed linear**」 |
| セッション復元 | **分岐を足していない。** `loadSession` は既に `imagefile::forPath` で継ぎ目に回すので、`.y4m` はそこを通る。旧ブランチが `.y4m` 分岐を足したのは、当時それが無いと `loadNpy` の magic check で落ちて **N 枚全部が黙って消える**からで、その穴は継ぎ目が塞いだ |
| メモリ予算 | **v1 では効かせない**(下記) |

**旧ブランチとの差 1 件 —— メモリ予算。** 旧 `loadY4m` は `seqMemBudget()` を
frame バイト数で割って読む枚数を切っていた。継ぎ目の `decode` はバイト列から
`vector<Image>` を返す形なので、その途中で予算を見る場所が無い。**黙って切るより
切らない方を選んだ**: 予算で切られた stack は「n of N」を出すが、その N は
「ファイルが持っている枚数」であって「読める枚数」ではなく、2 つの理由で同じ
文が出るのは診断を潰す。上限は `MAX_FRAMES`(100000)で、これは予算ではなく
**敵対的なヘッダに対する境界**である。大きな y4m を予算付きで読むのは
`docs/background/project/split-plan.md` 後の別件(継ぎ目に streaming decode を教える話)で、
**未解決事項として残す**。

### v1 の既知の制限(意図的) — **#111 で解決済み**

v1 はこう書いていた: 「Browse パネルには y4m は出ない。一覧は `isNpyName()` で
門番されており、ここを広げると**リモートの y4m 対応があるかのように見えて
しまう**。『見えるのに開けない』より『経路が限られている』方が嘘が少ない」。

**この判断は #111 で覆った。** 前提が間違っていたため:

- 「広げると 1つになる」のではなく、**述語が 2つある**。ローカルの一覧は
  「この viewer が開けるか」、リモートは「この peer が配れるか」を訊く
  (`viewerReadsName` / `peerServesName`, input-adapters.md §3.6.4)。片方を
  広げてももう片方は動かないので、リモート対応があるようには見えない。
- **「見えるのに開けない」も既に起きていた**。行は淡色で出ており、理由だけが
  無かった。この repo の流儀は**名指しで断る**ことなので、正しい形は隠すのでも
  黙って出すのでもなく、**出して理由を言う**(#111 の裁定)。

現在: **ローカル／ssh どちらの Browse からも y4m が開く**。protocol 10 で
`viewer-serve` が同じ `core/imagefile.cpp` / y4m backend を使うため、単クリック preview、
正式 open、stack のフレーム送りは同じ経路で動く。FFmpeg を要する圧縮動画は
§6 の採用条件が満たされるまで対象外のまま。

**`abValueUnit()` は変更していない。** 読み込むのはビット完全な値だけなので、
**[DN] は正しい**。ラベルを剥がす必要が出るのは非可逆を読むようになったときで、
そのときこそ §6 の再評価が要る。逆に言えば、v1 は「DN と名乗ってよいものだけを
入れる」ことで、DN ラベルの意味を守っている。

**2026-08-09 更新**: 固定しているのは **`--media-selftest` の M24-M28**(旧 V24)。
移した理由は 2 つある。1 つは同居 —— PNG/JPEG/TIFF/EXR の契約と同じ場所に置く方が、
「形式が増えたら M1 の一覧が赤くなる」という結び付きが働く。もう 1 つは**走る場所**で、
`--verify-selftest` は GL コンテキストを要るので 3 ランナーのうち 1 つでしか走らない。
M24-M28 は `NOGL` なので **3 OS 全部で門番**になる。

フィクスチャは C++ ではなく **`tools/gen_testdata.py`**(他のメディア用
フィクスチャと同じ場所)。旧ブランチが C++ で書いたのは「CI に ffmpeg が無い」
ためで、それは事実だが要点ではない: y4m は**テキスト 1 行 + 生プレーン**なので、
自前のサンプルから書くのに 20 行の Python で足りる。そしてそれこそが、この形式が
「数値が生き残る唯一の動画形式」である理由そのものである —— フィクスチャ生成に
codec が要るような形式なら、この viewer に入る資格が無い。

## 6. FFmpeg を採用する条件(何が変わればひっくり返るか)

「今はやらない」であって「永久にやらない」ではない。以下のどれかが成立したら
再評価する:

1. **可逆形式の実ファイルが持ち込まれたとき。** FFV1/v210/ProRes 4444 XQ の
   実データが業務に現れたら、§1-C のとおり値は測定値なので、開けないのは
   純粋な機能不足になる。そのときは §4.5 の最小構成を**実測してから**入れる。
2. **§4.5 の最小構成が実測で 10 MB 未満・3 OS で CI 10 分以内に収まったとき。**
   この 2 数字が満たされれば 4.2/4.3 の反対理由は消える。
3. **「見るだけ」の要求が独立に立ったとき。** 測定ではなく確認のために動画を
   スクラブしたい、という要求は正当だが、それは**測定パスとは別の口**で
   受けるべきで、値が統計に流れない設計(view-only doc)が前提になる。
   その設計が先。
4. **配布形態が変わったとき。** インストーラや package manager 経由になり、
   `binaries` ブランチの force-push が配布経路でなくなれば、4.2 の
   転送量の反対理由は弱まる。

逆に、**8-bit lossy を測定パスに入れるために FFmpeg を採用することは、
どの条件でも認められない。** §1-A / §1-B がその根拠。

## 6.5 入力アダプタとの関係(main の adapter-native / adapter-python 合流後)

main に **Python 入力アダプタ**([input-adapters.md](../adapters/input-adapters.md))が入った。
これは本書の結論を**強める**方向に効く。

**アダプタは codec 動画の正しい入口である。** H.264 を測定に使いたい人は、
`ffmpeg` を明示的な `-pix_fmt` で呼ぶアダプタを書けばよい。利点は §5 の変換
コマンドと同じで、しかも自動化される:

- viewer は libavcodec を**リンクしない**(95.6 MB を払わない)
- **画素形式を選ぶのは利用者のコード**であり、ツールが黙って選ばない
- 対応形式が増えても viewer 本体は変わらない

つまり「FFmpeg を本体に入れる」以外の道が main 側にできたので、§6 の
再評価条件 1(可逆形式の実ファイルが来たら)は**さらに満たされにくくなった**。
FFV1 ですらアダプタ経由で読める。

### ただし、Reader では native 経路の制約を回避できる

Reader の返り値は **native な numpy 配列として入ってくる**。つまり
8-bit H.264 をデコードして `uint8` を返す Reader を書けば、その値は
**[DN] を名乗ったまま統計に流れる** — §1-A で σ_t が 0.00 になる、まさにその
経路である。本ブランチが `openPath` で無効にしたのは**拡張子から開く経路だけ**であり、
Reader 経由の読み込みは対象外である。

**これは現在の Reader 経路に存在する境界である。** Reader host はローカルと peer の
両方に配線済みで、viewer は返された numpy 配列を Reader の宣言どおりに受け取る。
任意の Python が内部でどの codec / pix_fmt を使ったかを viewer が推測することは
できないし、推測してはならない。

緩和策は既に契約の中にある: `note`(素性の一文)と `meta`(機械可読な事実)。
input-adapters.md §4.3.1 は「viewer 自身が note を書く場面が既にある
(dtype を変換した、n/N しか読めなかった)」と書いており、**非可逆コーデックを
通した旨はまさにその種類の事実**である。

したがって、動画を復号する Reader は `note` に変換を明記し、`meta` に
`codec` / `pix_fmt` / `lossless` 等の provenance を返す責任を持つ。ただし現行契約は
任意の metadata を運ぶだけで、これらのキーを必須検査したり、`abValueUnit()` が
`[DN]` 表示を自動で外したりはしない。Reader が誤った内容を宣言しても viewer は検証
できない、という [input-adapters.md](../adapters/input-adapters.md) §6 の境界に含まれる。

## 7. 再現方法

測定スクリプトは repo に入れていない(実行時依存でない ffmpeg を要求するため、
CI で回らない)。手順は以下で、数値は §1 のとおり:

1. LGPL shared ビルドを入手 (`BtbN/FFmpeg-Builds`,
   `ffmpeg-master-latest-win64-lgpl-shared.zip`)。
2. 既知の合成 stack (320x240x24, 平坦 8 段, 既知 σ) を numpy で作り、
   16-bit は `Cmono16`、8-bit は `Cmono` の y4m として書く。
3. `-c:v libopenh264 -pix_fmt yuv420p -b:v 4M -g 8` で符号化 →
   `-f rawvideo -pix_fmt gray`(または `gray16le`)で復号 → 真値と比較。
4. `-c:v ffv1 -level 3 -pix_fmt gray16le` で C の可逆往復。
5. 出力ファイルを 50 % で切って D の n-of-N。

**検証していないこと(正直に):**

- 実カメラの H.264/HEVC ファイルでの誤差(合成データのみで測った)。
- libx264 での数値(LGPL ビルドに無いため libopenh264 で代用。CRF ではなく
  固定ビットレートなので、絶対値は符号化器と設定に依存する。**方向と桁**は
  codec に依らない性質だが、11 % という数字そのものは設定依存である)。
- §4.5 の最小構成サイズ(ビルド不能)。
- macOS / Linux の CI での実所要時間(このブランチでは CI を回していない)。

## なぜ y4m リーダは §1 が却下した「自前最小リーダ」ではないのか

media-support.md §1 は EXR の自前最小リーダを却下した。理由は
**「実務の EXR は PIZ / DWA 圧縮が普通に混ざる。『NONE+ZIP だけ読める』は
開けないファイルへの不満を量産する」** — つまり**圧縮方式の網羅率**の問題だった。

y4m には**圧縮が無い**。ヘッダ(テキスト 1 行)+ 生プレーンであり、
「一部の y4m しか読めない」という状態が原理的に起こらない。実装は
**デコードではなくパース**で、既存の `.npy` ヘッダ解析や `.raw` 読み込みと
同じ種類の作業である。よって §1 の却下理由は転移しない。

正直な弱点はそこではなく、**y4m はカメラが吐く形式ではない**こと。利用者は
一度 `ffmpeg` で変換する必要があり、その `ffmpeg` は自分で用意することになる。
ただしこの変換は**利用者が明示的に画素形式を選ぶ**という意味で、ツールが
黙って選ぶより正直である。
