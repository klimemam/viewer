# .npz の key 対応 — 経緯と検討

ユーザー提起 (2026-08-03):「npz で array 直ではなく、key が入った場合ってどういう対応しましょうかね」。

## 1. 今どうなっているか (コードで確認)

> 以下は対応前 (v1 実装前) の挙動。現在の挙動は
> [npz-design.md](../npz-design.md) §4 を見ること。

`loadNpz` (main.cpp 3661) は zip 内の `*.npy` メンバを**全部**、名前順に**黙って開く**。
各メンバは `loadNpyBuffer` → `decodeNpyBuffer` を通り、名前は `file.npz:key`。
セッションには `member <key>` が残り、復元は zip 経由で同じメンバを読み直す。

形の解釈 (decodeNpyBuffer 3900-3922):

| メンバの shape | 今の結果 |
|---|---|
| (H,W) / (H,W,C) / (F,H,W) など | 画像 / stack。**正しい** |
| 4次元より深い | **先頭要素 [0] を黙って取る** |
| **1次元 (N,)** | **H=1, W=N の「画像」になる** |
| スカラー | 1×1 の「画像」になる |
| 文字列・object dtype | `unsupported dtype` で拒否(正しい) |

### ここが欠陥

**1次元の配列が「高さ1ピクセルの画像」として開かれる。**
露光時間の列 `exposure_ms = [1,2,5,10,...]` を渡すと、それが**絵として** Files に並ぶ。
これは正典の「黙って捏造しない」に反する — 1次元配列は画像ではない。
4次元超の `[0]` 黙殺も同じ family。

そして**全メンバを無条件に開く**ので、`{data, dark, flat, exposure_ms, gain}` の
npz を開くと画像3枚 + 偽画像2枚が Files に並ぶ。

今の「全部開く」は、key が意味を持つファイルでは間違い。

## 3. 決めてほしいこと

> この5問は v1 実装で全て解決済み。答えは
> [npz-design.md](../npz-design.md) §4 にある。

1. **全部開く → picker、で良いか。** (推奨: 良い。画像1つなら picker なし)
2. **1次元 key を軸として提案するか。** (推奨: する。これが一番効く)
3. **metadata (スカラー/文字列) をどこに出すか。** (推奨: プロパティ。
   将来 series の値としても使えるが、それは別途)
4. **4次元超の黙殺をやめる方向で良いか。** (推奨: 良い。訊くか拒否する)
5. **Browse の npz 展開はローカル先行で良いか。** (推奨: 良い)

## レビューで出た欠陥と対応 (V21d〜V21g で固定)

初版は敵対レビューで実欠陥が出た。全部直してある。

- **単位の trim が呼び出し側にしか無かった。** `" "` は貼り付け経路では拒否され
  npz 経路では通り、`x axis in  ` と描画された。trim を
  `applyFrameAxisVals` の中へ移動 — 規則は規則の在る場所で効かせる。
- **.npz を2つ同時に drop すると先の1つが黙って消えた。** `openPath` はループで
  呼ばれ、2つ目が1つ目の picker を上書きしていた。**待ち行列**にして、待つ側の
  ファイル名を言う。accept / Cancel のどちらでも次が出る。
- **長さ0の軸が画像になった。** `(8,8,0)` は W/H だけ範囲検査され C は無検査で
  `ch=0` の ImageDoc を作り、`(0,8,8,3)` は空の payload から H*W*C 個読んだ。
  F と C も範囲検査する。
- **1次元の要素数が桁溢れし得た。** ヘッダが宣言した次元の積が size_t を回り
  込むと 0 になり、バッファ検査を通って `reserve` が `length_error` を投げた。
  各次元・積・**zip ディレクトリの usize** に対して検査する。
- **全メンバが失敗しても空の batch が残った。** 何も開かなければ
  `pruneEmptyBatches()`。
- **走査が全メンバを完全展開していた。** ~128 バイトのヘッダを見るために
  数GB を UI スレッドで展開していた。`npzExtractPrefix` で 64 KiB だけ
  ストリーム展開する (`HAS_MORE_OUTPUT` は成功)。値が要るメンバ
  (metadata と軸候補) だけが全体を読む — **画像メンバは走査中に一切展開しない**。
- **文字列配列が要素0を配列そのものとして表示していた。** descr の item size で
  読みを区切り、`(5,)` なら `"..." (first of 5)` と言う。

### 副産物

`loadNpyBuffer` / `loadNpy` が作る in-file stack は、先頭 frame しか batch を
持っていなかった (2枚目以降が `addImage` を通らないため)。フォルダ経路
(`pumpSequence`) は既にやっていたことを、この2箇所にも入れた。
「1つの stack は1つの batch」が実際に成り立つようになった。
