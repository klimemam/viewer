# 設定の棚卸し — 何が設定になりうるか、どう分けるか、どの形で置くか

> **状態: 提案 (2026-08-10, #50)。** [issue #50](https://github.com/klimemam/viewer/issues/50)
> の指示 —— 「設定としてでてきそうなものを列挙 → 分類 → コメントアウト許容の
> json (vscode みたいな形)」—— の**前半2つと、形式の提案まで**である。
> **コードには1行も手を入れない。** 移行 (prefs.txt を読む側・書く側の
> 差し替え) は別の変更で、この棚卸しが合意されてからでよい。理由は単純で、
> 今 prefs.txt に無いものが**設定として存在しないのか、散っているだけなのか**
> が誰にも分かっていないからである (§3.8 がその答えで、これが本書で一番
> 重い節になった)。
>
> 判断が要るものは **§9 の判断リスト**にまとめてある。番号で答えられる。

## 1. 非目標

- **Preferences パネルの UI 設計** (どのタブに何を、どの順で並べるか)。
  中身が決まってからの話で、#50 の指示も列挙 → 分類 → 形式の順である。
- **移行の手順とコード**。§8 に見積もりだけ置く。
- **キーバインドの割り当て表そのもの。** 本書が決めるのは「設定にするか」
  だけで、どのキーに何を割るかは別の設計 (判断14)。
- **測定量そのものの是非。** detrend の既定や有効数字が「どうあるべきか」は
  [flat-field-stats.md](flat-field-stats.md) と `todo-open.md` 項目23 の
  領分で、本書はそれらが**設定という形を取るかどうか**だけを扱う。

## 2. 数え方 —— どうやって見つけたか

棚卸しの値打ちは網羅性なので、記憶ではなく検索で出した。出所と方法:

PR #115 の勘定 (CLI 66 / env 11 / CMake 13) を出発点にして引き直した結果:
**CLI 66 は `--help` の行数としては正しく、パーサの綴り数としては 6 足りない。

`CMakeLists.txt` の「26 の `--*-selftest`」(実数 39) と PR #115 の 13 でも
起きていた。**本書も数を持っているので、同じ理由でいずれ古くなる**
(判断16 が対処)。

棚卸しで出た事実、3件:

1. **`linunit` は書いて読まない。** `writePrefsTo` が prefs.txt に書き、
   `loadPrefs` にはこのキーの枝が**無い**。読んでいるのは `loadSession`
   (`core/app/session.inc:2136`) だが、`writeSessionTo` は `linunit` を
   **書かない**。つまり prefs は書きっぱなし、セッションは読みっぱなしで、
   **両方向とも繋がっていない**。単位を変えて再起動すると `lx` に戻る。
   形式の話ではなく欠陥である (判断15)。
2. **25 キーのうち 5 つは設定ではなく履歴**である (`remoteurl` `rbookmark`
   `rbrecent` `readerfor`、および位置としての `window`)。人が手で書く
   ファイルと、アプリが毎回書き換えるファイルが1つになっている —— これが
   JSONC のコメントを持てるかどうかの分かれ目になる (判断3)。
3. **上限が2つ、別々の書き方で埋まっている。** `readerfor` の 64 は名前つき
   定数 `READER_MEMO_MAX`、`rbrecent` の 10 は `loadPrefs` の中の裸の
   リテラルである。どちらも設定候補ではないが、後者は名前も持っていない。

### 3.2 (B) セッションにあるが「設定」の顔をしているもの

**線の引き方 (これは判断である、と明記する)。** 提案する規準:

> **その行を消したとき失われるのが「何を開いていたか」なら document、
> 「どう見せるか / どう測るか」なら preference。**

ただし**例外を1つ置かねばならない**: 数値の意味を変える設定は、preference で
あってもセッションに**も**残る必要がある。印刷された数値が何を意味したかは、
その時の設定と一緒でなければ再現できないからである。板 row 104 の
`seriespanel` 行 (フィット法・窓) はまさにこの理由で既にセッションに入って
いる ——「**印刷された数値の MEANING の一部**だから一緒に運ぶ」。
だから preference / document は**排他ではない**。設定ファイルは「次に起動
したときどうあってほしいか」を持ち、セッションは「そのとき実際どうだったか」
を持つ。同じキーが両方にあってよく、**セッションが勝つ** (判断11)。

セッション行のうち、この線で preference 側に立つもの:

| 行 | 何を決めるか | 数値を動かすか |
|---|---|---|
| `linkrange` / `rangescope` | 表示レンジの決め方 (毎フレーム自動 / stack 毎 / 全画像連動) | **動かす** — 各面の黒/白が決まる |
| `cmpfollow` | B が A のフレーム番号に追従 | **動かす** — どのフレームと比べたか |
| `cmprange` | A/B の表示レンジの関係 (各自 / A に合わせる / union) | **動かす** |
| `compare` | 比較モード・wipe/split 位置・diff ゲイン・abs・blink | **一部動かす** (diff 系) |
| `analysis` | 選択中のアナライザ・自動再実行・参照線 | **動かす** (アナライザ選択) |
| `seriespanel` | フィット法・窓・表示プレーン・SNR 単位 | **動かす** |
| `projection` | 畳み方 (mean/max/min)・Y 軸・H/V の表示 | **動かす** (畳み方) |
| `projstatlayout` | 統計表の並び・小数桁・all 行・行順 | **一部動かす** (all 行) |
| `abstats` | A/B 統計の配置・ヒストグラムのプレーン | 表示のみ |
| `histlog` | ヒストグラムの Y 軸 log | 表示のみ |
| `roichannel` | ROI 表のチャンネル | 表示のみ |
| `panels` | 10 パネルの開閉 | 表示のみ |
| `rbplace` | Browse の各インスタンスの現在地 | document 寄り (履歴) |
| `linunit` | 単位の prefill | 表示のみ (§3.1 の片道) |

### 3.5 (E) CMake —— `option()` は 0 個

PR #115 の「13」は失効。`VIEWER_WITH_EXR` は PR #122 で撤去され、いま
利用者が上書きできる CACHE 変数は **`VIEWER_REPO_URL` の1つだけ** (peer を
自己導入するときに `git clone` する先; 既定 `https://github.com/klimemam/viewer.git`)。
残りの `CACHE ... FORCE` 群 (GLFW / OpenEXR の下請けビルド) は毎回上書き
されるので利用者の手が届かない。**SIMD・浮動小数点モデル・スレッド数・精度に
関するフラグは1つも無い** —— つまり「ビルドの仕方で数値が変わる」経路は
現状**存在しない**。これは設定の設計にとって良い前提条件なので、明記しておく。

`VIEWER_REPO_URL` だけは設定候補である: フォークを使う人にとって、
peer の導入元を変えるためにビルドし直す理由が無い (判断17)。

## 4. 分類 —— 3軸

読み手が「あれはどこにあるか」を引けるように、3つの軸で分ける。

**軸1 · 有効範囲 (scope)** —— 誰に効くか

| 値 | 意味 | 住処の帰結 |
|---|---|---|
| `application` | このマシンのこの利用者に、常に | 設定ファイル |
| `panel` | パネルのインスタンスごと (Browse は複数立つ) | 設定ファイルは**初期値だけ**持ち、実体はインスタンス |
| `document` | 開いたもの1つごと (`cfa`、`npyread`、ROI の可視) | セッション。**設定ファイルに置かない** |
| `invocation` | この1回の起動 (`--serve`、`--*-selftest`、`--bench`) | CLI のみ。**設定ファイルに置かない** |

**軸2 · 安定性 (stability)** —— どれくらい持つべきか

| 値 | 意味 | 例 |
|---|---|---|
| `preference` | 利用者が決めて、変えるまでそのまま | theme、`dragpans`、`seqload` |
| `view state` | 今この1枚をどう見ているか。次に開いたものに引き継ぐと**害** | zoom/pan、wipe 位置、選択中の ROI |
| `history` | アプリが勝手に書き足す。人は編集しない | `rbrecent`、`readerfor`、`window` の位置 |

**軸3 · 帰結 (consequence)** —— 変えると何が変わるか

| 値 | 意味 | 数 |
|---|---|---|
| `measuring` | **画面に出る数値そのものが変わる** | CLI 12 + セッション由来 12 + prefs 2 (`membudget`・間接的に `seqload`) |
| `presentation` | 見え方・並び・配置だけ | 大多数 |
| `plumbing` | どこから読むか・どこで走るか (数値は同じであるべき) | `remoteexe`、`procpolicy`、`pythonexe`、`readerdir` |

**交差表** (代表例のみ、全数は §3):

| | measuring | presentation | plumbing |
|---|---|---|---|
| **application / preference** | `membudget`、`seqload`、raw の既定 10、detrend の既定 (F5)、有効数字 (F3)、ビン数 (F4) | theme、compact、gamma、grid、frame、`rbnatural`、クリック挙動 (F1) | `remoteexe`、`procpolicy`、`pythonexe`、リーダ探索パス (F7)、`EDITOR` |
| **panel / preference** | `projMode`、`fitMethod`、`winMode` | Browse の flat/tree/sort、`histLog`、パネル開閉 | — |
| **document** | `cfa`、`npyread`、`rangeScope` | ROI の可視、表示レンジの値 | — |
| **invocation** | — | `--zoom`、`--center` | `--serve`、`--no-window`、`--*-selftest` |

### 4.1 measuring 級だけは別扱いが要る

正典の規則は「**数値の意味は、どこで・どうやって見せたかに依存してはならない**」
である。`--remote-policy` が「どちらで走らせても同じ数値」を設計上の約束に
しているのも、板 row 157 が並び順を「stack にとっては測定の一部、一覧に
とっては表示の好み」と切り分けたのも、同じ規則の適用である。
measuring 級の設定は、この規則と**構造的に衝突しうる唯一の階級**なので、
以下3つを形式のレベルで課すことを提案する:

- **M1 · 申告を伴う。** measuring 級の値は、それで出た結果に付いて回る
  (detrend が既に `cutoff:` 行でやっていること)。設定ファイルにあるだけで
  結果に現れない measuring 級の設定を作らない。
- **M2 · セッションが勝つ。** 設定ファイルは「次回どうあってほしいか」、
  セッションは「そのとき実際どうだったか」。設定ファイルを後から触っても、
  保存済みセッションを開き直したときの数値は変わらない。
- **M3 · 既定は自己記述的でなければならない。** できないなら**既定を置かず、
  未設定は聞く** (`seqload` の `ask` が既にこの形)。理由は
  flat-field-stats.md 判断7 —— **既定値がそのまま社内の基準値になる**。

## 5. JSONC の提案

### 5.1 住処と、今のファイルとの関係

```
%APPDATA%/viewer/            (Windows)   ~/.config/viewer/   (POSIX)
├─ settings.jsonc     ★新   人が書く。アプリは読むだけ、絶対に書き戻さない
├─ state.json         ★新   アプリが書く。履歴・ウィンドウ位置。人は編集しない
├─ layout.ini               ImGui が所有。そのまま
├─ autosave*.vsession       document。そのまま
└─ prefs.txt          撤去  settings.jsonc + state.json に分かれる
```

- **prefs.txt は置き換える**が、**2つに割る**。今の 25 キーのうち 20 が
  設定、5 が履歴で、`savePrefs()` はトグルのたびに (`core/browse/panel.cpp`
  だけで7箇所から) ファイル全体を書き直す。**同じ規律で JSONC を書けば、
  利用者が書いたコメントは最初のトグルで消える。** VS Code は
  JSONC を保存しながらコメントを保つ編集器を持っているからできているので
  あって、こちらは持っていない。割るのが安い (判断3)。
- **layout.ini は置き換えない。** ImGui が読み書きする形式で、こちらが
  持つと ImGui を更新するたびに追随費用を払う。パネルの位置は
  「どこに何を置いたか」で、設定ではない。
- **`.vsession` は置き換えない。** §3.2 の線で document 側。
- **設定ディレクトリの解決は1箇所にする** (§3.4 の二重定義、板 row 185)。
  settings.jsonc がもう1つ独立な解決を持てば三重になる。

### 5.2 未知キー —— 飛ばすが、黙らない

セッション形式の規則は「古い読み手は未知キーを飛ばす」である。
**設定はこれを継承しない**ことを提案する。

セッションの未知キーは「新しい版が書いた、この版が知らない**事実**」なので、
飛ばしても嘘にならない。設定の未知キーは**打ち間違い**である可能性が同じ
くらい高く、黙って飛ばすと「設定したのに効かない」になる ——
**#50 が起票された症状そのもの**を、形式のレベルで再生産することになる。

- 未知キーは**読まないが、名指しで1行**言う (log + Messages パネル)。
- 綴りが既知キーに近いときは併記する: `"naturlSort" は知らないキーです
  (settings.jsonc:14) — "browse.naturalSort" のことですか?`
- **退役キーは名指しで「もう無い」と言う。** prefs.txt の `rbadv` が既に
  「読んで捨てる」の前例を持っているが、あれは黙っている。JSONC では
  「このキーは PR #NNN で撤去されました」まで言える (コメントが書けるので、
  移行のときにファイルへ書き込むこともできる)。

### 5.3 壊れたファイル —— 名指しで断り、既定に落ちない

リポの規則は「名指しで断る」である (`manual.md` が形式について 8 箇所で
そう書いている)。設定にも同じ規則を適用する。**ただし粒度を2段に分ける**:

- **ファイル全体がパースできない** (括弧の対応が取れない等) →
  **既定に落ちない。** 起動はするが**設定を一切読まず**、行・列・理由を
  名指しし、画面にも出す。そして **settings.jsonc を書き戻さない** ——
  上書きすると、直す元になる利用者の記述ごと消える。
- **1つのキーの値が型違い / 範囲外** → **そのキーだけ**名指しで断り、
  そのキーだけ既定を使う。ファイル全体は生かす。
  100 行のうち1行の打ち間違いで全部を捨てるのは、断るのではなく罰である。

対比のため今の挙動を書いておく: `loadPrefs` はヘッダが
`viewer-prefs ` で始まらなければ**黙って return する**。壊れた prefs.txt は
「設定が全部リセットされた」としか見えない。今の形式は既に規則に反している。

### 5.4 「未設定」と「既定と同じ値」を分ける

**書いていない = 未設定。既定値でもキーは書かない。アプリは既定値のキーを
書き出さない** (VS Code と同じ規律)。

なぜ区別が要るか —— **既定が変わったときに効く**。板 row 157 が実例で、
一覧の並びの既定を辞書順から自然順に**変えた**。あのとき必要だったのは:

- 辞書順を**明示的に選んだ**人 → そのまま辞書順
- 何も選んでいない人 → 新しい既定 (自然順) に乗る

「既定と同じ値が書いてある」を「未設定」と同一視すると、この区別が消える。
そして既定が変わるのは例外ではない —— row 157 は「今は見えている順が嘘なので
変えるべき」という理由で変えており、同じ理由はまた来る。

帰結として:

- **既定に戻す操作 = キーごと消す。** 値を消すのではない。
- **`null` は書けない。** 書いてあれば型エラーとして行・列を名指しする。
  `null` を「明示的に既定」の意味にすると、上の区別を復活させるために
  三値 (未設定 / null / 値) が要るが、`terminology.md:105-108`
  (「値は読めなければ未設定、バケツは1つ」) がその三値を既に却下している。

### 5.6 パーサ —— 自前で書く

このリポに JSON パーサは無い (`third_party/` は `stb` だけ)。読む形は
**1階層のオブジェクト、スカラーと文字列配列、深さ 3 まで**で、
`//` `/* */` と末尾カンマを許す最小のパーサは数百行に収まる。
vendored ライブラリを入れるより自前を薦める理由は大きさではなく
**断り方**である —— §5.3 が要求するのは「行・列・理由の名指し」と
「キー単位の断り」で、汎用パーサの例外メッセージはそのどちらの形にも
なっていない (判断2)。

## 7. 残る穴 (棚卸しでは埋まらないもの)

- **有効数字 (F3) とビン数 (F4) は、設定の形が決まっても値が決まらない。**
  どちらも `todo-open.md` の4択・2択が未決で、選ぶのは Fable の仕事。
- **float32 固定 (F8) は設定ではなく欠陥**である。今すでに誤った平均を
  TSV に出しており、「設定で選べるようにする」は答えの1つでしかない。
- **キーバインド (§3.8) は棚卸しの外**。割り当て表そのものの設計が要る。

## 8. 数の扱いについて

本書は数を多く持っている (72 / 20 / 43 / 12 …)。`printUsage()` のコメントが
自分について言ったこと ——「ここに書いた数は事実の2つ目の写しで、写しは
古くなる」—— は本書にもそのまま当てはまる。**数が古くなったときに直す先は
本書ではなく §2 の「方法」の列である**: 同じ検索をやり直せば同じ表が出る、
という形で書いてあるのはそのためである (判断16)。

## 9. 判断リスト

番号で答えられる。各項が推奨と、その理由1行。

1. **形式は JSONC を採る。** 指示どおり。設定ファイルは「なぜそうしたか」が
   値と同じくらい重要で、それを値の隣に書ける実用形式は他に無い。
2. **パーサは自前で書き、JSON ライブラリを vendor しない。** 読む形は
   1階層のスカラーと文字列配列だけで、§5.3 が要求する「行・列・理由の
   名指し」と「キー単位の断り」は汎用パーサの例外の形になっていない。
3. **人が書くファイルとアプリが書くファイルを分ける
   (`settings.jsonc` / `state.json`)。** `savePrefs()` は今トグルのたびに
   ファイル全体を書き直すので、同じ規律で JSONC を書けば利用者のコメントは
   最初のトグルで消える。
4. **`layout.ini` は置き換えない。** ImGui が所有し ImGui が書く形式で、
   こちらが持つと更新のたびに追随費用を払う。
5. **`.vsession` は置き換えない。ただし measuring 級のキーは両方に載る。**
   設定は「次回どうあってほしいか」、セッションは「そのとき実際どうだったか」
   で、両者は排他ではない (§3.2)。
6. **未知キーは読み飛ばすが、名指しで1行言う (近い既知キーを併記)。**
   セッションの未知キーは事実だが設定の未知キーは打ち間違いで、黙って
   飛ばすと #50 の症状「設定したのに効かない」を形式のレベルで再生産する。
7. **パースできないファイルは既定に落ちず、行・列・理由を名指しして
   その回は設定を読まない。書き戻さない。** リポの規則は名指しで断ることで、
   上書きすれば直す元の記述ごと消える。
8. **値のエラーはキー単位で断り、ファイル全体は生かす。**
   100 行のうち1行の打ち間違いで全部を捨てるのは、断るのではなく罰である。
9. **「未設定」はキーが無いことで表す。既定値のキーは書き出さない。
   `null` は禁止 (型エラーとして名指し)。** 既定が変わったとき (板 row 157 の
   自然順が実例) に、明示的に選んだ人と選んでいない人を分けられる唯一の表現。
10. **measuring 級は独立した節に置き、既定をそこに書かず申告を強制する。**
    既定値がそのまま社内の基準値になる (flat-field-stats.md 判断7)。
11. **measuring 級はセッションが設定ファイルより強い。**
    印刷済みの数値の意味を、後から設定ファイルを触って変えてはならない。
12. **invocation 級の CLI 52 個は設定ファイルに写さない**
    (`--serve` `--no-window` `--secondary` `--bench*` `--*-selftest`
    `--crash-test` `--session` ほか)。「この1回どう起動するか」であって
    「どう振る舞うか」ではなく、混ぜると `ba40ba8` が塞いだ「scripted run が
    利用者の状態を読む」穴が別の口から開く。
13. **既定を決める CLI 20 個は設定キーと1対1にし、同時に与えられたら
    CLI が勝つ。** 一時的な上書きが CLI の役目で、真実が2つ要らない。
14. **キーバインドは v1 に入れないが、入る場所 (`input`) をコメントで
    空けておく。** 今どこにも存在しない (§3.8) ので棚卸しの外の設計が要り、
    それを待って v1 を止める理由が無い。
15. **`linunit` の片道は移行を待たずに直す。** 書いて読まないキーは、
    移行のときに「既定が lx」と「利用者が lx を選んだ」を区別できなくする
    —— 判断9 が守ろうとしているものを、移行の初日に1つ失う。
16. **本書の数は §2 の「方法」の列とセットでのみ意味を持つ。数が合わなく
    なったら数ではなく方法を直す。** PR #115 の CMake 13 と
    `CMakeLists.txt` の「26 の selftest」が、写した数が古くなる同じ事故を
    2回起こしている。
17. **`VIEWER_REPO_URL` は設定から上書きできるようにする** (ビルド時の値は
    既定のまま)。フォークを使う人が peer の導入元を変えるためにビルドし直す
    理由が無い。
18. **環境変数は3つ (`EDITOR` / `VIEWER_SERVE_PLUGINS` /
    `VIEWER_SERVE_PIN_BUDGET_MB`) だけ設定ファイルにも置き、環境変数が勝つ。
    残る8つは置かない。** 前者は利用者の好み、後者は試験の口である。
19. **パネル内トグル 43 のうち設定に昇格するのは、「まっさらな起動のとき
    どうあってほしいか」に答えるものだけ。** 「今この1枚をどう見るか」は
    view state で、設定に置くと次に開いたものにも掛かる。
20. **F10 (祖先行) の前例を規準として採る —— 設定にしない判断も記録する。**
    設定は取りうる状態の数だけ正しさを保証する義務を増やすので、
    「断った」ことが後から読めなければ同じ要望が何度も戻ってくる。
