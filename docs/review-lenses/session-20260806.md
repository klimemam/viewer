# Session / persistence lens — re-derivation (adversarial review)

Target: `core/main.cpp` on `ref-integrate` @ 39b6c0b (working tree).
Scope: `writeSessionTo`/`saveSession` (6584–6920), `loadSession` (7849–8296), and every
open/resolve path they call (`loadNpy`/`loadNpyBuffer`, `loadNpz`/`npzOpenMember`,
`loadRaw`, `openRemote`/`openRemoteStack`, `openWithReader`, `findSequenceSiblings`,
`startSequenceLoad`/`pumpSequence`, `pumpSequenceAndQueue`, `resolveSeriesRestore`,
`migrateLegacyLevels`, `pumpStackAverages`, `pumpCompareSlotRestore`, `resolveB`).

Excluded per instructions (already handled on the branch, verified present, not re-reported):
identity-before-bytes for vnz/reader origins; decimated-remote crop refused by
`cropInPlace` (6436–6438); the vnz/reader already-here dedupe dropping later lines'
display state (8226–8232, recorded); local:// mtime/fsize baseline.

Every finding below survived an attempted refutation against the code; refuted
suspicions are listed at the end with the reason they died.

## Confirmed findings (all MINOR, PRE-EXISTING, main-side session machinery)

### F1. `cmpSlotRestore` survives `closeAll` — a dead session's compare-slot wants graft onto whatever opens that path next

- `App::cmpSlotRestore` declared 757; filled by the `cmpslot` parse at 7900–7903;
  drained only by `pumpCompareSlotRestore` (2240–2256), which erases an entry **only
  when it lands**. The comment promises "retried until it lands or the load settles" —
  the settle half does not exist: no code path ever discards an unresolved want.
- `closeAll` (3982–4058) clears every other restore queue precisely so that "orphan
  frames from a previous load must not graft onto the restored list" (its own words,
  and loadSession's at 7857–7859): `seqRestore` 3996, `pendingAvg`/`avgRestore`
  3997–3998, `seriesRestore` 4022, `seqLevelLegacy` 4023, compare-B state 4044–4045.
  `cmpSlotRestore` is the one it misses. `loadSession` doesn't clear it either.

Scenario (session file): session A contains `cmpslot -1 D:\data\x.npy`; `D:\data\x.npy`
is missing at restore time, so its `image` line fails (toasted) and the want stays
queued. The user then loads session B — one with **no** cmpslot lines — which opens
`D:\data\x.npy` as an ordinary image. `pumpCompareSlotRestore` (called from the
histogram/projection draws, 15441/16042) binds the stale want: slot C appears in
session B, which never asked for a slot. Variant without a second session: user fixes
the missing drive an hour later and opens `x.npy` by hand — it silently becomes slot C.

Wrong outcome: compare state (extra slots) from a discarded session resurrects in a
later, unrelated session; the A/B/C stats, per-slot histograms and projections all
follow it. Fix shape: clear `app.cmpSlotRestore` in `closeAll` (or at load-settle).

### F2. In-file (frame-axis) stacks: everything the stack's session line carries lands on frame 0, while `seqframe` puts the user back on the representative frame

The save side writes ONE line per stack from the **representative** frame (the frame
it was left on — `isSavedLine`, 6596–6614): its black/white (6712), lut (6711),
cfa/cfaPattern/cfaColorize and crop (6723–6725), `imgbatch` from its `batchId`
(6728–6730), and `seqframe <rep.seqIndex>` (6732).

The load side applies all of it to `cur()`:
- `loadNpy` → `loadNpyBuffer` (4843–4899) builds the whole stack; `addImage(first)`
  leaves `app.current` on **frame 0** (4269–4270); frames 1..N-1 are pushed directly
  and inherit frame 0's *decode-time defaults* (black/white 4870, batchId 4875 — no
  lut, no cfa).
- Then 8243–8248 (cfa trio + `cropInPlace(*cur(), …)`), 8262–8264 (black/white/lut)
  and 7995 (`cur()->batchId = batchReuse(nm)`) all hit frame 0 only.
- `seqframe` (8125–8131) then selects the representative frame — which holds only
  defaults. With the default `rangeScope == 1` nothing recomputes on selection
  (9221–9225), so the user is standing on the rep frame looking at the default
  auto-range/lut/batch, while the saved state sits invisibly on frame 0.

(Folder stacks are fine: the head IS the representative frame's file, and
`pumpSequence` copies black/white/lut/cfa/batch from the head to every sibling at
integration, 8814–8821 — which happens *after* the session lines were applied.)

Concrete scenario: `burst.npy` is `(100,H,W)`; the user stands on frame 42, sets
range 100..4000, moves the stack to batch "night run", saves. Restore: frame 42 is
selected showing the **default** range; frame 0 (not on screen) holds 100..4000 and
sits alone in batch "night run" while frames 1–99 sit in the folder-leaf batch
"captures" — violating the invariant every other path enforces ("frames never move
between batches one by one", `moveStackToBatch` 3840–3873; loadNpyBuffer's own
comment at 4871–4874: "A stack is in ONE batch").

Wrong outcomes, in escalating order:
1. Restored view shows the wrong range/lut on the frame the session put you on.
2. The stack is split across two batches. `closeBatch("captures")` (3746–3774
   collects seqIds by per-frame batchId) closes the **whole** "night run" stack.
3. Silent decay on the next cycle: after restore, `si->lastImageIdx` = the rep frame
   (9232), whose batchId is the leaf batch and whose black/white are defaults — so the
   next autosave writes `imgbatch captures` and the default range. One save→load→save
   round trip silently reverts the batch assignment and loses the range, without the
   user touching anything.
4. Cosmetic: `batchReuse(leaf, dir)` created the leaf batch before `imgbatch` moved
   the head out, and `loadSession` never calls `pruneEmptyBatches` (3815–3838), so a
   restore of a renamed batch leaves an empty phantom heading in Files until the next
   close/move (this part hits folder stacks too).

Fix shape: for `seqId != 0`, apply the line's display state and `imgbatch` to every
frame of the stack (or to the stack via `moveStackToBatch`), and/or apply black/white/
lut to the frame `seqframe` names rather than to `cur()`.

### F3. ssh:// and Browse-local (local://) FOLDER stacks: the session records the stack, the restore silently hands back one loose frame

- Save: a remote folder stack (one doc per file, urls minted by `makeRemoteUrl`,
  11217–11218 — `local://` when host is empty; membership lives only in
  `SeqInfo::remoteFiles`, 12541, which `writeSessionTo` never persists) passes the
  `!inFile` test (6736–6738, frames have distinct paths) and gets `seqload 1` plus
  `seqname`/`seqaxis*` lines.
- Restore: the image line's `isRemote` branch (8210–8215) calls `openRemote(p)` —
  for a single-frame file that is one doc, no stack (the stack branch at 12458
  requires `m.frames > 1`, i.e. an in-FILE axis). Then `seqload` (8132–8143) calls
  `findSequenceSiblings(cur()->src->path, …)` — a **local filesystem directory scan**
  (8509–8515: `parent_path` + `is_directory`) that returns empty for any
  `ssh://…`/`local://…` url, so `files.size() >= 2` never holds and nothing is queued.
  No failure is recorded — the branch just does nothing.
- Knock-on losses, all silent: `seqname` (8004–8011) and `seqaxisvals/unit/name`
  (8017–8046) find neither a SeqInfo nor a queued `seqRestore` entry for the doc and
  drop the user-given stack name and hand-typed x-axis; a series member naming that
  stack fails `seqIdOfFirstFramePath` (`d->seqId != 0`, 8895) — that one is at least
  counted by the restore toast.

Scenario (session file): Browse to `ssh://user@cam/data/10lx/`, "Open as stack"
(30 files), rename the stack "10lx dark", give it an axis, put it in a series, save.
Restore: one loose frame `frame_007.npy` (the frame the user was left on), no stack,
no name, no axis; the series comes back minus that member ("1 member(s) … could not
be resolved"). Identical failure for a local folder opened **through Browse** (its
paths are `local:///…` urls) — the same folder opened via File > Open restores fine,
which makes the discrepancy look like user error.

Sub-symptom (frame-axis remote file, which otherwise DOES restore via 12458–12501):
`seqframe` runs at parse time when only frame 0 has landed (siblings arrive through
`rfEnqueue`), so `framesOfSeq` has no `seqIndex == want` yet (8128–8130) and the
saved frame position is dropped — the stack comes back on frame 0.

Fix shape: persist the membership the save side already knows (`SeqInfo::remoteFiles`
+ host/port) as an additive key, or teach the `seqload` branch to route urls through
the remote lister; at minimum count the drop so the restore toast stops reading clean.

### F4. The path-keyed cross-reference lines (`cmpslot`, `seriesmember`, `stackavg`) omit `npzMember` — two image members of one .npz mis-bind on restore

The registry's identity tuple is path+npzMember+fileFrame+npyRead+mtime/fsize (393),
and the per-doc image lines carry `member` (6704) precisely so "a session can come
back to exactly this member" (npzOpenMember, 5104–5122). But all three lines that
*name a doc/stack from elsewhere* speak bare path:

- `cmpslot` writes `seqIndex + d->src->path` (6635–6638); the pump matches
  `d->src->path == w.path` only (2245–2249). Two members of one `.npz` share that
  path; the want latches whichever member sits earlier in `app.images`, and the
  second want then dies on the dup check (2251–2254) — one slot lost, the other on
  the wrong member.
- `seriesmember` writes `app.images[fr.front()]->src->path` (6836–6837);
  `seqIdOfFirstFramePath` (8888–8900) matches path (with a `taken` list and
  `preferBatch`, neither of which can tell two members of one file apart — the
  comment at 8884–8887 concedes same-path stacks in one batch "are told apart by
  nothing but this list").
- `stackavg` writes `avgOfPath` (6799); resolution takes the first stack with that
  path (17009–17010).

Scenario (session file): `sweep.npz` holds two 3-D members, `dark` and `bright`, both
opened (two stacks, both with `src->path == sweep.npz`, distinguished only by
`npzMember`), both in one batch, in a series with values 0 and 100. The user opened
`bright` first, so it precedes `dark` in `app.images` and therefore in the saved
line order. The series block, written in member order, says `seriesmember 0 1
…\sweep.npz` then `seriesmember 100 1 …\sweep.npz`. On restore, member value 0 claims
the first unclaimed same-path stack in images order — **bright** — and 100 lands on
dark. Both members "resolve", the toast reads clean, `made` counts the series as
restored, and the linearity fit is now anchored on swapped axis values — the exact
"silently misplaced point on the axis the fit is taken against" that the
resolveOnePendingSeries comment (9015–9021) calls worse than a loss. The next
autosave (written from the resolved series) makes the swap permanent. The same
ambiguity puts a `cmpslot` on the wrong member and averages the wrong member's stack
for `stackavg`.

Fix shape: append the member name to these three lines (additive — older viewers
drop unknown trailing fields only if formatted as new keys, so likely a
`cmpslotmember`-style companion key or a v2 line), and match on (path, npzMember).

## Refuted suspicions (attempted, did not survive)

- `linunit` parsed by loadSession (8123) but never written by writeSessionTo — not a
  drop: it is a prefs key (`savePrefs`, 7189); the session parse is legacy acceptance.
- `current` ordinal drift across failed image lines — both sides count the same set
  of `image` lines; a failed line still increments `lineOrd` (8170), ordinals stay aligned.
- Annotations vs restored crops — anns are saved post-`shiftAnnotations` in cropped
  coordinates and the crop is reapplied before ann lines parse; coordinates agree.
  ROI/POI label counters are continued (8278–8283); `selann` index round-trips.
- `compareb` by name+frame latching the wrong same-named doc — accepted design (uids
  cannot survive; comment 6656–6657), and npz members carry distinct display names.
- Batch-name collision on restore — `batchReuse` merges by name **by design**
  (2092–2094); `uniqueBatchName`/`renameBatch` keep live names unique to protect it.
- `seqframe` silently skipped for folder stacks (cur()->seqId==0 at parse) — no wrong
  outcome: the saved line's path IS the representative frame's file, and
  `startSequenceLoad` keeps the head at its file position (8618–8621).
- Save during the folder-rescan / series-drain window — handled: `seqload` re-asked
  via `seqLoadingId` and `app.seqRestore` (6740–6776), series round-trip verbatim
  from `seriesRestore` (6841–6869), pending picker sweeps and legacy levels counted
  as lost (6870–6885).
- Preview promotion by save — refuted; `isSavedLine` excludes previews without
  promoting (6597–6601), per the saveSession comment.
- §3.3 `npyRead` round-trip for in-file stacks and npz members — sound: written per
  saved line (6710), applied to the whole rebuild (`loadNpyBuffer` passes it to every
  frame's decode, 4848/4865; `loadNpz` → `npzOpenMember` 5817–5820), out-of-range
  values clamped to native (7986–7990), cleared after each line (8255). Identity keys
  match a fresh open. Folder-stack siblings decode natively (8682–8687, 8714) — but a
  folder stack whose head holds a declaration cannot be built fresh either
  (`npyReReadAs` dissolves stack membership, 6033), so the session cannot record a
  state it then fails to reproduce.
- Cross-session graft via the other restore queues — refuted for everything except
  cmpSlotRestore (F1): `seqRestore`, `avgRestore`, `seriesRestore`, `seqLevelLegacy`,
  `pendingAvg` are all cleared in `closeAll` (3996–4023); stale `cmpExtra` uids are
  pruned at resolve (2149–2154) and uids are never reused.
- `pendingMember`/`pendingRead`/`pendingLut` leaking across a failed image line —
  cleared on both success and failure paths (8254–8260).
- Two stacks from the same folder (canon-blessed duplicate) restoring — works: two
  seqRestore entries matched by uid, `taken`+`preferBatch` keep their series apart.
- Derived/processed/plugin docs absent from sessions — by design and the comments say
  so (6690–6699, 6103); frame averages persist as the `stackavg` recipe; the average
  doc's own display state is recomputed, inherent to recipe-only persistence.
