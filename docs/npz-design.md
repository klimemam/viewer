# .npz に key が入っているときどう扱うか

> **2つの npz がある。** この文書は**人が `np.savez` で書いた npz** を viewer が
> どう読むか。もう1つ、**viewer 自身が書く容器**があり (予約メンバ `__viewer` /
> `__layer_<i>` / `__parent_<i>`)、そちらは
> [input-adapters.md §4.11](input-adapters.md) にある。
> **区別は `__viewer` メンバの有無ひとつ**で、無ければこの文書の規則が働く。

ユーザー提起 (2026-08-03):「npz で array 直ではなく、key が入った場合ってどういう対応しましょうかね」。

## 1. 今どうなっているか (コードで確認)

`loadNpz` (main.cpp 3661) は zip 内の `*.npy` メンバを**全部**、名前順に**黙って開く**。
各メンバは `loadNpyBuffer` → `decodeNpyBuffer` を通り、名前は `file.npz:key`。
セッションには `member <key>` が残り、復元は zip 経由で同じメンバを読み直す。

形の解釈 (decodeNpyBuffer 3900-3922):

| メンバの shape | 今の結果 |
|---|---|
| (H,W) / (H,W,C) / (F,H,W) など | 画像 / stack。**正しい** |
| 4次元より深い | **先頭要素 [0] を黙って取る** |
| **1次元 (N,)** | **H=1, W=N の「画像」になる** |
| スカラー | 1×1 の「画像」になる |
| 文字列・object dtype | `unsupported dtype` で拒否(正しい) |

### ここが欠陥

**1次元の配列が「高さ1ピクセルの画像」として開かれる。**
露光時間の列 `exposure_ms = [1,2,5,10,...]` を渡すと、それが**絵として** Files に並ぶ。
これは正典の「黙って捏造しない」に反する — 1次元配列は画像ではない。
4次元超の `[0]` 黙殺も同じ family。

そして**全メンバを無条件に開く**ので、`{data, dark, flat, exposure_ms, gain}` の
npz を開くと画像3枚 + 偽画像2枚が Files に並ぶ。

## 2. 提案 — npz は「入れ物」であって画像ではない

正典の層 (frame ⊂ stack ⊂ series ⊂ batch) にそのまま乗る:

- **npz ファイル = batch** (フォルダを開いたときと同じ意味。「一緒に開いたもの」)
- **メンバ = stack** (frame 軸があるとき) **または frame**
- 形の違うメンバが同居してよい (`dark` 480x640 と `flat` 1024x1024) — 別 stack になるだけ

### 2.1 メンバを役割で分類し、それを言う

| shape | 役割 | 扱い |
|---|---|---|
| 2次元以上で画像として解釈可能 | **画素** | stack / frame として開く |
| 1次元 (N,) | **軸か metadata** | 画像にしない。frame 数と一致すれば **per-frame 軸の候補**、そうでなければ metadata |
| スカラー | **metadata** | プロパティに出す (露光・ゲイン・温度…) |
| 文字列 / object | **metadata** | 同上 (今は拒否するだけ) |
| 4次元超 | **曖昧** | 黙って [0] を取らない。「どの軸を frame にするか」を訊くか、明示的に拒否する |

### 2.2 1次元 key は「捨てるもの」ではなく、いま一番欲しいもの

Temporal パネルには既に**フレームごとの X 軸**がある (貼り付けで与える。
カンマ/空白/タブ/改行区切り)。**長さが frame 数と一致する 1 次元 key は、
まさにその軸そのもの**。

つまり撮影スクリプトが `np.savez(out, data=stack, exposure_ms=exp)` と書けば、
リニアリティのチャートの X 軸が**ファイルから直接**来る。貼り付けが要らなくなる。

- 開くときに「軸候補が N 本ある」ことを言い、名前で選ばせる (`exposure_ms`, `lux`)
- 単位は key 名から推測しない。**軸名と単位はユーザーが確定する** (既存の
  seqaxisname / seqaxisunit にそのまま入る)

### 2.3 何を開くかを選ばせる — 既存のフォルダ picker と同じ形

今の「全部開く」は、key が意味を持つファイルでは間違い。
**メンバ一覧の picker** を出す (フォルダ picker と同じ語彙・同じ操作):

```
+- open dark_sweep.npz ----------------------------------+
| [x] data          (24, 480, 640)  uint16   -> stack 24 |
| [ ] dark          (480, 640)      uint16   -> frame    |
| [x] exposure_ms   (24,)           float64  -> axis     |
| [ ] gain          scalar          float64  -> metadata |
|                                                         |
| batch: dark_sweep.npz          [Open]  [Cancel]         |
+---------------------------------------------------------+
```

- **画像メンバが1つだけなら picker を出さずに開く** (今の使い勝手を落とさない)
- 軸候補は「その stack に適用する」チェックとして出す
- metadata は開く対象ではなく、**プロパティに残る**

### 2.4 Browse からも中身が見えるべきか

`.npz` の行を展開して中のメンバを見せるのは自然 (入れ物なので tree と相性が良い)。
ただし**リモートでは peer に zip の中身一覧を返す動詞が要る** — プロトコル追加。
ローカル先行、リモートは後続で良い。

> **後続が来た (2026-08-17, issue #217)。** その動詞は `MSG_NPZ_SCAN` (protocol 13)
> で、返すのは**事実だけ** — member 名・shape・descr・宣言サイズ・展開可否と、
> 小さい member の値。分類 (`npzScan` の RImage/RAxis/RMeta/RAmbig/RBad) と
> picker は client の 1 箇所のままで、行の文言がどちらの端から来ても変わらない
> ことが構造で保証される。member の画素は `[key][node]` トレーラで 1 本ずつ
> 遅延 materialise される。設計は `docs/remote-reader-design.md §10`。
>
> **行の展開そのもの (Browse の tree にメンバを出す) はまだ**。今日の道は
> 「行をダブルクリック → SCAN → 同じ picker」で、1クリックのプレビューは
> 付かない (コンテナに 1 つの幾何は無い)。

## 2.5 人が手で書ける形 — adapter 無しでどこまで言えるか

viewer の容器 (`__layer_0` / `__parent_0`) は**機械のための形**で、往復が保証される
代わりに人が書くものではない。ではユーザーが `np.savez` で普通に書いたとき、
**adapter 無しでどこまで読めるべきか**。

### 2.5.1 いま既に読める(いちばん人間的な形)

```python
np.savez("run42.npz", data=stack, exposure_ms=exposures)   # (480,H,W) と (480,)
```

- `data` は形から stack、`exposure_ms` は**長さがフレーム数と一致するので軸の候補**
- picker が「これを軸にするか」を訊き、**名前と単位はユーザーが確定**する

**つまり stack + 軸は、すでに人間の形で読める。**

### 2.5.2 足りないもの — series・単位・CFA

人が書きたいのに今言えないもの:

| 言いたいこと | 人が書きそうな形 |
|---|---|
| 条件ごとに stack が分かれている | `10ms/data`, `20ms/data`, … (npz のキーは `/` を含められる) |
| 振った条件と単位 | `exposure_ms=[1,2,5,10]` |
| CFA | `cfa="RGGB"` (0次元の文字列) |
| stack の名前 | グループ名 (`10ms`) をそのまま使う |

### 2.5.3 規則(提案)

1. **`/` の前がグループ名**。同じ接頭辞のメンバは1つの stack になり、
   グループ名がその stack の名前になる
2. **1次元配列の長さで役割が決まる**:
   - 長さ == **フレーム数** → `timestamps` の候補
   - 長さ == **グループ数** → `conditions` の候補 (= series になる)
3. **0次元の文字列 `cfa`** は CFA パターンの候補
4. **キー名の末尾は単位の *提案* に使う** (`_ms` `_s` `_lx` `_dB`)。
   **推測して適用はしない** — picker に**既定値として入れて、ユーザーが確定する**。
   「`exposure_ms` は誰かが選んだ名前であって ms である証明ではない」は変えない。
   変えるのは「**黙って捨てる**」から「**候補として差し出す**」へ

```python
np.savez("sweep.npz",
         **{f"{e:g}ms/data": arr[i] for i, e in enumerate(exposures)},
         exposure_ms=exposures,      # 長さ == グループ数 -> conditions
         cfa="RGGB")
```

これで **series・条件・単位・CFA・stack 名が、素の `np.savez` で言える**。

### 2.5.4 2つの形の役割分担

| | 人が書く形 (この文書) | viewer が書く容器 (input-adapters §4.11) |
|---|---|---|
| 誰が書く | 人 (`np.savez` 一行) | harness / viewer |
| 曖昧さ | **ある**。picker で1回確定する | **無い**。層も軸も明示 |
| 往復 | 保証しない | **保証する** (書いて読んで同一) |
| 用途 | 手元のデータをとりあえず開く | 変換結果の保存・キャッシュ・peer への配置 |

**確定した内容はセッションに残る**ので、同じファイルを次に開くときは訊かれない。
一度確定すれば「人が書いた形」も実質的に曖昧さゼロになる。

## 3. 決めてほしいこと

1. **全部開く → picker、で良いか。** (推奨: 良い。画像1つなら picker なし)
2. **1次元 key を軸として提案するか。** (推奨: する。これが一番効く)
3. **metadata (スカラー/文字列) をどこに出すか。** (推奨: プロパティ。
   将来 series の値としても使えるが、それは別途)
4. **4次元超の黙殺をやめる方向で良いか。** (推奨: 良い。訊くか拒否する)
5. **Browse の npz 展開はローカル先行で良いか。** (推奨: 良い)

## 4. 実装で答えたこと (v1)

`--verify-selftest` の V19/V19b/V19c が全部を押さえている。

1. **全部開く → picker。** ただし picker を出す条件は「画像メンバが2つ以上」
   **または**「frame 数と一致する 1 次元 key がある」。画像1つ + 軸候補ゼロなら
   ダイアログ無しで開く (今の使い勝手をそのまま維持)。軸候補があるときに picker を
   出すのは、**単位はユーザーしか決められない**から — 黙って開いたら軸を捨てるか
   単位を捏造するかの二択になる。画像メンバが**ゼロ**なら picker ではなく
   中身を並べたエラーを出す (Cancel しか押せないダイアログは何も答えていない)。
2. **1次元 key を軸として提案する。** picker で1本だけ選べる (名前と単位が1組
   しかないため)。値は `npyElem` が **double のまま**読む (画素経路の float を
   通さない: 12345.678901234567 が壊れる)。適用は Temporal の貼り付けと**同じ**
   `applyFrameAxisVals`。単位が空なら適用しない — 貼り付けと同じ規則で、
   ファイル由来だからといって緩めない。
3. **metadata はプロパティ (Inspector の Image 節)** に、開いた frame の隣。
   専用パネルは作らない。文字列 (`<U` / `|S`) は**読んで**出す。
4. **4次元超は拒否**。`decodeNpyBuffer` の共有経路で拒否するので `.npy` 単体でも
   同じ (黙って [0] を取る箇所はコードから消えた)。メッセージは shape を名指しする。
5. Browse の npz **展開**(メンバを行として並べる)は**未着手**のまま。ただし
   #111 以降、**ローカルの Browse からは `.npz` がダブルクリックで開く**
   (`viewerReadsName` が真 → `openPath` → `loadNpz`、メンバピッカーも従来どおり)。
   リモートは `peerServesName` が `.npy` のみで `serve.cpp` に npz が無い —
   **プロトコルは一切触っていない**。

### レビューで出た欠陥と対応 (V21d〜V21g で固定)

初版は敵対レビューで実欠陥が出た。全部直してある。

- **単位の trim が呼び出し側にしか無かった。** `" "` は貼り付け経路では拒否され
  npz 経路では通り、`x axis in  ` と描画された。trim を
  `applyFrameAxisVals` の中へ移動 — 規則は規則の在る場所で効かせる。
- **.npz を2つ同時に drop すると先の1つが黙って消えた。** `openPath` はループで
  呼ばれ、2つ目が1つ目の picker を上書きしていた。**待ち行列**にして、待つ側の
  ファイル名を言う。accept / Cancel のどちらでも次が出る。
- **長さ0の軸が画像になった。** `(8,8,0)` は W/H だけ範囲検査され C は無検査で
  `ch=0` の ImageDoc を作り、`(0,8,8,3)` は空の payload から H*W*C 個読んだ。
  F と C も範囲検査する。
- **1次元の要素数が桁溢れし得た。** ヘッダが宣言した次元の積が size_t を回り
  込むと 0 になり、バッファ検査を通って `reserve` が `length_error` を投げた。
  各次元・積・**zip ディレクトリの usize** に対して検査する。
- **全メンバが失敗しても空の batch が残った。** 何も開かなければ
  `pruneEmptyBatches()`。
- **走査が全メンバを完全展開していた。** ~128 バイトのヘッダを見るために
  数GB を UI スレッドで展開していた。`npzExtractPrefix` で 64 KiB だけ
  ストリーム展開する (`HAS_MORE_OUTPUT` は成功)。値が要るメンバ
  (metadata と軸候補) だけが全体を読む — **画像メンバは走査中に一切展開しない**。
- **文字列配列が要素0を配列そのものとして表示していた。** descr の item size で
  読みを区切り、`(5,)` なら `"..." (first of 5)` と言う。

### 副産物

`loadNpyBuffer` / `loadNpy` が作る in-file stack は、先頭 frame しか batch を
持っていなかった (2枚目以降が `addImage` を通らないため)。フォルダ経路
(`pumpSequence`) は既にやっていたことを、この2箇所にも入れた。
「1つの stack は1つの batch」が実際に成り立つようになった。
