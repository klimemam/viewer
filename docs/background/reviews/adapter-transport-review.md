## 1. 問い1 — 枠付き形式は妥当か

**妥当。骨格は残す。** 理由:

- **npz が流せない理由が構造的** (中央ディレクトリが末尾 = 全体を持ってから
  でないと読めない = 除きたいバッファそのもの)。これは形式の選び直しでは
  消えない。
- **ヘッダがセッション形式の規則を借りている** (1行1キー・値は行の残り・
  未知キーは読み飛ばし)。追加が互換になる性質を新発明せずに得ている。
- **版の規則がコンテナと同型**。レビュー時点は `VIEWERSTREAM 1`、setを載せた
  ときだけ2で、新しい版は読まずに断る規則だった。後続の#230 phase④では骨格を
  変えず、typed semantics適用能力を要求する安全世代v3を現writerが常に出す。
  現readerは既存v1/v2/v3を同じsemanticsで読む。
- **切断が黙らない**: ヘッダ途中なら "the stream stopped before its header
  ended"、blob 途中なら不足バイト数を言う (`loadViewerStream`)。
- **継ぎ目の選び方が正しい**: blob の前に合成 .npy ヘッダを書いて
  (`writeNpyHeaderFor`)、既存の `decodeNpyBuffer` を無傷で通す。復号器は
  スイートが最も濃く守っているコードで、そこに手術しなかったのは 518128f の
  一番良い判断。afc1977 の「木の構築は1つ、fetch だけ差し替え」(`vnzFetch`)
  も同じ筋で、層の規則のコピーが2つに割れていない。

### 1.1 ただし欠陥を3つ見つけた (レビューの成果物)

**(F1) 改行で枠が壊れる — ヘッダ注入。**
`stream_out` は `name` / `note` / `timestamps_name` / `unit` を**無害化せずに**
1行に書く (`run_adapter.py` の `_stream_line` 呼び出し群)。リーダが
`note="line1\nline2"` を返すと、`\n` 以降が**別のヘッダ行として解釈される**。
未知キーなら黙って読み飛ばされ (note が**黙って切れる** — この repo が最も
嫌う失敗)、`pixels` や `layer` に見える行なら枠そのものが狂う。
**npz 側は免疫がある** (文字列は npy メンバとして運ばれる) ので、
「2つの運び屋が同じことを言う」原則が現に破れている。
直し方は §6 の段 A2 (最小エスケープを凍結仕様に入れる)。

**(F2) 運び屋間で検査が非対称 — 破損キャッシュで境界外読み。**
npz の門は構築前に木を検査する (`loader_npz.inc:1384-1452`: 親は自分より
前・layer 語彙・batch は入れ子にならない・series の conditions 長)。
**stream の門はこの塊を通らない** — `parent` は `atoi` の値のまま
(`loader_npz.inc:1275`)、上限検査が無い。そのまま
`vnzCheckSets` (`:1126` — `parent >= 0` しか見ずに `nodes[parent]` を引く) と
`vnzBuild` (`:1974`) に届くので、**壊れた .vstream キャッシュ 1行
(`parent 1 999999`) が境界外読みになる**。.vstream はディスクに永続する
(再起動をまたぐキャッシュ) 以上、切断・破損は起きる前提で読むべき入力。
直し方は §6 の段 A3 (`vnzCheckTree` を1つ作って両門から呼ぶ —
afc1977 が fetch でやったことの、検査側の残り半分)。

**(F3) ワイヤのバイト順が暗黙。**
harness は配列を native endian に正規化し (`to_numpy` の
`newbyteorder("=")`)、viewer は合成ヘッダに常に `<` を書く
(`writeNpyHeaderFor`)。LE 機しか無い今日は一致するが、**仕様として
「ワイヤは little-endian」とどこにも書かれていない**。凍結時に書き、
harness 側を `=` でなく `<` に1行直す (段 A4)。ついでに
`run_adapter.py:571` の `.replace("f8","f8")` は無為なので掃除。

### 1.2 仕様が実装にしか無い状態の畳み方 — 書き出して凍結する

**両方やる。片方では足りない。**

- **書き出す**: `input-adapters.md` に **§4.11.2「枠付きストリーム
  (transport)」** を新設し、キー表 (`VIEWERSTREAM` / `n` / `layer` / `parent` /
  `role` / `refs` / `name` / `note` / `layout` / `cfa` / `range` /
  `timestamps*` / `conditions*` / `meta` / `pixels` / `end`)、blob は
  `pixels` 行の宣言順に生バイト、dtype トークンは viewer の読む9つ
  (`u1 i1 b1 u2 i2 u4 i4 f4 f8`)、UTF-8 / LF / little-endian、未知キー
  読み飛ばしの規則、版の規則 (追加は互換・意味の変更は版上げ・set を
  載せたときだけ 2) を明文化する。
- **凍結する**: この形式は**既に load-bearing** である —— .vstream キャッシュが
  再起動をまたいで残り、次の viewer がそれを読む。「実装がリファレンス」の
  ままでは、悪気のない実装変更が昨日のキャッシュを黙って壊せる。
  凍結の意味は npz コンテナの規則 (§4.11.1 の 1 と 5) と同一でよい。

**同時に §4.11 の誤記を正す。** 現行 §4.11 は「**.npz への書き出し**」
「npz を運び屋にするのは、viewer が既に読める形式だから」と書くが、
518128f 以降 **npz はリーダ経路のどこも通らない**。正しい整理は:

| | 形式 | 役割 | 状態 |
|---|---|---|---|
| **運搬 + キャッシュ** | 枠付きストリーム (.vstream) | harness→viewer の払い出し、adapter-cache | 実装済・本レビューで凍結 |
| **静止した容器** | viewer npz (`__viewer`) | ファイルとして持ち歩く/開く形式 (§4.11.1) | 読み手は済、書き手 (Save as viewer npz) は未 (§4.11.1 表の 3) |

§4.11.1 は**そのまま生きている** (npz コンテナは容器形式として正しい)。
死んだのは「npz が運搬もする」という一文だけ。**.vstream を第2のファイル
形式にはしない** (ドラッグして開ける等の口は作らない) — 1つの問いに
ファイル形式が2つ答えると、それ自体が #148 の「2つの答え」を形式の層で
作ることになる。持ち歩く形が要るなら §4.11.1 の書き手を書くのが正道。

## 2. 問い2 — 段階の切り方。パイプの段は消す

### 2.1 元の段階表と、その検死

元の表 (755 MB 外挿): npz 約1.1 s → 枠付きファイル 約0.6 s →
パイプ 約0.23 s → 共有メモリ 約0.04 s。

- **npz → 枠付きファイル: 実測で完了。** 151 MB 実測 0.421→0.268 s
  (1.57倍、Python 起動を除き約2.3倍)。この段は済み、数字も生きている。
- **パイプ 0.23 s: 死んだ。** 上記のとおり同一コミットの実測が
  0.441 s (パイプ) 対 0.296 s (ファイル) で逆転。
- **共有メモリ 0.04 s: 数字の出自が別の経路のものだった。** 0.04 という桁は
  「**フレームが既に区画に居る**」ときの呼び出し往復 (0.04 ms) か、区画への
  書き込み (0.051 ms/MB × 755 ≈ 39 ms) の外挿。だがリーダの向きでは
  Python が 755 MB を**作って書き**、viewer が **f32 へ変換**する
  (0.165 ms/MB ≈ 125 ms) のが残る。つまり**旧表の最終段はアナライザ
  (#45) の数字であって、リーダ (#44) の数字ではない**。方向が逆である
  ことが、段階表の中にまで混入していた — これがこの合同レビューの
  一番の発見である。

### 2.2 パイプの段は「保留」ではなく「削除」する。理由は3つ

1. **実測で負けた** (0.441 対 0.296、この機械、viewer と同じ書き方)。
2. **「読みながら消費しないと詰まる」は事実で、しかも高くつく。**
   `adapter.cpp` の注釈 (:104-107) が既に言っているとおり、パイプは
   バッファ (Windows 既定 数KB〜64KB 級) を超える払い出しで、消費側が
   同時に読まない限り**永久にデッドロックする**。つまりパイプ段は
   「fetch の差し替え」では済まず、排水スレッド + 逐次パース +
   途中失敗の意味論 (何ノードまで着地した状態で切れたか) を新設する
   仕事である。afc1977 が作った継ぎ目は fetch が**同期で完結する**ことを
   前提にしており、その単純さは価値そのもの。
3. **キャッシュがファイルを要求する。** .vstream キャッシュ (再起動を
   またぐ、§7 段5) は**まさにこのバイト列のファイル**である。パイプ化しても
   キャッシュのためにディスクへ tee することになり、消したはずの書きが
   戻ってくる。今の実装は「キャッシュ書き = 運搬」が**同じ1回の書き**で、
   これはパイプ化すると失われる性質である。

**再訪条件** (これを満たす測定が出たら段を再興してよい):
対象データでの**初回オープン**のプロファイルで、ファイル書き+読み戻しが
壁時計の 30% 以上を占め、**かつ**逐次消費 (Python が書いている間に viewer が
先頭 stack を着地させる) の試作が tee 込みで実測 1.3 倍以上勝つこと。
518128f 自身が「この段は測定で自分で稼げ」と書いており、その言葉どおり。

## 3. 問い3 — 共有メモリまで行く価値があるか。数字で答える

**経路で答えが分かれる。リーダ (#44) には無い。アナライザ (#45) にはある。**

### 3.1 リーダ (#44): 行かない。数字:

ファイル往復 ≈ 0.78 ms/MB (48 MB 実測 37.3 ms) に対し、区画書き
0.051 ms/MB + 区画→`FrameSource::data` のコピー ≈ 0.165 ms/MB。
差 ≈ **0.56 ms/MB** = **151 MB で ≈ 0.08 s、755 MB で ≈ 0.42 s (外挿)**。
それが効くのは:

- **初回オープンだけ。** 2回目以降はキャッシュが Python ごと消す (V25i)。
  そしてキャッシュはファイルなので、共有メモリ化しても**キャッシュへの
  書きは残る** (非同期に逃がせるが、消えはしない)。
- **Python 起動 0.12-0.19 s がその上に乗ったまま。** 起動を消せるのは
  常駐ワーカだけで、区画ではない。
- issue の「端から端までコピー0」は、`FrameSource::data`
  (`std::vector<float>`) を**マッピング裏付けのバッファに変える手術**が
  前提になる。それは「運び屋の差し替え」ではなく doc の画素の持ち方の
  変更で、レジストリ共有・reload・remote 全部に触る。0.42 s のために
  払う代償ではない。

**決定: #44 は枠付きファイル渡しで確定。共有メモリ段は作らない。**
**再訪条件**: #45 の W2 (区画モジュール) が main に入ったら、**リーダを
常駐ワーカ経由で走らせる**形を再測する。そのときの利得は区画の 0.4 s
ではなく**起動の 0.12-0.19 s + torch リーダなら 1.2-1.4 s** で、
桁が違う。つまりリーダにとっても、価値があるのは区画ではなく**ワーカ**。

### 3.2 アナライザ (#45): 行く。数字:

- 呼び出し1回の床: 毎回起動 **120-190 ms** 対 常駐+区画 **0.03-0.04 ms**
  (実測、48 MB フレーム既置)。約 **4700 分の1**。
- 呼ばれ方が違う: リーダは1ファイル1回、アナライザは **ROI ジェスチャ毎・
  フレーム毎**。最も安い C アナライザ (`noise/floor` 256² = 0.11 ms) より
  往復が安い、が成立条件。
- torch は import だけで **1.2-1.4 s** (実測)。毎回起動では構造的に不成立。
  ユーザーの要望に torch が入っている以上、常駐は前提。
- フレーム書き込みは **2.5-3.0 ms / 48 MB、フレームが変わったとき1回**
  (`dataRev` キャッシュ)。ROI ドラッグ中は 0 回。

### 3.3 ただし、入れる前に払う設計2つ (これが無いと入れられない、の答え)

#### (a) ハングの始末 — ワーカ監督器 (W1)

- **契約**: 全呼び出しは id 付き要求/応答。**期限は呼び出し毎**
  (既定 30 s — study §9-6 の推奨どおり。リーダの 300 s とは別の定数)。
- **期限超過**: 画面に「applied analyzer did not answer within 30 s」+
  経過表示 + キャンセル可。kill はプロセスツリーごと
  (`TerminateProcess` / `SIGKILL` — `adapter::run` の sliced wait と
  同じ道具)。**次の呼び出しが lazy に再起動** (実測 118 ms。torch 持ちは
  1.2-1.4 s 再徴収 — メッセージがそれを言う)。
- **例外はハングではない**: 実測で例外は**データとして返り、ワーカは
  生存**する (study §2.3)。kill が要るのは無応答だけ。
- **排水の規律**: 制御路 (stdin/stdout) は行ベースの小メッセージのみ、
  応答読みは専用スレッド。stderr は adapter と同じ**ファイル**へ
  (tail 可能、デッドロック不能 — `adapter.cpp` の規則を踏襲)。
  §2.2 の「詰まる」問題は、**大きい払い出しをパイプに載せない**ことで
  構造的に回避する — 画素は区画、パイプは制御だけ。

#### (b) 落ちたときの後片付け — 区画の単独所有 + 名前を残さない (W2)

- **単独所有の規則: 区画を作る・数える・消すのは常に viewer。** ワーカは
  attach するだけ。これで「ワーカが落ちた」場合は viewer がハンドルを
  閉じて終わり (両方向とも)。残るのは「viewer が落ちた」場合だけ。
- **Windows**: `CreateFileMapping` のセクションはカーネルが参照カウントする。
  全ハンドルが消えれば (両プロセス死亡を含め) セクションも消える。
  **リークは構造的に起きない。** 反論の「後片付け」は Windows では
  ほぼ空集合である — これは反論が弱いのではなく、実装対象の主戦場
  (この repo の実測は全部 Win) で費用が低いという朗報。
- **POSIX**: `shm_open` は名前が `/dev/shm` に残り得る。**attach 完了の
  ack を受けた瞬間に host が `shm_unlink` する** (fd/マッピングは生きた
  まま、名前だけ即座に消える — 標準の unlink-after-attach パターン)。
  ack が期限内に来なければ unlink して作り直し。これで「クラッシュが
  名前を残す」窓は attach ハンドシェイクの数 ms だけになり、保険として
  起動時に自 PID 系列の死骸名を掃く。
- **予算**: 区画バイトは `claimedImageBytes()` に計上する (study 反論2(b))。
  予算の外で RAM が育つ状態を作らない。fail-first の試験対象 (§6 W2)。

## 4. 問い4 — #45 は #44 の機構を再利用できるか。共通部の正確な棚卸し

「共通なのは常駐ワーカと区画の管理だけ」は**方向としては正しいが、
少なく数えすぎている**。正確には:

**共通 (1回だけ作る。置き場所も提案する):**

| 部品 | 中身 | 置き場所 (案) |
|---|---|---|
| プロセス監督 | spawn / probe / 期限 / kill / 再起動 / どこで動いたかの記録 | `core/pyworker.{h,cpp}` (adapter.cpp と同じく viewer 状態フリー) |
| 区画管理 | 作成 / attach / unlink規律 / 予算計上 / 掃除 | `core/shmseg.{h,cpp}` |
| 制御路の枠 | 行ベース1キー1行 + 未知キー読み飛ばし — **枠付きストリームのヘッダ規則そのもの**を制御メッセージに再利用 | 仕様は §1.2 の凍結文書 |
| Python 環境 | `findPython` / 信頼 (明示選択のみ) / エディタ起動 / 置き場所の登録 (§4.13.2) | 既存 (adapter.cpp / prefs) |
| provenance 語彙 | 名前 / VERSION / 内容ハッシュ / python・numpy・torch 版 / 実行場所 | 既存の出所行に列を足す |

**共通でない (共有しようとすると歪む):**

| | リーダ (#44) | アナライザ (#45) |
|---|---|---|
| 向き | Python が作った画素を viewer に **materialise** | viewer が持つ画素を Python に**見せる** |
| データ面の契約 | **一回きりの木の払い出し** (層・軸・set 検査つき、`vnzBuild`) | **pull 窓** (`psStack` §9.2: get/release、区画は stack 全体でなく窓) |
| 呼ばれ方 | 1ファイル1回 | ジェスチャ毎・フレーム毎 |
| キャッシュ | .vstream (静止、再起動をまたぐ) | 無し (`dataRev` で区画を書き直すだけ) |
| 期限 | 300 s (データ量に比例) | 30 s (対話) |
| 結果 | doc / series / set | number / curve / (map は #49 撤回済) |

区画の**書き手**も逆になる (リーダ: ワーカが書く / アナライザ: viewer が
書く) が、**所有者は常に viewer** (§3.3(b)) なので管理コードは同じ1つ。

**順序の帰結**: 方向が逆で用途が独立、はそのとおり。ただし §3.1 の結論に
より、**リーダ側の次の一歩 (ワーカ経由化) は #45 の W1/W2 の後**に来る。
「リーダを先に作ってよい」は枠付きストリームについて既に果たされ、
ここから先の共通部は #45 が先に敷く。

## 5. 問い5 — peer の配備問題。パリティが「2つの numpy の ULP 一致」に劣化する件

**まず問題を2つに割る。向きが逆なので、劣化の仕方も逆である。**

### 5.1 リーダの peer 実行 (§4.13.1、段7 未実装)

**「1つのファイルが端によって2つの答えを返さない」(#148) は、構造で
ほぼ満たせる。** リーダは**ファイルが居る側で走り**、materialise された
画素はその側に留まる (TILE と MEASURE だけが流れる — §4.13.1 の決定)。
つまり1つのファイルは**1つの場所で1回だけ読まれ**、比べるべき
「もう一方の答え」がそもそも生成されない。ULP 一致を測る必要がない。

例外は**同じバイト列が両端から見える**場合 (NAS を両側でマウント)。
このとき local 読みと peer 読みで numpy 版が違えば画素が ULP で違い得る。
ここは保証ではなく**申告**で守る: リーダ実行の provenance に
python / numpy (/torch) の版と リーダの VERSION・内容ハッシュを刻む。
違いが出たとき、それが**黙っていない**ことが #148 の規則の実体である
(#148 自身も f16 を wire に足したのであって、全数値の同一性を証明した
のではない — 規則は「静かに違うことの禁止」)。

### 5.2 アナライザの peer 実行 (#45 の W6、abi-v3 §10 の延長)

こちらが本丸。C プラグインは「同じ .so を viewer が配る」= バイト同一で、
Python は「送った .py を peer の numpy が走らせる」= **バイト同一が版一致に
格下げされる**。study の反論1は正しく、**ULP 一致は約束できないし、
測って回ることもできない**。

答えは abi-v3 §10 が C に対して既にやった手の拡張 — **実測パリティを
宣言パリティに置き換える**:

1. **走らせる前に照合する組を広げる**: name + VERSION + 内容ハッシュ +
   **python / numpy / torch の版**。1つでも違えば**両方の値を並べて理由つき
   拒否** — 黙って local に振り替えない、黙って古い方で計算しない
   (§10 の文言そのまま)。
2. **逃げ道は明示**: 「手元で走らせる (フレームが回線を流れます)」を
   選ばせる (`--remote-policy local-fetch` の既存の線)。
3. **provenance が常に実行場所と版の組を刻む** (study §9-9)。数字を後から
   疑えることが、測れない一致の代替である。
4. **selftest は張れる範囲だけ張る**: 同一マシンで worker を2つ立てて
   一致を assert する試験は書ける (環境が1つなので常に緑 = 配線の検査)。
   異版 numpy の不一致検出は CI では作れない — **作れないものを作れると
   書かない**。

これで反論1は「解消」ではなく「**封じ込め**」になる。それが正直な着地で、
study 自身の言葉 (「黙って違う数字を出すことだけは絶対にさせない」) とも
一致する。

## 7. 決定record

1. **枠付きストリームは妥当、当時のgenerationはv2として凍結して文書化する**
   (§1)。欠陥3つ (改行注入 / 検査非対称 / endian 暗黙) は A2-A4 で塞ぐ。
   **後続裁定 (#230 phase④):** 枠・既存fieldの意味は変えず、安全gateとして
   writer generation v3を追加。新writerは常に3、new readerはv1/v2/v3を読む。
2. **npz は運搬から容器へ役割を狭めたと記述を正す** (§1.2)。.vstream は
   内部形式で、ユーザーの持ち歩く形は viewer npz (§4.11.1、書き手は未)。
3. **パイプ段は削除** (§2.2)。根拠: 実測逆転 0.441/0.296 s + 排水機構の
   新設費 + キャッシュがファイルを要求。再訪条件を明記。
4. **リーダの共有メモリは作らない** (§3.1)。0.08 s/151 MB・初回のみ、は
   `FrameSource::data` の手術に見合わない。再訪 = W2 着地後の
   ワーカ経由再測 (利得の主体は起動 0.12-0.19 s / torch 1.2-1.4 s)。
5. **アナライザの常駐ワーカ + 共有メモリは進める** (§3.2)。ただし
   W1 (ハング始末)・W2 (後片付け + 予算) が**画素より先** — 反論2件は
   段の順序で払う。区画は viewer 単独所有 + unlink-after-attach。
6. **共通部の棚卸し** (§4): ワーカ監督・区画・制御路の枠・Python 環境・
   provenance 語彙の5つを1回だけ作る。データ面 (木の払い出し / pull 窓)
   は共有しない。
7. **peer パリティは宣言パリティ** (§5): name + VERSION + ハッシュ +
   ランタイム版の等値ゲート、不一致は両版併記の拒否 + 明示の逃げ道。
   ULP 一致は約束しない (できない約束を書かない)。リーダ側は「ファイルの
   居る側で1回だけ読む」構造で #148 を満たす。
