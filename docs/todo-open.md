## 0. 【最優先】stack から stack を作る — 「別の stack と同じファイル名だけ抽出」

ユーザー要望 (2026-07-30): 「あるスタックから，別のスタックと同じファイル名だけ抽出して
Stackを作り直す，という機能があったら，A,B比較とか色々やれること増えそう．Stackの整理？
Stackの再＊＊？的な．抽出要件は色々ありそうなので，Dialogueメニューでいい気がするが．」
**着手順の指示: これを Fable TODO の先頭でやること。**

### なぜ効くか

A/B のフレーム追従 (`compareFollowFrame`) は **B の stack に A と同じフレーム番号が
あること**を前提にしている。無ければ `g_abFollowDiverged` が立ち、比較は
「A と B と1フレーム分の時間ノイズの差」になる (項目21 参照)。
撮り直しや欠損で**メンバが揃っていない 2 つの stack** は現場に普通にあり、
今はそれを揃える手段が無い。揃えられれば比較・σ_t・per-frame 表がそのまま効く。

### 先に決めないと進めない構造上の制約 (コードで確認済み)

**`ImageDoc::seqId` は int が1つ** (main.cpp:165)。
つまり **1 フレームは 1 つの stack にしか属せない**。「抽出」の意味は2択:

1. **移す** — 元の stack からフレームが**抜ける**。元が壊れる。破壊的。
2. **読み直す** — 同じファイルを別の `ImageDoc` として開く。元は無傷だが
   **メモリが 2 倍**になり、リモートなら**転送も 2 回**。

どちらにするか(あるいは選べるようにするか)が**この機能の設計の中心**。
「参照だけ増やす」は現在のデータモデルでは**できない**ので、そこを期待しないこと。
(できるようにするなら `seqId` を集合にする話になり、σ_t やセッション保存まで
波及する。それは別案件。)

### 抽出の規則 (ダイアログで選ばせる)

ユーザーの言うとおり要件は複数ある。最低限:

- **同名のみ** — 相手 stack のファイル名(basename)と一致するものだけ
- **同フレーム番号のみ** — `seqIndex` が相手にもある番号だけ
- **共通部分 / 差分** — 相手にあるもの / 相手に無いもの (両方いる)
- **番号範囲** — `10..30` のような指定
- **手で選ぶ** — チェックボックス一覧 (最後の逃げ道として必ず用意する)

相手 stack を選ぶ UI が要る。**A/B が設定済みなら既定で相手 = B** が素直。

### 外してはいけない約束

- **両方向で数を言う。** 「24 中 18 が一致、相手の 3 個はこちらに無い」。
  片方向だけだと「揃った」と誤解する。正典の「黙って捨てない」。
- **元 stack を勝手に壊さない。** 破壊的な方を選ぶなら、実行前に何が抜けるか
  を出す。
- **派生した stack は名前で素性を名乗る。** 「どこから、どの規則で」が名前か
  note に残ること。montage で使った形 (`ROI ... (montage H)`) が前例。
- **series の値は自動で継がない。** 派生 stack は別の測定対象。正典どおり
  series メンバシップは明示 (`Series::members` が唯一の真実)。
- **batch はどうするか決める。** 既定は元と同じ batch が素直だが、
  「整理」目的なら新しい batch に出したいこともある。ダイアログで選ばせる。
- **部分ロードの扱い。** 元 stack が n/N のとき、常駐フレームだけで照合するのか、
  ファイル一覧で照合するのか。**リモートは後者でないと役に立たない。**

### 名前 (正典の語彙に合わせる)

`docs/terminology.md` の層は frame ⊂ stack ⊂ series ⊂ batch。
既存の操作語は Close / ungroup / Move to batch / rename。
新しいのは「**既存の stack から部分集合の stack を作る**」操作なので、
`Derive stack...` / `Filter stack...` / `Rebuild stack...` あたり。
**項目5 (sequence と stack の用語混在) と同時に決めること** — ここで
新しい語を増やすと、混在をもう1つ作ることになる。

### 検証

`--verify-selftest` か新規 selftest で、合成した 2 つの stack (片方に欠番) から:
一致数・不一致数が両方向とも正しいこと、派生 stack のフレーム順が
`seqIndex` 昇順であること、元 stack が(非破壊モードで)無傷であること、
そして**派生後に A/B の follow-frame が発散しなくなること** — 最後のが
この機能の存在理由なので、必ず assert する。

- 原因は **release イベントが食われる (eaten release)**。`_NET_WM_MOVERESIZE` を投げると

### 修正の方向 (上の観測から確定的に言えること)
`_NET_WM_MOVERESIZE` を送った直後に、**アプリ側のドラッグ状態を自分で降ろす**

WM にグラブを渡した時点でそのドラッグはアプリのものではなくなるので、
「release を待つ」設計自体が誤り。

### 不変条件 (これは死守)

## 3. A と B のサイズが違うと画面全体 Fit になる (ユーザー報告 2026-07-29 夜)

ユーザー報告 (逐語): 「A, Bが異なるサイズの時に画面全体Fitになってしまう．」

### 構造 (調査済み — ここから始めれば早い)

**ビューは1つしかない。** `app.view` (zoom + center) を A と B が共有していて、
`mapIn`/`unmapIn` (main.cpp ~7563) はどちらのペインでも同じ `app.view` を使う。
これは意図的で、コメントもそう言っている:

    // "fit" must fit the pane the image is drawn in, not the whole canvas. A is
    // the reference, so fit A's pane; B is the same view by construction.
    ImVec2 fitSize = split ? ImVec2(paneAsz.x, canvasSize.y) : canvasSize;
    if (im && app.fitRequested) { fitToCanvas(fitSize); app.fitRequested = false; }

`fitToCanvas` (~7480) は `cur()` = **A の寸法だけ**で zoom を決める:

    app.view.zoom = std::min(canvasSize.x / im->w, canvasSize.y / im->h) * 0.97f;
    app.view.center = ImVec2(im->w * 0.5f, im->h * 0.5f);

`fitRequested` を立てる場所: 2140 / 2252 (画像を閉じたとき) / 2700
(`images.size()==1 || fitOnSwitch`) / 3352 / 3400 / 7035 / 13587 / 13643
(stack 切替時の `fitOnSwitch`)。**B を設定した経路がどれかを踏んでいないか**を
まず確認すること。

### ここは設計判断が要る (だから Fable 案件)

サイズが違う2枚に「同じビュー」を課すと、fit は本質的に定義できない
(A に合わせれば B がはみ出す/縮む)。取れる道は3つ:

1. **共有ビューのまま、大きいほうに fit** — 両方必ず画面内。ただし A が小さいと
   A が小さく表示される。
2. **共有ビューのまま A に fit** (現状の建前) — B のはみ出しを許容し、はみ出して
   いることを画面で言う。
3. **ペインごとに独立 fit** — 見た目は一番きれいだが、**画質評価では罠**。
   異なる倍率で並べた2枚の解像感・ノイズ感を比べると誤った結論に直行する。
   やるなら「倍率が違う」ことを両ペインに常時明示しないと危険。

**推奨は 1 か 2。** 3 を選ぶ場合はラベル必須。どれを選ぶにせよ、
**倍率が共有されているのか否かは画面から常に読めること** が要件。
(既に `b->w != im->w` のときは Compare 設定に "size differs: B is %dx%d" と
橙で出している — main.cpp ~8805。表示の置き場所としてはこの近くが自然。)

### 回帰テスト

`--abstats-selftest` に、サイズの違う2枚を A/B にして
「fit 後に A も B も可視で、zoom が共有されている(または共有されていないと
明示されている)」を assert する check を足す。fixture はサイズ違いが要るので
`tools/gen_testdata.py` に1つ足すことになるはず。

## 5. `sequence` と `stack` が混在している — 用語を定義しなおす

ユーザー指摘 (2026-07-29): 「sequencesとstackという言葉が混在している．terminologyを
改めて定義しなおしましょう．」

正典 (`docs/terminology.md`) は **stack** を層の名前として定義している
(`frame ⊂ stack ⊂ series ⊂ batch`)。にもかかわらず UI は今も `sequence` と言う。
**同じ物を2つの名前で呼んでいる**のが今の状態。

### 実測した混在 (UI 文字列)

    "Select sequences"            "Load sequence"        "Load sequence?"
    "Sequence loading"            "which sequences do you want?"
    "%d sequence(s), %d files"    "selected: %d sequence(s), %d files"
    "Open folder (all sequences below it)"   "Open the whole sequence (%u frames)"
    "each checked sequence becomes its own stack"      ← 1文に両方
    "folder: loads every numbered sequence below it, one stack per group"  ← 同上
    "step the previewed sequence"  "loading sequence: "  "frame number (index in sequence)"
    "needs a stack: load a numbered sequence first"    ← 同上

最後の3つが症状を一番よく表している: **1つの文の中で両方使っている。**

### まず決めるべきこと (これが設計判断で、だから Fable)

`sequence` は消すべき同義語なのか、それとも**別の物を指しているのか**。
後者に見える根拠がある:

- **ディスク上の連番ファイル群** (`frame_000.npy … frame_023.npy`) と、
- **読み込まれて時間軸を持つ計測対象** (`SeqInfo`、σ_t が意味を持つ単位)

は同じものではない。前者はまだ何も開いていない状態でも存在する
(ブラウザのグループ行、picker の候補)。正典が名前を与えているのは後者 = **stack**。

**推奨**: ディスク側は「連番ファイル (numbered files)」と呼び、`sequence` という
語を UI から**引退**させる。読み込まれた物は常に **stack**。
"each checked sequence becomes its own stack" は
"each checked group of numbered files becomes its own stack" になる。
ただし最終判断はユーザーに確認すること — 日本語の画面表記も併せて決める。

### 触ってよい範囲と、触ってはいけない範囲

**互換性のある表面** — 変えると既存のセッション/スクリプトが壊れる。改名しない
(するなら読み込み側で旧キーも受ける移行が要る):

- セッションのキー: `seqload` `seqname` `seqframe` `seqlevel`
- CLI: `--sequence ask|always|never`
- selftest 名 (`--lin-selftest` 等の内部名は自由だが、既存スクリプトが叩いている)

**自由に変えてよい**: UI 文字列、`docs/*.md`、トースト、ログ。

**コード識別子** (`SeqInfo` `seqId` `seqQueue` `seqLoadingId` … 約40個) は
機械的な一括改名になるので**別コミット**にすること。混ぜると意味のある変更が
レビューで埋もれる。急ぎではない — 画面の言葉が先。

### 成果物

1. `docs/terminology.md` に「`sequence` は使わない。ディスク上の連番ファイル群は
   〜、読み込まれた物は stack」と**明記**する (今は stack の定義はあるが、
   `sequence` を禁じる記述がない。だから混ざった)。
2. UI 文字列の置換。
3. 回帰: 文字列を assert しているテスト (`--browse-selftest` の row 文言など) の追随。

## 8. zoom % は Image View の中にあるべき

ユーザー指摘 (2026-07-29): 「zoom ?%の表示はImage Viewに会った方が良い気が．
デザイン的なむずかしさがあるのでこれもFable TODOでも．」

現状 zoom は**ステータスバー**に出ている (main.cpp ~20418)。画面の一番下、
Image View から目を離した先。拡大率は**今見ている画素の性質**なので、
画素の隣にあるべき、という指摘。

デザイン上の難しさ (ユーザー自身が挙げている):

- Image View には既に下辺に2行のフッター (バッチ / ファイル名 + スクラブバー +
  フレーム番号) があり、上辺には何も置きたくない (画素を隠す)。
- A/B 分割時はペインが2つあるが、ビューは共有なので zoom は1つ。どちらのペインに

- ステータスバーから**消す**のか、両方に出すのか。両方は重複だが、

判断してから実装すること。ついでに: 現状の表示は `%.0f%%` と `%.3g%%` の

## 9. Histogram の bin は整数 / 2のべき乗で切る

ユーザー指摘 (2026-07-29): 「HistgramのBinだけど基本的には整数もしくは2のべき乗
Floatでbin切りたいなぁ．」

### なぜ効くか

今は **256 bin を [black, white] に等分**しているだけ (main.cpp ~8270,
`inv = 256.0f / (H.white - H.black)`)。レンジが 256 の整数倍でないと、
bin 幅が半端になる (例: 64..1023 なら 3.746 DN/bin)。整数センサ値をその幅で
刻むと、**ある bin には 4 個の DN 値が、隣の bin には 3 個が入る**。
結果として実在しない周期構造 = 櫛状のアーティファクトが出る。
ノイズ分布の形を読む用途では致命的で、ユーザーの指摘はここを突いている。

### 実装の勘所 (調べた結果)

**snap する場所は1箇所でよい**: `recomputeHistogramIfNeeded` の頭で
`wantBlack`/`wantWhite` を求めた直後 (~8241)。ここで丸めれば、キャッシュキー・
ビニング・x軸ラベル・A/B の bin 共有が**全部同じ値を見る**ので追随する。
**キャッシュ比較 (`H.black == wantBlack`, ~8254) より前**に丸めること —
後で丸めると毎フレーム キャッシュミスして再スキャンする。

規則:
- 整数 dtype (u8/u16/i16/u32...): `w = ceil((white-black)/256)` を整数に切り上げ、
  最低 1。origin は `floor(black/w)*w`。u12 の 0..4095 なら w=16 でちょうど、
  0..255 なら w=1 でちょうど 1 DN/bin になる。
- float: `w = 2^ceil(log2((white-black)/256))`。origin は `floor(black/w)*w`。
  bin 端が2進で厳密に表現でき、再ビニングで誤差が積まれない。
- 丸めたレンジは元のレンジを**必ず含む**(外側に広げる)。

### 見落としやすい罠 (これを踏むと測定値が変わる)

**クリップ数を bin レンジで数えてはいけない。** 今は `t < 0` / `t >= 256`
(= bin の外) で `below`/`above` を数えている (~8283)。bin レンジを外側に広げると
**飽和画素の数が減って見える**。`clipLo`/`clipHi` は「表示レンジ = ユーザーが
見ている白飛び/黒潰れ」の話なので、**元の black/white と比較して数える**ように
分離すること。bin の外か否かとは別の量。

x 軸ラベルにも、丸めた実効レンジと bin 幅 (DN/bin) を出すこと
(グラフは常に量と単位を言う、という既存の規則)。

### 検証

`--abstats-selftest` か新しい単体テストで:
- u16 の 0..4095 → bin 幅がちょうど 16 DN、櫛が出ない (各 bin の DN 個数が均一)
- 0..255 → 1 DN/bin
- float の任意レンジ → bin 幅が 2 のべき乗
- **飽和画素の数が、bin レンジを広げても変わらない**(上の罠)

## 10. セッション復元で remote (ssh) が戻らない

ユーザー指摘 (2026-07-29): 「restore sessionで，remote sshが復元されない．」

### 原因は確認済み — セッションは remote browse の状態を1行も書いていない

`writeSessionTo` (main.cpp ~3421-3658) に `rb*` / `remote*` の書き出しは
**0 行**。ホスト・ポート・現在のディレクトリはどこにも保存されていない。

保存されているのは **prefs のほう** (`savePrefs`, ~3731):
`rbflat` / `rbadv` / `rbtree` (表示の形)、`remoteexe`、
`remoteurl` (= `app.lastRemoteUrl`、ただし **Start Remote ダイアログの
入力欄の初期値としてしか使われていない** — ~14522)、`rbookmark` / `rbrecent`。

つまり「次に開くときダイアログに前回のホストが入っている」までは実装済みで、
**セッションを開いたら勝手に繋ぎ直す**は未実装。画像のパスは
`ssh://host/path` 形式で保存されているので、**フレームは復元されるのに
ブラウザだけ空**という今の状態になる。

### 設計判断 (だから Fable)

1. **勝手に繋ぐのか、聞くのか。** ssh 接続は数秒かかり、鍵のパスフレーズや
   VPN 未接続で失敗しうる。セッションを開くたびに固まるのは避けたい。
   案: 復元はするが**遅延接続** — Browse パネルに「trc2:/data (click to
   reconnect)」を出しておき、押した時に繋ぐ。`docs/browse-as-file-manager.md`
   の「場所 (place)」設計と素直に噛み合う (復元された場所が1つ増えるだけ)。
2. **何を保存するか。** host / port / dir。`placeUrl()` が既に
   「このホストのこのディレクトリ」の正準 url を作るので、**1行 `rbplace <url>`
   で足りる** (ポートも含む — `makeRemoteUrl` はポートを落とさない)。
3. **失敗の見せ方。** 復元時に繋がらないのは平常運転。エラーはその場所の
   行にインラインで出す (グローバルなエラー枠ではなく)。これも
   browse-as-file-manager.md と同じ方針。

### 注意

- セッション形式は**キーを増やすだけ**なら後方互換 (未知キーは読み飛ばす)。
  古いビューアで開いても壊れない。
- 画像側の復元と**順序を競合させない**こと。`seqRestore` の隊列と
  `rbOpenQueue` は別物で、ブラウザの復元はどちらにも入れてはいけない
  (ブラウザは「見ている場所」であって、開いているデータではない)。

## 11. Inspector の remote 行が出たり消えたりして、下の行が動く

ユーザー指摘 (2026-07-29): 「inspectorで，remoteだと，remote host名 サイズ，という
一行がでたり消えたりして行が変わるのが非常にわずらわしい．」

### 原因は特定済み — note を持つフレームと持たないフレームが1つの stack に混在する

その行は `ImageDoc::note` (Inspector の Image 節、main.cpp ~8902
`if (!im->note.empty()) ImGui::TextWrapped(...)`)。

`openRemote` は開いた doc に **note を書く** (~7007):

    doc->note = "remote " + host + "  -  " + w + "x" + h + (frames>1 ? " N frames" : "");

ところが **stack の兄弟フレームは rfWorker 経由で作られ、note を書いていない**
(~1714-1726 に `doc->note = ...` が無い)。つまり同じリモート stack の中で、
先頭フレームだけ note を持ち、他は空。**フレームを送るたびに行が現れて消える**。
Image 節はその下に Interpret コンボなどの**操作**が続くので、押そうとした物が
動く — 今日3回直したのと同じ欠陥族。

### 直し方

1. **note は frame ではなく source の性質**。リモート stack の全フレームが同じ
   文言を持つようにする (rfWorker 側でも同じ note を書く)、または Inspector 側で
   「note が空なら stack の `SeqInfo::remoteHost` から組み立てる」。
   後者のほうが、doc を1つずつ触らずに済む。
2. 出す/出さないで**行数を変えない**。リモートなら常に1行、ローカルなら常に0行、
   のように **stack 単位で一定**にする。
3. ついでに: 現状の文言は `remote <host> - WxH` で、**サイズは既に1行上にある**
   (`%dx%d %dch %s`)。重複しているので、source 行は host (と必要ならフレーム数)
   だけでよい。

## 15. 表記の重複と不統一

ユーザー指摘 (2026-07-30):
- 「FileBrowseで，[remote xN]と表示されるが，行末にすでに記載あるから不要なのでは」
- 「WxH Cch Type Framef という表記だが，File Browser では numpy shape を出している
  から numpy shape と dtype で統一するのがいい気がする」

**(1) `[remote xN]` の重複。** stack 名に付く `[remote x8]` の N は、行末の
列に既に出ている。同じ数字が1行に2回。`[remote]` だけにするか、
列があるなら丸ごと落とす。
(`stackNameFor` / `openRemoteStack` 周辺、main.cpp ~7134 付近で名前を組んでいる)

**(2) 形の表記が2種類ある。**
- File Browser: **numpy shape** (`8x32x32 f32` のような、`fmtEntryShape`)
- Inspector / フッター: `WxH Cch dtype  frame i/N`

同じファイルの同じ性質を、場所によって別の書き方で出している。
numpy shape + dtype に**寄せる**のが素直 (元データがそう名乗っているので、
ユーザーが npy を直接触るときと一致する)。

ただし判断が要る: Inspector の `frame i/N` は **今どのフレームを見ているか**
という状態であって、ファイルの形ではない。**形は shape+dtype で統一し、
位置は別に出す**、という分け方になるはず。項目11 (Inspector の remote 行) と
同じ節を触るので、まとめてやるのが安全。

## 17. Browse パネルは分けるべきか — そして「複数あってよいか」【議論・要決定】

ユーザー提起 (2026-07-30): 「filebrowse自体、ローカル用のパネルとリモート用の
パネル、分けざるを得ないと思うんだよね。分けるとリモート用のパネルが複数存在するか、
みたいな別の議論も生まれますが。」

### まず: これは既存の決定と正面から衝突する

`docs/browse-as-file-manager.md` (2026-07-29) は**逆**を主張している —
「概念はひとつ: 場所 (place)。ローカルパスも `user@server:~/data` も同じ場所」。
どちらかが古い。**先にこの矛盾を解くこと。** 片方を消すか、片方を書き直す。

### 分けざるを得ない、と感じる理由 (実際にコードにある差)

| | ローカル | リモート |
|---|---|---|
| 応答 | 即時 | 非同期。進捗・キャンセル・「listing...」の仮行が要る |
| 失敗 | まず起きない (権限程度) | 接続失敗、peer 未導入、版不一致、途中切断 |
| 固有機能 | — | サーバ側測定、GLOB 検索、peer 版数、prefetch |
| 寿命管理 | 無い | 接続・deploy・切断 |
| 対象の数 | **1つ** (このマシン) | **N 台**ありうる |

ツールバー3段目 (接続とサーバ) は**リモート専用**。項目12 (上部の認知負荷が高い) は
この非対称がそのまま出たもの。1枚のパネルに両方載せている限り、
ローカルで使う人は常にリモートの分の重さを払う。

そして決定的なのは最後の行。**ローカルは1つ、リモートは N 台。**
「1パネル = 1つの現在地」である限り、**2台のマシンのデータは並べられない**。
ローカルとリモートを並べることも (コピー元/先を見比べる、という一番普通の操作) できない。

### ただし `browse-as-file-manager.md` が正しかった部分は壊さないこと

- **プロトコルの統一 (両方 peer 経由) は正しい。** 分けるとしても **UI だけ**。
  ローカル用に別のファイル列挙経路を作り直すのは退行 (それこそが
  `TODO_one_implementation.md` の二重実装問題そのもの)。
- **「接続」をユーザー語彙にしない**という判断も正しかった。
  パネルを transport で分けると、その語彙が裏口から戻ってくる危険がある。
- **2パネルは同じバグを2箇所に作る。** 今日直した `..` 行・ツールバーの折返し・
  検索からの復帰は、パネルが2つなら2回直すことになっていた。

### 筋の良い問い直し方

「ローカル対リモート」ではなく:

> **Browse パネルは singleton なのか、「1つの場所を見るビュー」の実体なのか。**

後者 (= 複数インスタンス可) にすると:
- ローカル/リモートは**パネルの種類ではなく、そのインスタンスが今いる場所**になる。
  `browse-as-file-manager.md` の「場所」思想を壊さずに済む。
- **複数リモートが自動的に解ける。** ユーザーの2つ目の論点への答えになる。
- ローカルとリモートの並置も自動的に解ける。
- タブ型ファイラや VSCode の複数エクスプローラと同じ、馴染みのある形。

### 複数インスタンス化のコスト (実測)

**今のコードは徹底的に singleton 前提。**

- `app.rbrowse` — 現在地・エントリ・接続状態を持つ**構造体1個**
- `drawPanelRemote` の**関数ローカル static が 21 個** (`rbSel`, `rbSelAnchor`,
  `rbFilter`, `rbPathEdit`, `rbSearchBuf`, `rbSearchRoot`, `selSig` …)

  **N セッション × N 所有者**になり、あの規律を「場所ごとに1つ」へ一般化する必要がある

小さくはないが、やる価値のある向き。**ただし順序が重要。**

### 違い

- **残: 画像側 N の見せ方。** タイル表示か順次点滅か。Shift+C をそこに繋ぐ話は
  項目25-3。

## 20. Watch — 変化したファイルを取り込む / 開いているものを更新する

「watch folder」は未着手機能として挙がっていたが、要件が増えたのでここに集約する。

### (a) 元の watch folder

フォルダを監視し、**新しく現れたファイル/連番を自動で開く**。
撮影しながら見る、バッチが吐き出されるのを待つ、という使い方。

### (b) 開いているものを、元ファイルの更新と比較して更新する

ユーザー要望 (2026-07-30): 「開いているファイルを，元のファイルの更新と比較して，
Updateする的な機能は追々ほしくなるね．Remote, Local問わずに．Watch機能と整合しないと
いけないので」

同じパスのファイルが**上書きされた**とき、開いている側を作り直す。
再撮影して同じ名前で保存する、処理をかけ直す、といった運用で効く。

### (a) と (b) は同じ機構の上に乗る

どちらも「**元が変わったか**」を知る必要がある。判定材料:

- **mtime とサイズ** — LIST が既に両方返している (`remote::Entry::mtime`, `size`)。
  ローカルも `std::filesystem` で取れる。**追加のプロトコルは要らない**。
- ハッシュは不要 (画像は大きく、mtime+size で実用上足りる)。
  ただし「mtime が戻る」ケース (コピーで属性が保存される) はあるので、
  **等しくないこと**を変化とみなす — 新しいことではなく。

**リモートもローカルも同じ扱いにできる**のが重要。判定は peer 側の LIST から
来るので、`TODO_one_implementation.md` の「両端が同じ関数を呼ぶ」に沿う。

### 設計上の要点 (ここを外すと危険)

1. **勝手に置き換えない。** 測定中のデータが足元で入れ替わるのは事故そのもの。
   既定は**通知**: 「この stack の 3 枚が更新されています [再読込]」。
   自動更新はオプトイン。
2. **stack 単位で考える。** 24 枚のうち 3 枚だけ更新された stack は、
   σ_t の対象として**もう同一条件ではない**。部分更新は「n/N が変わった」より
   重い意味を持つので、**stack ごと作り直すか、更新を拒むか**を決める。
   frame 単位でこっそり差し替えるのが一番危ない。
3. **測定結果を道連れにする。** 更新した stack の σ_t、series の fit、
   A/B のキャッシュは**古い画素に対する答え**なので、無効化する
   (series の fit 無効化と同じ規律 — `5092c4b` の考え方)。
4. **書き込み途中のファイルを掴まない。** 撮影中のファイルはサイズが増えている。
   **サイズが2回連続で同じ**になってから読む、程度の安定化が要る。
5. **ポーリング間隔とコスト。** リモートで数百ファイルを毎秒 LIST するのは
   論外。数秒〜十数秒、かつ**パネルが見えているときだけ**、が妥当。
   アイドルループ (`app.wakeFrames`) との整合も要る。

### 順序

(b) は (a) の一部として作るのが自然 (どちらも「元が変わったか」の上に乗る)。
ただし **項目17 (Browse パネルの構造)** が決まってからにすること — 監視の
対象が「1つの場所」か「N 個のパネルの場所」かで、置き場所が変わる。

## 21. A は即時、B は1テンポ遅れ — 統計表に「古い」表示が無い

ユーザー報告 (2026-07-30): 「A,B比較のときにH,V Projectionの表が，Aは即時に変わるけど，
Bは１テンポ遅れて変わりますね．」

### 遅れ自体は意図的 (`main.cpp` ~9765)

    // skipped while frames are being stepped (see abStepBusy), except on the
    if (Bim && (!abStepBusy() || app.proj[1].uid == 0))
        recomputeProjectionIfNeeded(Bim, app.proj[1]);

`abStepBusy()` (~1123) は「300 ms 以内に2回フレームが切り替わったら、さらに 300 ms は
B の再計算を止める」(`selectImage` ~5147 が武装させる)。キー長押しで送ると B の
キャッシュ再計算がフレームごとに乗ってUI全体が重くなる、という実測に基づく throttle。
**A は throttle されない。**

### 本当の欠陥はそこではない — 表が「古い」と言っていない

`bStale` は計算されているのに、**使われているのは凡例と side-by-side の帯だけ**
(`drawABLegendRow` と `drawABBand`)。**統計表には一切出ていない。**

つまり表は、**古い数字を新しい数字と同じ見た目で出している**。
だからユーザーには「B が遅れて変わる」と見える — 「B は今 stale です」ではなく。
**表の数字は事実として読まれる**ので、これは遅さの問題ではなく**嘘の問題**。

なお今日追加した wide 表 (`d9174e0`) も同じ状態。**この欠陥を1つ増やした。**

### 設計上の問い (だから Fable)

**半分だけ更新された比較は、遅い比較ではなく、間違った比較。**
A がフレーム k、B がフレーム k−1 を映している瞬間、その表の σ_h の差は
「A と B の差」ではなく「A と B と1フレーム分の時間ノイズの差」。

取れる道:

1. **両方 throttle する。** 比較としては常に整合。A の反応が鈍く感じる。
2. **どちらも throttle しない。** まず**再計測する** — throttle が入った当時と
   比べてキャッシュも計算も変わっている (領域σを今日足した分は増えた)。
   根拠が古い可能性がある。速いなら一番きれい。
3. **throttle は残し、stale を見逃せなくする。** 表の B 行を淡色にする、
   数値を `…` にする、行に印を付ける。**古い数字を平文で出さない**のが要点。
   数字を伏せるほうが、古い数字を見せるより安全。
4. **B を非同期で計算する。** 一番きれいだが一番重い。

**3 は他とは独立に、いますぐやってよい**(表示の誠実さの話で、同期の設計判断を
待つ必要がない)。1/2/4 は同期の設計そのもの。

### 確認すること

- throttle の根拠を**再計測**する (`--bench`、B あり/なし、`g_abNoThrottle` は
  `--ab-no-throttle` 相当で既に存在する)。300 ms という値も同時に。
- Histogram と Temporal の表も同じ構造か (`app.hist[1]` も同じ gate を通る)。
  おそらく同じなので、直すなら**3パネル横断**。
- `--abstats-selftest` に「throttle 中は B の表が古い値を平文で出さない」を
  assert する検査を足す (P2c が staleness を uid で見ているので、その隣)。

## 23. 数値の書式が場所ごとに違う — 有効数字を誰が決めるのか

ユーザー指摘 (2026-07-30): 「profile statisticsの小数有効数字はそろえたい，指定できれば
いいのかな．暫定UIで，本来どうすべきかはFable TODOにつみましょう．」

Projection の表への**暫定の per-table 指定は入った** (`6047aab`: `app.projDecimals`
+ `textStat` ~9128、コンボは ~10304)。**1つの表に1つのつまみ**で、明示的に暫定。
ここに記録するのは**全体の話**のほう。

### 数えた事実

表示用の書式は1つではない (main.cpp 全体の printf 書式、出現回数):

    %.6g 84   %.0f 19   %.1f 14   %.2f 13   %.4g 10   %.5g 8   %.3g 7
    %.4f 3    %.3f 3    %.5f 1    %.2e 1
    (%.9g / %.11g / %.12g / %.17g はセッション保存と selftest の stderr。表示ではない)

「値をどう書くか」を決める関数も **3つ**ある:

- `textNum(fmt, v)` (~9117) — **書式は呼び出し側が持つ**。20箇所以上が各自
  `"%.6g"` と書いている (Histogram の quickstats、Temporal、Linearity、A/B 差分表)
- `fmtVal(v, dtype)` (~7713) — **dtype で分岐する唯一の場所**。整数 dtype なら
  `%.0f`、それ以外は `%.5g`。Inspector の画素値・min/max とステータスバーの
  ホバー値だけがここを通る
- `textStat(v)` (~9128) — 暫定で入った Projection 専用

### 何が壊れているか

`%g` は**値ごとに文字数が変わる**。1023 は4文字、1023.5 は6文字、0.00012345 は指数。
`textNum` は `CalcTextSize` で右揃えしているが、**小数点の位置が揃わないので
列として目で追えないし、貼っても列にならない**。ユーザーの「そろえたい」はここ。

そして **コピー経路は表示書式を一切見ていない**。`copyPerFrameStats` (~11460) は
TSV に `"\t%.6g\t%.6g\t%.4g\t%.4g"` と**直書き**している。表に指定を足しても
クリップボードには届かない。

### 決めるべきこと (これが設計判断)

有効数字を決める主体の候補は4つ。混ぜると必ず破綻するので**1つ選ぶ**:

1. **量ごと** — mean は DN、σ% は小数2桁、r² は5桁、という固定表。読みやすさは最良。
   量が増えるたびに表が伸びる。
2. **元データの dtype から導く** — `fmtVal` が既にやっている考え方。ただし
   **画素値と統計量で規則が違う**: u12 の生画素に小数6桁は嘘だが、その平均や σ は
   整数より細かくて当然。dtype 一本では決まらない。
3. **アプリ全体の設定** (engineering 表記 / 有効数字 n 桁)。1箇所で決まる代わりに、
   DN と % と r² が同じ桁数になる。
4. **表ごと** — 暫定で入ったのがこれ。表が増えるたびに設定も増える。

### 外してはいけない制約

- **報告書に貼った数値は再現可能であること。** 表示を丸めるなら、コピー経路は
  丸めないか、丸めたと分かる形にすること。`fmtExact` (~2280) という
  「round-trip する最短表記」(9桁から17桁まで上げて `strtod` の一致を確認する)
  が既にあり、series の level 入力で使われている。**コピーはこれを使うのが筋。**
- **整数センサの DN には自然な精度がある。** u12 の画素に `%.6g` を当てると
  存在しない精度を出す。float 書式は**その精度を隠してしまう**。
- 単位を落とさないこと (DN は DN、% は pt との差)。既存の規則。

## 24. 統計表の行 — 「all」行、B 側のプレーン展開、並び順 (**(1)(3) は済、(2) が不具合**)

ユーザー要望 (2026-07-30): 「chあるのは素晴らしい．BayerのときとかにR,Gr,Gb,B以外に
all欲しい．あとA,B比較でBはR,Gとかに展開されない．また，並びはSide順か，CHはそろってて
その中でSide順か，切り替えられるようにしておくとよいね．」

3つ別の話。**(1) と (3) は `1b3c94b` で入った** (下に何が決まったかを書く)。
残るのは (2) — 調べたら**別の、もっと深い不具合**が出てきたので、そこから。

### (2) 【確認済みの不具合・設計判断は不要・先に直す】CFA の間引きが**プレーンを丸ごと落としている**

`recomputeProjectionIfNeeded` (~9789) の間引き:

    const size_t PROJ_MAX_SAMPLES = 2000000;
    int step = (int)std::max<size_t>(1, ((size_t)rw * rh) / PROJ_MAX_SAMPLES);
    if (im->cfa) step = ((step + 1) / 2) * 2;   // keep the CFA phase intact   ← ~9844

**step は CFA なら必ず 2 以上になる** (`((1+1)/2)*2 == 2`)。小さい画像でもそうなる。
そのあと2パス:

    for (int y = 0; y < rh; y += step) for (int x = 0; x < rw; x++)   accumulate(..., true);   // H
    for (int y = 0; y < rh; y++)       for (int x = 0; x < rw; x += step) accumulate(..., false); // V

H パスは**偶数行しか見ない**、V パスは**偶数列しか見ない**。CFA では
`accumulate` が `cfaChannelAt` で**1画素1プレーン**にしか足さないので、
奇数行にしか居ないプレーンは H プロファイルに、奇数列にしか居ないプレーンは
V プロファイルに**1サンプルも入らない**。しかも `fStat` (領域の mean/σf) は
**H パスでしか積んでいない** (`if (toH) { fSum[s] += ... }`)。

RGGB / ROI 原点 (0,0) で loop を再現して数えた結果:

| plane | H の n | V の n | 表示 |
|---|---|---|---|
| R | 有 | 有 | 全部出る |
| Gr | 有 | **0** | σv が `-` |
| Gb | **0** | 有 | mean と σf と σh が `-` |
| B | **0** | **0** | `!f.valid && !hh.valid && !vv.valid` (~10374) で **行ごと消える** |

640x480 / 2048x2048 / 4096x3072 のどれでも同じ (step は 2 / 2 / 6)。
ROI 原点が奇数だと**消えるプレーンが R に変わる**だけで、必ず1枚消える。
つまり **Bayer の Projection 表は今、4プレーンのうち1枚を黙って落とし、
もう2枚は統計の半分を欠いている。** ユーザーが「R,Gr,Gb,B 以外に all 欲しい」と
書いた画面には、そもそも **B の行が無かった**可能性が高い。

87bc0a3 が mean 列に入れた `if (f.valid) ... else if (hh.valid) ...` のフォールバックは、
この非対称を**症状として踏んでいた**もの (原因ではなく表示側で回避している)。

**同じ族が他に2箇所ある** (どちらも平坦インデックス `p += step` を歩き、
step が偶数・幅が偶数だと x の偶奇が固定される):

- `recomputeHistogramIfNeeded` の `step = max(1, total/1000000)` (~8667) —
  1920x1080 で step=10、2048x2048 で 4、4096x3072 で 12。いずれも
  **Gr と B のサンプル数が 0**、mean/sd が 0、ヒストグラム曲線が空になる。
  1 Mpx 以下 (640x480, 1024x1024) では step=1 なので出ない。
- `roiBasicStatsUncached` の `step = max(1, total/200000)` (~11983) —
  800x600 で step=2、1920x1080 で 10、4096x3072 で 62。**Gr と B が n=0**、
  `valid=false` なので ROI 表のその行が空になる。

(`ensureDiffTexture` の `total/200000` (~1476) も同じ歩き方だが、プレーン別ではなく
チャネル最大の百分位なので測定値ではない。表示ゲインが偏るだけ。)

**素性**: この間引きは `a56d159` "Performance audit fixes" (2026-07-27) で入った。
それ以前は1重ループで全画素を H と V の両方に積んでいた (`hN[s][x]++; vN[s][y]++;`)。
**性能修正が測定値を黙って変えた**典型。コメントが謳う不変条件
「no column or row is ever left without data」自体が CFA では成立していない。

**`1b3c94b` の「all」行はこの偏りをそのまま受け継いだ。** プールは同じ2パスの中
(`if (P.allRow) put(4, val);` ~9868) で行われるので、**H の "all" は偶数行 = R と Gr
だけ、V の "all" は偶数列 = R と Gb だけ、領域の σf は H パス由来なので R と Gr だけ**。
「全プレーンをまとめた」と読める行が、実際には**4枚中2枚のプールになっている。**

**そして新しい検査 V17 はこれを見られない。** `--verify-selftest` の V17 (~19888) は
プーリングの算術を検算するとき `if (!T2.fStat[i].valid) continue;` で**空のプレーンを
飛ばす** — つまり「サンプルが来なかった2枚」をちょうど除外した上で全分散の法則を
確認している。`T2.nSeries == 4` も通る (`nSeries` は `cfa` から決まる値で、
サンプルが入ったかとは無関係)。**欠陥を跨いで自己無矛盾なので、永久に緑のまま。**

**直し方の要点**: 「位相を保つために step を偶数にする」が逆効果。CFA では
**step を 2 の倍数にするのではなく、位相ごとに 4 本の走査を持つ** (偶数行と奇数行の
両方を、偶数列と奇数列の両方を必ず1回は通す) か、`step` を奇数に丸めるかのどちらか。
`fStat` を H パスだけで積むのもやめること。
**回帰**: 「CFA 画像で `nSeries` 本すべての `fStat`/`hStat`/`vStat` が valid」
「plane 別サンプル数が 0 でない」を assert する検査を足す。数字が合うかではなく
**存在するか**を見る検査 — V17 の `continue` を消して「valid でなければ落ちる」に
変えるのが最短。fixture は既存の Bayer データで足りる。

### (2') 「A,B比較で B が展開されない」の、compare スロット側の読み — **画面で言う所までは済 (`36cc08d`)**

上の不具合と別に、**compare スロット B のプレーン数が A と違う経路も実在する**。
`recomputeProjectionIfNeeded` は `P.nSeries = cfa ? 4 : std::min(im->ch, 3)` を
**その doc 自身の `cfa`** から決める (~9811、`cfa = im->ch == 1 && im->cfa != 0`)。
Histogram も同じ形 (`H.nSeries` ~8661)。そして:

- CFA の解釈は **`ImageDoc` ごとの属性**で、Inspector の "Interpret" コンボは
  `cur()` = **A にしか効かない** (~9317)。
- `seqMosaicChanged` (~6752) が伝播するのは **同じ `seqId` の中だけ**
  (`if (d->seqId == si->id)`)。別々に開いた2ファイルなら B には伝わらない。
- 一括で効くのは CLI の `--cfa` (`app.forceCfa`、ロード時に適用 ~2944 / ~7375) だけ。

つまり **A を手で Bayer にした瞬間、B は Gray のまま**になり、A は R/Gr/Gb/B の
4行、B は `ch0` の1行になる。表の欠陥ではなく「B の解釈を設定する手段が無い」
という欠陥。`abStepBusy()` は 300 ms の throttle でしかなく (項目21)、
`abSeriesMatch` (~8989) も**行を落とさない** — 使っているのは線の色と
凡例だけ (~10088、名前が一致しないプレーンは `ODD_COL` で描く)。**行を減らしているのは
`nSeries` そのもの。**

ついでに数えた事実: **Histogram の "quickstats" 表 (~9564) には B の行が1本も無い。**
`app.hist[0]` の `nSeries` だけを回していて side 列すら無く、比較中でも A の
数字しか出ない。Projection だけが side 列を持っている。「B が展開されない」を
Histogram の表で見たのなら、これが答え (=そもそも B が居ない)。

**済んだ部分 (`36cc08d`)**: 「最低限、プレーン集合が違うことを表で言う」は入った。
`projSayPlaneMismatch` (~10243) が、少ない側の名前と
"its CFA interpretation differs" を橙で出し、ツールチップで直し方
(Inspector > Interpret) を言う。サイズ違いの "size differs" (項目3) と同じ扱い。

**残っている決めごと**: **CFA の解釈は doc の属性か、比較ペアの属性か、
それともセンサの属性か。** 「B にも自動で同じ解釈を当てる」にすると、
意図的に別解釈で並べたい場合 (raw と demosaic 済み) が壊れる。
逆に今のままだと、**A を Bayer にするたびに B を選び直して同じ操作をやり直す**
必要がある (Interpret は `cur()` にしか効かないので)。
候補: (a) doc のまま + 警告 (今)、(b) 比較に入る側へ引き継ぐ、
(c) 「この stack はモザイクである」を stack/series の宣言にする
(項目16-3 の flat/dark 宣言と同じ形の問題 — 宣言か推論か)。

### (1) 「all」行 — 済 (`1b3c94b`)。正典との折り合いの付け方も込みで

正典はこう言っている:

- `docs/stats-taxonomy.md` 29行目: 「**鉄則 — plane は決して混ぜない**」
  「plane 混合平均は**「別の測定」であり既定にしない**」
- `docs/terminology.md` 92行目: 「CFA プレーンは統計で決して混ぜない」

入ったものは正典に沿っている: `app.projAllRow` は**既定 OFF**、`P.allRow` は
`nSeries` とは**別のフラグ** (~967 / ~9815) なので 5枚目のプレーンにはならず、
行はその組の**最後**に固定 (`projForEachRow` ~10257)。プールは plane 行と
**同じパスの中**なので、全体と部分が同じサンプルでできている。

**残っている宿題**: 画面が「これは σ に何を含むか」を言っていない。
プールされた σf には**プレーン間の平均差 (= モザイクのコントラスト)** が
全分散の法則どおり入る (V17 が `within + between` で検算しているとおり)。
Bayer の "all" の σ は**ノイズではない**。既存の語彙
`"plane=all (no CFA split)"` (~11324 / ~11417 / ~13514 / ~13930) と
`nPl > 1 ? "CFA planes" : "plane=all"` (~11735) が既にあるので、
**同じ言い方をこの行にも出す**こと。

**もうひとつ残っている**: 「all」という語は既に**別の意味**で使われている。
Histogram の `plane##hist` コンボ (~9604) と ROIs の `channel` コンボ (~12060) の
"all" は「**全プレーンをそれぞれ描く/並べる**」というフィルタで、混合ではない。
ところが **ROIs の "all" だけは実際に混ぜている**: `roiBasicStatsUncached` (~11976)
は `chSel < 0` のとき CFA でもプレーンを分けずに `sum`/`sum2` に積む — つまり
Projection に入ったのと同じ測定を、**ラベル無しで**出している。
**同じ単語が3通りに使われている状態。** ROIs 側を Projection に揃えること。

### (3) 並び順 — 済 (`1b3c94b`)。ただし channel 主の突合せが**名前ではなく添字**

`app.projStatOrder` (0 = side 主 / 1 = channel 主) と `projForEachRow` (~10257) が
入り、**wide と per-axis の両方が同じ関数から行を取る**ので、2つの表が
「どの行が、どの順で」で食い違えなくなった。prefs は `projstatlayout` 行に同居
(~3803)。以前の状態 (wide = side 主、per-axis = axis 主 → side → plane、
どちらも `ImGuiTableFlags_Sortable` 無し) は解消。

**残っている欠陥**: channel 主の突合せが**スロット添字**で行われている:

    for (int i = 0; i < maxSeries; i++)
        for (const auto& sr : sides)
            if (i < sr.S->nSeries) row(*sr.S, sr.name.c_str(), i);

(2') のとおり **サイドごとにプレーン集合が違いうる**ので、A が Bayer で B が
Gray だと **`R:A` の真下に `ch0:B` が並ぶ**。「同じプレーンを縦に並べる」という
channel 主の目的がそこで壊れる。名前で突き合わせる `abSeriesMatch(names, n, want)`
(~8989) が既にあり、片側にしか無い系列に -1 を返す — **これを使うこと**。
片側に無いプレーンの行は**詰めずに `-`** を出す (詰めるとサイドごとに行数が変わり、
縦の対応が取れなくなる)。

もう1点、表の高さは**先に予約されている** (`statRows` ~10040 / ~10048、
`allRows` を数え込むよう追随済み)。行の組み方をこれ以上変えるなら予約式も
同じ規則で直すこと。並び順がフレーム送り中に変わらないことも維持する
(「columns must not reflow while stepping through frames」~9562 の行版)。

## 25. Compare を入れたときの B の既定と、Shift+C

ユーザーの最初の言葉 (2026-07-30): 「A, B比較でない状態で，Cを押すと，何かがBになって
A,B比較になりますが，選択中のやつをBとしてAも選択中のやつで開始した方が分かりやすく
ない？」
すぐ自分で訂正: 「ああ，A,B比較してないときに，CショートカットでBが何か選択されるのは
前の状態を維持しているからか．これは使いやすいね．ごめん，正確にはBが**前のやつあったら
それ，無かったら選択のやつ**，にしましょう．で，**Shift+Cで，A,B,C,...のC以降の比較**を
呼び出せばいいのかな，きっと．」

### 半分は `6047aab` で入った。**残り半分は入ったが動いていない。**

行番号は `6047aab` (= この記録を書いた時点の HEAD) のもの。

| 要望 | 状態 |
|---|---|
| 「B が前のやつあったらそれ」 | **済 (`6047aab`)。** `App::lastCompareBUid` (~325) を `setCompareB` (~1122) が書き、`ensureCompareB` が最初の候補として読む (~1324)。`--abstats-selftest` の A9 が固定 (~20794) |
| 「無かったら選択のやつ」 | **未。** 第2候補は従来どおり `app.prevImageUid` (直前に**見ていた** doc、`selectImage` ~5281 が更新) → それも無ければリストで次の画像 (~1332)。下記1のとおり、今の作りでは「選択のやつ」は B になれない |
| 「Shift+C で C 以降の比較」 | **書かれたが到達しない。下記2。** |

なお、ユーザーが気付いた「前の状態を維持している」挙動そのものは `lastCompareBUid`
とは別物で、`ensureCompareB` 先頭の `if (resolveB()) return;` (~1319) が作っている
— `app.compareBUid` はモードを Off にしても消えないため。B が消えるのは画像を
閉じたときと Close All (~2404 / ~2516 / ~2735)、セッション読み込み (~4289) だけ。
`lastCompareBUid` が効くのは**その先** (B を閉じた後、比較を組み直すとき)。

### 1. 「無かったら選択のやつ」= A と B が同じ画像 【要決定】

今の作りはこれを**意図的に禁じている**:

- `resolveB()` の最後 `return b == cur() ? nullptr : b;` (~1096)
- `ensureCompareB` の候補走査は全部 `d.get() != cur()` 付き
- `addCompareSlot` も `if (!d || d == cur()) return;` (~1280)

理由は `selectImage` (~5272) のコメントに書いてある — 「B はユーザーが意図して
留めたもの。A がそこへ歩いてきても書き換えない。立っている間だけ比較が黙り、
離れれば留めたまま戻る」。**A==B で始めるなら、この規律を変えることになる。**
差分は全ゼロ、ワイプは無意味、統計表は同じ行が2本 — 何を見せるのかまで決めること。

選択肢: (a) A==B を許し「同一」と画面で言う、(b) 「B 未設定」という第3の状態を
作る (モードには入るが B が空)、(c) 要望を採らず `prevImageUid` の今の挙動を
維持し、画面で説明する。

### 2. 【不具合】Shift+C は書かれたが**永久に到達しない**。しかも二重予約

`6047aab` は `showCompareSlots()` (~1343) を足し、こう呼んでいる:

    if (!io.WantTextInput && !popupOpen && io.KeyMods == ImGuiMod_None) {   // plain keys   ← ~21148
        ...
        if (ImGui::IsKeyPressed(ImGuiKey_Backslash, false) ||
            ImGui::IsKeyPressed(ImGuiKey_C, false)) {
            if (ImGui::GetIO().KeyShift) showCompareSlots();   // C, D, E...   ← ~21157
            else                         cycleCompare();
        }

ブロック全体が `io.KeyMods == ImGuiMod_None` でガードされているので、
**その中の `io.KeyShift` は定義上つねに false**。`showCompareSlots()` は
**死んだコード**で、Shift+C は下の Shift ブロック (~21225) に落ちて
**`swapCompare()` になる** — つまり挙動は変わっていない。

さらに Shift+C は**もともと Swap に予約済み**で、5箇所に印字されている:
Files 行メニュー (~14240 / ~14246)、View > Compare A/B (~14999)、
ヘルプのキー一覧 (~15376)、ステータスバーのツールチップ (~21493)。

**決めること**: Swap をどのキーへ動かすか、あるいは「C 以降」を別のキーにするか。
どちらにしても**上の5箇所の文字列が追随する**こと。実装側の注意は
「Shift 付きは plain キーのブロックに書けない、~21225 の Shift ブロックに書く」。

### 3. 「C 以降の比較を呼び出す」とは何をすることか 【要決定】

スロット C, D, E… は `caa5216` で**数値側だけ**実装済み (`app.cmpExtra`、
`compareExtras()` ~1255、`slotName()` ~1268 — Projection の表に行が増える)。
画像側は依然 A 対 B のみ。`showCompareSlots()` が実際にやっているのは
`compareMode = CmpSplit` にすることだけで、**CmpSplit は 2枚の左右分割**だから、
スロットが3つあっても画像は A と B しか出ない。

つまりこのキーが「呼び出す」ものは、今のところ**統計表を見に行く**ことしかない。
**項目19 の「画像側を N にする見せ方」(タイル / 順次点滅) が決まるまで、
このキーに与える意味が無い。** 19 → 25 の順。

## 26. Browser のダブルクリックで、押していない物まで開かれる

ユーザー報告 (2026-07-30): 「Browserからダブルクリックしたときに，ダブルクリックした
以外のやつも追加されるように思うのは他のクリックがダブルクリック判定になってるからなの
かなー」

**項目1 (Preview バグ) と同じ根の可能性が高い。** 一緒に見ること。

### 潰した仮説 (再調査しないこと)

- **「プレビューが出て行がずれ、2クリック目が別の行に落ちる」— 違う。**
  スクラブバーの領域は `rbFootH = GetFrameHeightWithSpacing()` で**無条件に**
  予約されており (main.cpp ~14192、テーブルの outer_size が `-rbFootH`)、
  プレビューの有無で行は動かない。コメントにも
  「appearing must never move the rows (double-click depends on it)」とある。
- **「隣の行への2連クリックが二重クリック判定になる」— 違う。**
  ImGui は距離しきい値 `io.MouseDoubleClickMaxDist` (既定 6px) を見る。
  行の高さはそれより大きいので、別の行へ移動した2クリックは二重にならない。

### まだ潰せていない筋 (ここから始める)

1. **2クリック目が単クリック処理も走らせる。** `Selectable` は離した時に true を
   返すので、二重クリックの**2回目でも** `rowClicked` が真になり
   `rbActivateRow(r)` (= プレビュー生成) が走り、**同じフレームで**
   `IsMouseDoubleClicked` も真になって `rbOpenRow(r)` が走る
   (main.cpp ~14342 と ~14366)。グループ行の `rbOpenRow` は先に
   `dropPreview()` するが、**単一ファイル行は `promotePreview` する**。
   この2経路が同フレームで重なったときに何が残るかを、実際に数えること。
2. **`IsItemHovered()` が指す item。** 二重クリック判定は
   `ImGui::IsItemHovered()` に依存しているが、これは**直前に提出された item**を
   指す。Selectable と判定の間に item が挟まっていないか、クリッパの都合で
   行の提出順が変わらないかを確認する。
3. **キーボード経路との二重発火。** カーソル移動は `rbActivateRow` を呼び、
   Enter は `rbOpenRow` を呼ぶ。マウスとキーが同フレームで両方走らないか。

### 調べ方

`--browse-keys-selftest` は実入力を注入してフレームを回せるので、
「1行を二重クリックしたあと `app.images` に何が増えたか」を数える検査を足すのが
一番早い。**増えた枚数と、その名前**を出すこと — 「2枚増えた」だけでは
どちらが余計なのか分からない。

## 28. 比較ではなく「2枚同時に見たい」— 1つの App 内か、別 Window か【議論・要決定】

ユーザー提起 (2026-07-30): 「A,B比較ではないけど，二枚開きたいときに，App内で完結
させるか，新しいAppを立ち上げるか悩ましい．統計値とか解析がActiveなフレームに紐ついて
いるので．後者いい気はしているが，それのインターフェースは欲しい．右クリックで，新Window
で立ち上げ，的な．」

### 問題の正体は `cur()` が1つしかないこと

Histogram・Projection・Temporal・Inspector・Analysis は**すべて `cur()` を読む**。
「アクティブなフレーム」がアプリに1つしかないので、2枚を**対等に**見るには
どこかで単一性を壊す必要がある。A/B 比較はその例外を2枠だけ作ったもので、
共有レンジ・follow-frame・B ピンといった**比較の意味**が付いてくる。
ユーザーが要らないと言っているのはその意味のほう。

### 取れる道は4つ

1. **別プロセスを立ち上げる**(ユーザーの本命)。分離は完全でリファクタ不要。
2. **App 内で2つ目のビューを持つ**。`cur()` を「パネルごとの対象」に一般化する。
   これは項目17 (Browse パネルが singleton か) と**同じ問題のより深い版**で、
   測定キャッシュ (`hist[2]` `proj[2]` `temporal[2]`)、`selectedAnn`、
   レンジスコープまで巻き込む。
3. **ImGui のマルチビューポート**で OS ウィンドウを増やす。**解決にならない** —
   ウィンドウが増えても `App` は1つなので `cur()` 問題はそのまま残る。
4. **パネルを画像にピン留めできるようにする**。「このヒストグラムは常に画像 X」。
   `cur()` を壊さずに済み、**今日入れた比較スロット (`cmpExtra`) の一般化**に
   なる。2枚を対等に見たいという要求の大半はこれで満たせる可能性がある。

**1 と 4 は排他ではない。** 4 を入れてなお別ウィンドウが欲しい場面
(2画面に出す、片方を触らず固定する) は残る。

### 1 を選ぶなら — 先に潰さないと確実に事故る箇所 (コードで確認済み)

- **オートセーブが衝突する。** `autosavePath()` (main.cpp ~4032) は
  `%APPDATA%/viewer/autosave.vsession` **固定**。2つ目のインスタンスが
  終了時に上書きし、**1つ目のセッションが消える**。
- **prefs も衝突する。** `prefsPath()` (~4055) は実行ファイルの隣の
  `prefs.txt` 固定。最後に終了したほうが勝ち、レイアウトやレンジ設定が飛ぶ。
- **リモートは ssh セッションが2本になる。** 同じホストの別ファイルを別窓で
  開くと、peer の deploy とセッション確立がもう一度走る。転送量と接続数が
  2倍になることをユーザーが知らないまま起きる。
- 起動時に**同じ場所にウィンドウが重なる**と、開いたことに気付けない。

対策の形: 2つ目以降は `--no-autosave` 相当で起動する / インスタンスごとの
オートセーブ名にする / prefs は読むだけにする、のいずれかを**決めてから**
インターフェースを付けること。順序を逆にすると、ユーザーのセッションを
食う機能を先に配ることになる。

### インターフェース

ユーザーの案どおり **Files / Browse の行の右クリックに「新しいウィンドウで開く」**。
実装は `GetModuleFileName` (Win) / `/proc/self/exe` (Linux) + そのパスを引数に
渡して起動するだけ。**リモートなら url をそのまま渡せる** (`ssh://...` の CLI
配線は `remote::parseUrl` があり、起動パスへの接続が未配線 — `docs/remote.md` 参照)。
表示状態 (CFA 解釈・レンジ・gamma) も引き継がないと「同じに見えない」ので、
何を渡すかを決めること。

### 順序

**項目17 の後**。パネルが singleton かどうかの判断がそのままここに効く
(2 と 4 は同じ土台の上にある)。1 だけ先に出すことも可能だが、
その場合でも上の衝突4件は先に潰すこと。

## 付録. 環境の重要事実 (両エージェントが独立に確認)

**この Windows 機は現在 OpenGL のクライアント領域を一切キャプチャできない。**
`CopyFromScreen` / `BitBlt+CAPTUREBLT` / `BitBlt(GetWindowDC)` / `PrintWindow` の
すべてが**真っ白**を返す。一方で同じ画像内のタイトルバー(GDI)は正しく写り、デスクトップ
全体のキャプチャも正常(VS Code は読める)。GL 自体は動いている
(`glReadPixels` はマゼンタを返す、`--bench` は 0.32ms/frame)。
→ **スクリーンショットによる検証は今この機械では不可能。** 白い画像を「モニタが寝てる」
と誤診して時間を溶かさないこと。代わりに使えた観測手段:
`GetWindowText` によるウィンドウタイトル、stderr、Win32 メッセージトレース、
そして「視覚的事実を selftest の測定可能な assertion に変換する」。

入力注入の罠2つ:
- `keybd_event` に scancode 0 を渡すと `GLFW_KEY_UNKNOWN` になり矢印キーが無反応。
  `MapVirtualKey` + `KEYEVENTF_EXTENDEDKEY` が要る。
- タイトルバーを続けて2回クリックするとダブルクリック扱いで最大化し、全座標がずれる。
