# 画像フォーマットをどう読むか — 測定に基づく判断 (EXR / PNG / ほか)

`.npy` / `.npz` / raw の外にある画像形式を、**どの機構で読むか**を決める文書。

この文書は [docs/media-support.md](media-support.md) の §1 (OpenEXR の候補比較) を
**置き換える**。あそこの結論は tinyexr だったが、ユーザーがそれを覆して公式
OpenEXR にした ([docs/tasks.csv](tasks.csv) の「フォーマット」行が
`OpenEXR(公式lib)` と書いているのがその記録)。media-support.md の動画と
click-to-open の節は生きているので、あの文書自体は残る。

出発点 (ユーザー、2026-08-03):

> oiio 使うのがいいのかね、きっと

> oiio と OpenEXR 公式で、oiio の方が読み出しが早かったような

後者は**記憶であって事実ではない**ものとして扱った。結果として
**その比較そのものは実行できなかった**が、記憶を説明する原因は測れた (§3.5)。
**測っていないことは「測っていない」と書く** — §10 に一覧してある。

---

## 0. 結論を先に

1. **戦略 C (狭く始める) を推す。** いま native にするのは **EXR だけ**。
   公式 OpenEXR を FetchContent で固定する (実測で建つ: configure +17.8 s /
   build +20.3 s / バイナリ +2.98 MiB / BSD-3-Clause)。
2. **OIIO (戦略 A) は退ける。** ただし理由を2つに分ける:
   - **実務上**: この repo が要求する **FetchContent だけでは建たなかった**。
     3回試して 212 s 費やし、一度も build に到達しなかった (§3.4)。
     OIIO を使うなら **vcpkg / conda / システムパッケージが要る** — つまり
     README:27 の「事前準備は不要」を破ることになる。
   - **設計上**: こちらが本質。**OIIO が買ってくれる幅の大半は、この道具が
     測定値として扱ってはいけない形式**である (§4)。依存を1桁増やして、
     読めるようになったファイルの測定を断る取引になる。
3. **EXR より先に `values` を入れる。** 画素が [DN] なのかを名乗るフィールドを
   `FrameSource` に置き、analyzer をそれで門番する (§5)。
   **表示参照の画素が1つも入ってこないうちに門を作る**のが一番安い。
4. **ユーザーの速度の記憶には、測定で説明がついた。**
   OIIO は EXR を**自前で読んでいない — OpenEXR をリンクして読んでいる**
   (これは実測: OIIO のビルドが OpenEXR 3.3.5 を依存として建てた)。
   同じデコーダである以上、差は**スレッド数**から来る。そして測ったところ:

   > **`Imf::setGlobalThreadCount()` を呼ばない既定の OpenEXR は、
   > 呼んだ場合より ZIP で 3.6 倍・PIZ で 5.0 倍遅い。**

   OIIO は既定でスレッドプールを張る。**素朴に書いた OpenEXR と OIIO を
   並べれば、OIIO が 3〜5 倍速く見える。** ユーザーの記憶はおそらくこれで、
   ライブラリの優劣ではない。**含意は実装に直結する** — §9 問い 4。

## 1. いま真であること (すべて測定値)

### 1.1 依存の流儀

| 事実 | 出典 |
|---|---|
| 依存は4つだけ。**全部 FetchContent の `URL` zip 固定**。`GIT_REPOSITORY` は1つも無い | [CMakeLists.txt](../CMakeLists.txt):23-43 |
| サードパーティの CMake プロジェクトを実質 `add_subdirectory` するのは **glfw 1つ** | 同 25 |
| imgui は**ソースファイルを直に並べて**自前の静的ライブラリにしている | 同 45-51 |
| miniz は `.c` を**各実行ファイルに直接コンパイル**。ライブラリにすらしない | 同 73 / 114 / 142 |
| pfd はヘッダのみ。`SOURCE_SUBDIR does-not-exist` で `add_subdirectory` を**わざと抑止** | 同 40-43 |
| README の約束: 「FetchContent が自動取得するので**事前準備は不要**」 | [README.md](../README.md):27 |

この repo の依存の作法は「**ピン留めした zip を落として、自分のターゲットに
直接混ぜる**」であって、「他人の CMake プロジェクトを丸ごと抱える」ではない。
vcpkg / conda / システムパッケージを要求する選択肢は README:27 を破る。
これは好みではなく**文書化された約束**である。

### 1.2 ビルドとバイナリの現状 (この機械での実測)

clean configure + clean build を3回。中央値と幅で書く。

| 量 | 中央値 | 3回の実測 |
|---|---|---|
| configure | **3.22 s** | 3.22 / 3.19 / 3.72 |
| build | **57.8 s** | 54.3 / 57.8 / 61.4 |
| configure+build | **61.5 s** | 57.5 / 61.5 / 64.6 |

| バイナリ | サイズ |
|---|---|
| `viewer.exe` | **7,996,319 B** (7.63 MiB) |
| `viewer-serve.exe` | **3,354,273 B** (3.20 MiB) |

build の幅は中央値に対して **±6%**。以降「ビルドが N 秒増える」は、
この幅より大きいものだけを意味あるものとして扱う。

### 1.3 CI の形

[.github/workflows/build.yml](../.github/workflows/build.yml) と
[tools/run_selftests.sh](../tools/run_selftests.sh) より:

- マトリクスは **windows-latest (MSVC) / ubuntu-latest / macos-latest** の3面。
- configure は `cmake -S . -B build -DCMAKE_BUILD_TYPE=Release` **だけ**
  (build.yml:49)。**vcpkg も conda も無い。** Linux の `apt-get` は
  X11/Wayland/GL/xvfb だけで、画像ライブラリは1つも入れていない (同 46-47)。
- selftest は 22 本 + 隔離1本。並列実行は禁止 (run_selftests.sh:97-99)。
- **ここが一番効く**: Linux ジョブは `viewer-serve` を Ubuntu 20.04 コンテナで
  **手書きの g++ 1行**で建て直す (build.yml:90-108)。このコンテナに入るのは
  `g++` だけで、**cmake は入っていない**:

  ```
  apt-get install -y -qq g++
  gcc -O2 ... build/_deps/miniz-src/miniz.c -o /tmp/miniz.o
  g++ -O2 -std=c++17 ... core/serve_main.cpp core/serve.cpp core/plugin_host.cpp /tmp/miniz.o
  ```

  古い glibc の計算機に配る peer を作るためのもの (同 85-86)。
  **`viewer-serve` が読む形式に外部ライブラリが1つでも入った瞬間、この行は破綻する。**

### 1.4 PNG は既に「書ける」。読めないだけ

[core/main.cpp](../core/main.cpp):2190 にこうある:

> `// PNG via miniz, which is already linked for .npz. No new dependency.`

`tdefl_write_image_to_png_file_in_memory_ex` で 8bit RGBA を書いている (同 2194)。
**書きはある、読みは無い。** そして書いているのは「今見えている絵」であって
測定値ではない (Save view as PNG)。

伏線として書いておく: **この repo は既に「PNG は絵であって測定値ではない」
という側に立って PNG を使っている。**

### 1.5 loader はどこにあるか

- デコードは全部 `core/main.cpp` の中にある
  (`decodeNpyBuffer` main.cpp:4451、`decodeRawFrame` 同 4634)。
- `core/serve.cpp` は**別実装**の npy ヘッダパーサを持つ (serve.cpp:115
  `parseNpyHeader`)。フレームを実体化せず、ストライド読みだけする設計。
- したがって **client に形式を足しても serve は影響を受けない**。
  逆に remote で新形式を読ませるなら serve 側にも要り、§1.3 の手書き g++ 行に当たる。

### 3.4 戦略 A (OIIO): FetchContent では建たなかった

**3回試した。1回目の失敗はこちらのせいなので、そう書く。**

| # | 条件 | 結果 |
|---|---|---|
| 1 | scratchpad (パス 126 文字) | configure が **36.2 s** で失敗。`CMAKE_OBJECT_PATH_MAX` (246/250 文字) の警告が並び、OpenEXR の vendored deflate のサブビルドが落ちた。**OIIO の問題ではなく置き場所の問題** |
| 2 | 短いパス (50 文字)、依存フル | configure が **93.7 s** で失敗。**ZLIB → Imath → OpenEXR 3.3.5 → libjpeg-turbo までは建った**。Google **libultrahdr** で `Could NOT find libuhdr` |
| 3 | 短いパス + TIFF/PNG/WebP/GIF/HEIF/LibRaw/Ptex/Freetype/OpenJPEG/libuhdr を**全部 OFF** | configure が **81.9 s** で失敗。さらに **pystring → expat → yaml-cpp** まで進み、`build_OpenColorIO.cmake:29` で `yaml-cpp` が建った直後に見つからず停止 |

合計 **211.8 s を configure に費やして、一度も build に到達しなかった。**

分かったことを、正確に:

- **「OIIO は FetchContent では無理」という単純な話ではない。**
  OIIO は `OpenImageIO_BUILD_MISSING_DEPS=all` という自前の依存ビルド機構を
  持っていて、**それは実際に動いた** — 7 個の依存を順に取得・ビルドしている。
- **しかし完走しなかった。** 落ちたのは毎回「ローカルに建てた依存を、直後の
  `find_package` が見つけられない」形で、MinGW でのインストール配置の問題に見える。
  **MSVC や Linux なら通る可能性は十分にある — そこは測っていない。**
- **依存の木は、事前の想定より深い。** 想定は「OpenEXR, libtiff, libpng,
  libjpeg, fmt, robin-map」だったが、実際には **OpenColorIO が必須**で、
  それが **pystring / expat / yaml-cpp** を連れてくる。形式ライブラリに
  たどり着く前にこれだけある。
- **OIIO は自分の OpenEXR / Imath の版を選ぶ**: OpenEXR **3.3.5**、Imath **3.1.10**。
  戦略 B で固定したい版 (3.4.13 / 3.2.2) とは別物。両方要る構成では OpenEXR が2本になる。

**質問への答え**: この repo が要求する「FetchContent だけ・事前準備なし」で
OIIO を入れることは、**この環境ではできなかった**。現実的には
**vcpkg / conda / システムパッケージが要る**。それは README:27 の約束を破り、
「1つの自己完結したバイナリ」という性格とも噛み合わない。

### 3.5 読み出し速度

4096×2160 の **float RGB** EXR を 3 通りの圧縮で作り、全画素を float に
展開する時間を測った。内容はグラデーション + 固定パターン + 画素ごとのノイズ
(決定的 LCG)。**平坦な画像は圧縮が効きすぎてデコード時間の嘘になる**ので、
センサらしいノイズを入れてある。

#### 3.5.1 既定 (スレッド数を設定しない場合)

| 圧縮 | ファイル | 中央値 | 最小–最大 |
|---|---|---|---|
| NONE | 106,203,193 B | **47.2 ms** | 46.5–50.4 |
| ZIP | 100,509,821 B | **177.7 ms** | 176.3–190.2 |
| PIZ | 85,386,113 B | **309.4 ms** | 307.9–317.5 |

ZIP と PIZ は後の実験で独立にもう一度測っており (182.6 / 315.5 ms)、
**2回の測定は 3% 以内で一致**した。再現性はある。

#### 3.5.2 スレッド数を振る — ユーザーの記憶の正体

OIIO と OpenEXR を並べることは**できなかった** (§3.4)。
しかし §3.4 の失敗ログが決定的な事実を1つ与えてくれた:

> **OIIO は EXR を読むために OpenEXR 3.3.5 を建ててリンクしている。**

つまり EXR に関して両者は**同じデコーダを走らせている**。速度差が出るとすれば
デコーダの優劣ではなく、**その周りの設定**である。いちばん怪しいのは
スレッド数だった: OpenEXR の C++ API は `setGlobalThreadCount()` の既定が **0**
(呼び出しスレッドのみ) で、OIIO は既定でスレッドプールを張る。

測った (中央値、n=10、コールド除外):

| threads | ZIP | PIZ |
|---|---|---|
| **0 (既定)** | **182.6 ms** | **315.5 ms** |
| 4 | 63.3 ms | 102.4 ms |
| 8 | **51.2 ms** | 77.8 ms |
| 20 | 54.5 ms | **63.5 ms** |

- ZIP: 182.6 → 51.2 ms、**3.6 倍速くなる**。8 スレッドで頭打ち (20 では
  わずかに悪化 — 過剰割り当て)。
- PIZ: 315.5 → 63.5 ms、**5.0 倍速くなる**。20 まで伸び続ける。
- **8 スレッドの ZIP (51.2 ms) は、無圧縮を単スレッドで読むの (47.2 ms) と
  ほぼ同じ。** スレッドを与えれば、読み側で圧縮はほぼ無料になる。

**これがユーザーの記憶の説明になっている可能性が高い。**
素朴に書いた OpenEXR と、既定でプールを張る OIIO を並べれば、
**OIIO が 3〜5 倍速く見える。** 差はライブラリではなく1行の設定にある。

**ただし断定はしない。** OIIO を建てられていない以上、これは
「差を説明しうる測定された機構」であって、「あの時の比較の再現」ではない。
ユーザーが別のもの (TIFF や JPEG、あるいは別マシン) を比べていた可能性は残る。

#### 3.5.3 比較を実際にやるときの注意

仮に両方測れても、**両者は同じものを読んでいない**:
OpenEXR の `FrameBuffer` は **R/G/B を別平面 (プレーナ)** に展開し、
OIIO の `read_image` は**インタリーブ**して返す。`ImageDoc` がどちらを
欲しがるかで片方に詰め替えが乗る。揃えてから測ること。

### 3.6 CI への波及

**測ったもの**: このローカル機械で OpenEXR を足すと configure +17.8 s、
build +20.3 s。CI ランナーは 20 コアより貧弱なので**増分はこれより大きい。
倍率は測っていない。**

**測っていないが構造から確実なもの**:

| 影響 | 中身 |
|---|---|
| 3面 × 初回ビルド | OpenEXR の取得とビルドが Windows/Linux/macOS の**それぞれで**走る。キャッシュを張らない限り毎回 |
| **MSVC** | この文書の時間は全部 MinGW。**MSVC での OpenEXR ビルドは測っていない** |
| **Ubuntu 20.04 コンテナ** | §1.3 の手書き g++ 行。**EXR を client 限定にすれば無傷**。serve に入れた瞬間、cmake を入れて OpenEXR を建てる工程に化ける |
| selftest の fixture | **numpy は EXR を書けない**。今の CI は「numpy さえあれば全 fixture が作れる」(build.yml:35-37) という単純さで回っている。EXR の fixture 生成手段は**未解決** — §9 問い 5 |

## 4. 数字が何を意味するか — ここが本題

[docs/terminology.md](terminology.md) と [docs/import-adapters.md](import-adapters.md) §9
が決めていること:

> **画素値の単位は [DN] 固定。**

σ_t も FPN も PRNU も linearity も PTC も、**画素値が集めた電荷に比例する**
という前提の上に乗っている。前提が崩れた値で σ_t を出すと**数字は出るが意味は無い** —
import-adapters.md §4.5 が「測定器として最悪の失敗」と呼ぶものである。

### 4.1 形式ごとに、ファイルは何を言うか

| 形式 | ファイルは何と言っているか |
|---|---|
| `.npy` / `.npz` / raw | 何も言わない。しかし**ユーザー自身が書き出したファイル**である |
| **EXR** | 仕様が**線形を規約としている**。ただし「センサの DN だ」とは言わず、スケールも言わない。**ファイルごとにそれを確認する旗は無い** |
| **PNG** | `gAMA` / `sRGB` / `iCCP` / `cICP` が**あれば**言う。**無ければ何も言わない** |
| **TIFF** | 伝達関数のタグは事実上無い。科学用 TIFF は float を素で置くことが多い |
| **JPEG** | 常に表示参照。DCT 量子化とクロマサブサンプリングを通っている |

**16bit PNG が一番厄介**という指摘は正しい。同じ 16bit PNG が、リニアな
センサ DN のダンプであることも、sRGB 符号化された画面の絵であることもあり、
**チャンクが無ければファイルはどちらとも言わない**。ビット深度は手がかりにならない。

### 4.2 この repo は既にこの問題を1度解いている

新しい原則を発明する必要は無い。**同じ問題が montage で既に起きていて、
既に解かれている。**

`perFrameAuto` の montage は各タイルを自分の min..max で正規化する。
その結果を main.cpp:3561-3566 のコメントがこう書いている:

> 正規化した montage は**見るための絵であって測定ではない**。
> **it says so in its name, its note and its unit-less display range**

画面のツールチップ (main.cpp:10275-10278) は
`The values stop being DN - the montage says so in its name and note. View only.`
と言い、**selftest E11 (main.cpp:23390) が note に `NOT DN` が入っていることを
assert している**。

つまり既定の作法は:

> **画素が DN でなくなったら、名前と note と表示レンジの3か所でそう言い、
> それを selftest が守る。**

表示参照の形式への答えは、**この作法をファイルの入口に広げること**である。

### 4.3 ただし `note` では足りない — これは追って分かった

`ImageDoc::note` の読み手を全部追ったところ、**Inspector 1か所
(main.cpp:11548) と selftest だけ**だった。そして:

- **`note` はセッションに保存されない。**
- **`note` はエクスポートに出ない。**

したがって「PNG は note に『解釈不明』と書いて読む」という設計は**成立しない**。
セッションを開き直した瞬間、あるいは TSV に書き出した瞬間、但し書きは消え、
**残るのは数字だけ**になる。

**では何が永続しているか** — ここが設計の手本になる:

| 経路 | 何を保存するか |
|---|---|
| セッションの `image` 行 | npy は `npy3`、raw は **`raw3 <rawDtype> <interp> …`** (main.cpp:4980-4988) |
| エクスポートの出所行 | `"%dx%d %s | CFA: …"` に **`d->dtype` が載る** (main.cpp:14938 / 14943) |

**npy の `dtype` は保存されていない** — 再読込時にファイルから読み直せるからである。
**raw の `rawDtype` は保存されている** — **raw のファイルはそれを言わないからである。**

これはそのまま `values` の設計指針になる:

> **ファイルが言えることは保存しない (読み直せばよい)。
> ファイルが言えず、人が宣言したことは保存する。**

### 4.4 決定: `FrameSource::values`

`dtype` の隣に、**画素が何であるかを名乗るフィールド**を1つ置く。
`ImageDoc` にミラーし、`syncMirrors()` (main.cpp:278) で同期する。

状態は**3つだけ**:

| 値 | 意味 | analyzer |
|---|---|---|
| `dn` | 測定値。[DN] | **可** |
| `display` | 伝達関数か非可逆符号化を通った値 | **拒否** |
| `unknown` | **ファイルが何も言っていない** | **拒否** |

**なぜ `display` と `unknown` を分けるか** — 2つに畳むと画面に出す文が書けない。
人にとって次にすることが違う:

- `display`: 「この PNG は sRGB と書いてある」→ **直しようがない**。
  元の線形値はファイルに残っていない。
- `unknown`: 「この PNG は伝達関数を書いていない」→ **人が宣言すれば直る**。

**永続化は §4.3 の規則に従う**: ファイル由来の `values` は保存しない
(次回も同じチャンクを読めば同じ答えが出る)。**人が Inspector で宣言した
`values` は保存する** — `raw3` が rawDtype を保存しているのと同じ理由で、
同じ場所 (セッションの `image` 行) に。

そして**エクスポートの出所行には常に出す** (main.cpp:14938 の `dtype` の隣)。
§4.3 のとおり `note` はそこに出ないので、ここは `values` でなければならない。

### 4.5 どの形式がどの状態で入ってくるか

| 形式 | 既定 | 根拠 |
|---|---|---|
| `.npy` / `.npz` / raw | **`dn`** | **ユーザー自身の書き出し**。現状維持 (退行を作らない) |
| アダプタの返り値 | **`dn`** (既定)、`values=` で上書き可 | 同上。§6.1 |
| **EXR** | **`dn`** | 仕様が線形を規約としている。ただし**スケールは名乗らない**ので note にそう書く |
| PNG + `gAMA`=1.0 / 線形 ICC | `dn` | **ファイルが線形と言っている** |
| PNG + `sRGB` / sRGB な `iCCP` / `gAMA`≈0.4545 | `display` | **ファイルが表示参照と言っている** |
| PNG (伝達チャンク無し) | **`unknown`** | **ファイルが何も言っていない** |
| TIFF | **`unknown`** (原則) | 同上 |
| **JPEG** | **`display`、宣言でも覆せない** | 量子化とクロマサブサンプリングは宣言では戻らない |

npy と raw が `dn` なのは推測ではなく**作者性**による。あれはユーザーが自分の
パイプラインから書き出したファイルで、書いた本人が [DN] のつもりで書いている。
落ちてきた PNG にはその後ろ盾が無い。**この線引きは「よくある形式か」ではなく
「誰がその数字に責任を持っているか」で引かれている。**

JPEG の「覆せない」は、この機構に歯があることを示すために要る。
どんな宣言もクロマサブサンプリングを元に戻さない。

### 4.6 逃げ道は既に設計されている

`unknown` を「開けない」にはしない。**開いて、見せて、測定だけ断る。**
言い直す場所は既に決まっている — import-adapters.md **§3.3「Inspector で言い直す」**。
`--npy-axis` の後継として設計した仕組みがそのまま使える:

- Inspector に「今どう読まれているか」が出て、その場で言い直せる
- 言い直しは**推測ではなくユーザーの宣言**なので、以後その doc に効く
- **セッションに保存される**。次に開いても同じ
- 見えるところにあり、後から「なぜこのファイルだけ違うのか」を説明できる

つまり `values` は新しい UI を要求しない。**§3.3 の欄が1つ増えるだけ**である。

## 5. コードで守らせる (助言ではなく)

不変条件として書けるようにする:

- **`values != dn` の doc は analyzer に渡らない。** 門は analyzer の呼び出し口
  (内蔵 stats と `plugin_host` の入口) の**1か所**に置く。形式ごとに散らさない —
  散らせば次の形式で忘れる。
- **エクスポートの出所行に `values` を出す** (main.cpp:14938 の `dtype` の隣)。
- **selftest を1本足す** (E11 と同じ形):
  `display` を名乗る fixture が (a) 開けること、(b) analyzer が**理由の文つきで**
  断ること、(c) エクスポートの出所行に値が載ること、(d) Inspector の宣言が
  セッションを跨いで残ること。

**`values` は EXR より先に入れる。** EXR だけなら `dn` 一択なので門は要らなく
見えるが、門が無いまま PNG が来ると「今回だけ」で通ってしまう。
**表示参照の画素が1つも無いうちに作るのが一番安い。**

## 6. 入力アダプタとの境界

境界は「よくある形式か / 珍しい形式か」ではない。
**ファイルが自分の数値の意味を言えるかどうか**である。

| | native C++ reader | 入力アダプタ |
|---|---|---|
| 条件 | **ファイルが自分の伝達特性を名乗る** | **名乗らない** |
| 例 | EXR、`gAMA`/`sRGB` を持つ PNG | 伝達情報の無い PNG/TIFF、DPX、ベンダ独自 raw |
| 誰が意味を供給するか | ファイル自身 | **アダプタを書いた人** |

この線が正しいのは、**アダプタが「読めない形式の逃げ道」ではなく
「意味を宣言できる唯一の場所」だから**である。アダプタを書く人は、その TIFF が
ラボの線形ダンプなのか誰かの sRGB 書き出しなのかを**知っている唯一の人間**であり、
それをコードに書ける。native reader にはその知識が無い。

> **伝達情報を持たない形式を native reader で足すのは、
> 「意味を知らない読み手」を増やすことにしかならない。
> 同じ形式をアダプタで読めば、読めるうえに意味も付いてくる。**

### 6.1 アダプタ契約への提案 (import-adapters.md への追補)

import-adapters.md は settled で、別ブランチが作業中なので、
**ここでは提案として書く。あの文書はこのブランチでは触っていない。**

§4.3 のフィールド表に **`values`** を足すことを提案する:

```python
return Frame(img, values="display")   # sRGB の PNG を読んだ、と宣言する
return Stack(arr)                      # 既定は "dn" (現状の素の配列と同じ)
```

- 既定は **`dn`**。既存のアダプタと素の配列の意味を変えない (退行を作らない)。
- 取りうる値は §4.4 の3つだけ。綴り間違いは**構築した行で TypeError** になる —
  型を名乗る利点そのもの (import-adapters.md §4.10)。
- `note` ではなく専用フィールドである理由は §4.3 (note は永続しない)。

**`meta` では代用できない。** `meta` は「viewer は運ぶだけで書き換えない」
key-value の事実 (import-adapters.md §4.3.1) であって、**viewer の振る舞いを
変える権限を持たない**。analyzer を門番するなら、viewer が意味を知っている
フィールドでなければならない。

## 8. 推奨

**戦略 C。** 具体的には:

| 段 | 中身 | なぜこの順か |
|---|---|---|
| **0** | **`values` フィールド + analyzer の門 + selftest 1本** (§4.4-§5) | 表示参照の画素が1つも入っていないうちに門を作る |
| **1** | **公式 OpenEXR を FetchContent で固定 (v3.4.13)、client 限定** | 実測で建つ・BSD-3・+2.98 MiB・+20 s。serve に入れないので CI の手書き g++ 行は無傷 |
| **2** | **`Imf::setGlobalThreadCount()` を必ず呼ぶ** (§3.5.2) | 呼ばないと 3.6〜5.0 倍遅い。**呼ばなければ「OIIO の方が速い」を自分で再現することになる** |
| **3** | EXR の fixture 生成を決める (§3.6) | numpy では EXR を書けない。selftest を足す前に要る |
| **4** | **PNG/TIFF はアダプタで読む** (§6)。native には**しない** | 意味を言えない形式は、意味を言える人に読ませる |
| **5** | (必要が立証されたら) PNG native を再検討 | §9 問い 2 |

**OIIO を退ける理由を、重さ以外で言う。** OIIO の売りは形式の幅である。
ところがこの道具にとって、**その幅の大半は「読めても測ってはいけない」形式**
(JPEG、表示参照の PNG/TIFF、HEIF) で埋まっている。依存を1桁増やして得るのは
「開けるが測定は断るファイル」の集合になる。**買っているものと払っているものが
噛み合っていない。**

これは OIIO が悪いという話ではない。OIIO は VFX パイプライン
(色空間を OCIO が別に管理する世界) のために設計されていて、そこでは幅が正しく
価値になる。**OpenColorIO が必須依存になっていること自体がその証拠**である。
この repo はその世界にいない。

## 9. 自分の推奨への、いちばん強い反論2つ

**反論1: 「アダプタに送る」は、ユーザーにとって Python を書けという意味である。**

PNG を1枚見たいだけの人が、いまは `viewer file.png` で済むはずのところを、
アダプタを書くか探すかしなければならない。しかも §4.5 のとおり、伝達チャンクの
無い PNG は開いても `unknown` で測定を断られる。**「開けない」と「開くけれど
測れない」の差は、その場のユーザーには小さく感じられる。**
そしてアダプタ機構 (import-adapters.md) は**まだ実装されていない**ので、
いま戦略 C を採ると「PNG は読めません」という期間が実在する。
これは実害であり、§10 問い 2 を早く決めるべき理由でもある。

**反論2: 版を固定するものが N 個になるという戦略 B の弱点を、C は解消していない。**

C は「いまは EXR 1つだから軽い」と言っているだけで、**形式が増えたときに
重くなる構造は B と同じ**である。2年後に EXR + PNG + TIFF + DPX を native で
持つことになったら、OIIO を1つ固定するほうが4つを別々に追うより保守が楽だった、
という結論はありうる。**この判断は「native の形式は増えない」に賭けている**が、
それを保証するものは無い。ユーザーが最初に言ったのが
**「EXR, PNG, and others」**であることを考えると、この賭けは見た目より危うい。

(反論2への部分的な答えは §6 にある: アダプタがあれば形式が増えても native は
増えない。ただしそれは**アダプタが実装されていれば**の話で、いまは設計文書である。)

## 11. 測れなかったこと (と、その理由)

**数字の無い断定を置かないための一覧。**

| 測れなかったもの | 理由 |
|---|---|
| **OIIO のビルドコスト・バイナリ増・読み出し速度** | configure が3回とも通らなかった (§3.4)。1回目はこちらのパス長、2・3回目はローカル依存ビルドの `find_package` 失敗 |
| **OIIO vs OpenEXR の直接比較 = ユーザーの仮説** | 上記のため相手がいない。**片側だけの数字で勝敗を言わない**。§3.5.2 は「差を説明しうる機構」であって比較の再現ではない |
| **OIIO が MSVC / Linux なら建つかどうか** | この機械は MinGW のみ。**建たないと結論していない** — 建たなかったのは MinGW でのこと |
| **MSVC でのビルドコスト** | toolchain が MinGW。**この文書の時間は全部 MinGW のもの** |
| **CI ランナー上での増分** | ローカル 20 コアの実測しか無い。ランナーはコアが少なく、倍率を測っていない |
| **Ubuntu 20.04 コンテナに OpenEXR を入れたときの追加時間** | Windows 機で Linux コンテナを回していない。**構造上壊れる**ことは build.yml:90-108 から確実だが、秒数は不明 |
| **`viewer.exe` に実際に混ぜたときのサイズ増** | +2.98 MiB は「EXR を読むだけの exe」対「何もしない exe」の差。本体でリンカがどれだけ捨てるかは別 |
| **loadExr の実装工数** | 実装していない。§7 の「S」は media-support.md §1 の見積りの引き写し |
| **PNG デコーダを miniz の上に自作する工数** | miniz は既にリンク済みで deflate を持っているので検討はしたが、**書いていないので工数は不明**。§10 問い 2 を先送りにした理由の1つ |
| **デコード用スレッドプールと背景ローダの干渉** | §10 問い 4。EXR を実装していないので測りようがない |
| **half→float32 の正しさ** | media-support.md §1 が「情報無損失」と書いており、今回そこは再検証していない |
