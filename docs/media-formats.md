# 画像フォーマットをどう読むか — 測定に基づく判断
### (EXR / PNG / JPEG / TIFF / ベンダ RAW / EXIF)

`.npy` / `.npz` / raw の外にある画像形式を、**どの機構で読むか**を決める文書。

この文書は [docs/media-support.md](media-support.md) の §1 (OpenEXR の候補比較) を
**置き換える**。あそこの結論は tinyexr だったが、ユーザーがそれを覆して公式
OpenEXR にした ([docs/tasks.csv](tasks.csv) の「フォーマット」行がその記録)。
media-support.md の動画と click-to-open の節は生きている。

**この文書は2度書かれている。** 初版は EXR (と、ついでの PNG) だけを対象にし、
**戦略 C = 「EXR だけ native、あとはアダプタ」**を推した。そのとき自分で挙げた
最大の弱点が「**native の形式は増えない、に賭けている**」だった。
その直後に対象が広がった:

> **PNG, JPEG, TIFF も対応したい。欲を言うと主要カメラベンダの RAW ファイルや
> スマホメーカーの RAW ファイルも、exif の解析も含めて対応したい。**
> (ユーザー、2026-08-03)

**賭けは部分的に外れた。** native の形式は 1 個から 2 個に増える。
以下はその前提で測り直した結果で、**結論は変わったが、判断の軸は変わっていない** —
そして軸が同じまま結論が動いたことこそ、軸が正しいことの証拠だと考える (§7)。

**測っていないことは「測っていない」と書く** — §15 に一覧してある。

## 0. 結論を先に

1. **推奨は C から C′ へ。** native にするのは **EXR と ベンダ RAW の2つ**。
   **PNG / JPEG / TIFF は native にしない** (アダプタで読む)。
   **A (OIIO) にも B (全部を公式 lib で) にも倒れない。**
2. **いちばん意外だった測定: RAW は EXR より安い。**

   | | build | バイナリ増 |
   |---|---|---|
   | OpenEXR + Imath | +20.3 s | **+2.98 MiB** |
   | **LibRaw** | **+11.8 s** | **+0.95 MiB** |

   「ベンダ RAW は重い」という直感は、この構成では**誤り**だった。
3. **誠実さの軸が反転する。** LibRaw の `unpack()` は
   **CFA パターン・ブラックレベル・ビット深度つきの生センサ値**を返し、
   デモザイクもホワイトバランスもガンマもかからない。
   一方 PNG/JPEG/TIFF は伝達特性を名乗らない。
   **RAW のほうが PNG より native にする資格がある。**
3b. **【第2改訂での訂正】ただし「ベンダ RAW = `dn`」は誤りだった。**
   ユーザーの指摘 (「新しめの RAW 圧縮フォーマット…コーデックが自明じゃない」)
   は正しく、**最初の5枚のうち2枚が非可逆圧縮**だった (Nikon 1 AW1 と
   Sony HX95)。非可逆 RAW は**綺麗に開き、完璧に見え、センサのカウントではない**。
   `values` は圧縮方式で決める — **可逆なら `dn`、非可逆なら `display`、
   判定できなければ `unknown`**。詳細と実測は **§4.8**。
3c. **【ウェーブレットについて】** 「Canon も Sony もウェーブレットの
   コーデックがあるが LibRaw は対応しているか」という問いへの答え:
   **Canon CRX はウェーブレットで、LibRaw は可逆・非可逆とも復号する**
   (ソースに `CrxWaveletTransform` / `crxIdwt` があり、実ファイルで確認)。
   **Sony には stills のウェーブレットコーデックが無い** —
   非可逆は 11bit デルタ、可逆はロスレス JPEG (予測) である。
   **そして「ウェーブレットか」は仕分けの軸にならない**:
   同じ CRX が可逆にも非可逆にもなり、非ウェーブレットの ARW2 は非可逆である。
   **仕分けるのは変換の種類ではなく、数が生き残ったかどうか。** → **§4.9**
3d. **復号できない形式は綺麗に落ちる (実測)。** Nikon Z 8 の HE / HE* で確認:
   `open_file()` は成功、**`get_decoder_info()` が復号前に
   `UNSUPPORTED_FORMAT` を立て**、`unpack()` は
   `"Unsupported file format or not RAW file"` で失敗し、**画素は返らない**。
   壊れた数字が測定値として出る経路は無い。
4. **「OIIO なら RAW もタダで付いてくる」は誤り。** OIIO は RAW を
   **LibRaw で読んでいる**。EXR を OpenEXR で読んでいるのと同じ構図で、
   OIIO は薄い皮であって、依存も義務も消えない。むしろ OIIO 経由だと
   LibRaw の版を OIIO が選ぶ。
5. **ライセンスが初めて本当の争点になる。** LibRaw は **LGPL-2.1 または
   CDDL-1.0 の二者択一**。exiv2 は **GPL** で、静的リンクすればバイナリ全体に
   伝染する。そして **この repo には LICENSE ファイルが1つも無い**のに
   CI がバイナリを自動公開している (§10)。
6. **EXIF は `conditions` の材料になるが、自動では入れない。**
   実測で **Olympus は aperture=0 / focal_len=0 を返した** — 欠けている値が
   0 として来る。正典の「読めなければ**未設定**、0 ではない」がそのまま効く (§9)。

## 4. ベンダ RAW の測定 (新規)

### 4.1 LibRaw は CMake を持っていない

これが最初に分かったことで、判断に直結する。

```
$ ls _deps/libraw-src/CMakeLists.txt
(無い)

$ cat _deps/libraw-src/README.cmake
Due to inability to support (user contributed) Cmake scripts,
the cmake builds are not officially supported by LibRaw team
since October 23, 2014
The scripts are moved to separate github repository
github.com:LibRaw/LibRaw-cmake.git
```

あるのは autotools (`configure.ac` / `Makefile.am`) と、
手書きの `Makefile.mingw` / `Makefile.msvc` / `LibRaw.sln` / `LibRaw.pro`。

したがって **`FetchContent_MakeAvailable(LibRaw)` は使えない。** 選択肢は3つ:

| 案 | 評価 |
|---|---|
| (a) `LibRaw-cmake` を**別リポジトリとして**追加で取得 | 非公式・別バージョン管理。固定するものが2つに増え、片方は上流が保証しない |
| (b) **ソースを直に並べて自分のターゲットに混ぜる** | **この repo が imgui にやっていること**そのもの (CMakeLists.txt:45-51) |
| (c) vcpkg / システムパッケージ | README:27 の「事前準備は不要」を破る |

**(b) を試した。動く。** 以下はその測定。

### 4.3 ただし「直に並べる」には既知の罠が2つある (どちらも実測)

**これは LibRaw が CMake を持たないことの具体的な代価**であり、
採用するなら CMakeLists にコメントとして残すべきものである。

| 罠 | 症状 | 対処 |
|---|---|---|
| `*_ph.cpp` は**プレースホルダ**で、実体版と**同じシンボルを定義する**。上流の Makefile はどちらか一方しか使わない | 素直に glob すると `multiple definition of LibRaw::fuji_rotate()` など **4 件**でリンク失敗 | `list(FILTER ... EXCLUDE REGEX "_ph\\.cpp$")` |

上流がファイルを動かすたびに、この知識を**持ち主が学び直す**ことになる。

> **拡張子とヘッダ項目だけを見ていては絶対に分からない**。
> 初版はこの 5 枚を「ベンダ RAW は `dn` を名乗れる」証拠として提出した。
> **その提出は誤りである。** 正しい結論は §4.8 にある。

### 4.7 正直に言うべき欠け — ブラックレベルは常に信用できるわけではない

**Nikon NEF はブラックレベル 0 を返した**が、先頭の生値は 80〜306 ある。
12bit センサでペデスタルが本当に 0 な可能性は低い。
LibRaw はベンダによってブラックをマスク領域から計算したり、
`cblack[]` の別の位置 (4 以降の 2×2 パターン) に置いたりする。
この probe は `cblack[0..3]` しか見ていない。

**含意は設計に直結する**:

> **ブラックレベルは「ファイルが言った値」として表示し、
> 引き算を黙って適用しない。** 5 件中 1 件で 0 が返った以上、
> 「LibRaw がブラックを言うから安心」とは書けない。

これは正典と同じ姿勢である — 単位を仮定しないのと同じ理由で、
**ペデスタルも仮定しない**。Inspector に出して、人が確認する。

**そして §4.8 を読むと、この 0 が返った1件が非可逆圧縮の1件と
同じファイルだったことが分かる。** 疑わしい兆候は、たいてい1つではない。

## 4.8 圧縮 — 「RAW」は1つの種類ではない (この改訂の中心)

ユーザーの問い (2026-08-03):

> **新しめの RAW 圧縮フォーマットって、対応できるのかしら？
> コーデックが自明じゃない気がしますが。**

**正しい。** そして初版の C′ はこの3つを1つとして扱っていた:

| 場合 | 何が起きるか | `values` |
|---|---|---|
| **1. 可逆で復号できる** | センサのカウントがそのまま出る | **`dn` を名乗ってよい** |
| **2. 非可逆だが復号できる** | **綺麗に開き、完璧に見え、数はセンサのカウントではない** | **`dn` を名乗ってはならない** |
| **3. 復号できない** | 開けない | 開けない理由を**コーデック名で**言う |

**危険なのは 2 である。** 1 と 3 は自明に振る舞う。2 は**黙って嘘をつく** —
これは動画の調査が測ったのと同じ失敗 (既知の σ_t = 40 DN16 が 0.00 として
到着する) が、`.CR3` や `.NEF` の拡張子を着て来るということである。

### 4.8.1 LibRaw は、どの場合かを教えてくれるか — 実測

**`get_decoder_info()` は `open_file()` の後・`unpack()` の前に呼べる**
(`load_raw` は open で束縛される)。つまり**1画素も復号せずに問える**。
持っている5枚 + 追加で取得した Nikon Z 8 の3枚で実測した:

| ファイル | `decoder_name` | flags | 判定できたか |
|---|---|---|---|
| Apple DNG | `lossless_dng_load_raw()` | 0x00010250 | **可逆** (名前が言っている) |
| Canon CR3 | `crxLoadRaw()` | 0x00000000 | **名前は何も言わない** → 下記 |
| **Nikon 1 AW1** | `nikon_load_raw()` | 0x00010050 | **`NEFCompression = 4` = 非可逆(type 2)** |
| **Sony HX95** | **`sony_arw2_load_raw()`** | 0x00010070 **SONYARW2** | **非可逆** (11bit デルタ) |
| Olympus E-M5 III | `olympus_load_raw()` | 0x00010040 | **何も言わない** |
| **Nikon Z 8 lossless** | `nikon_load_raw()` | 0x00010050 | **`NEFCompression = 3` = 可逆** |
| **Nikon Z 8 HE** | **`nikon_he_load_raw()`** | **0x00004000** | **`UNSUPPORTED_FORMAT`**、`NEFCompression = 13` |
| **Nikon Z 8 HE\*** | **`nikon_he_load_raw()`** | **0x00004000** | **`UNSUPPORTED_FORMAT`**、`NEFCompression = 14` |

**Canon は decoder 名では分からないが、別の場所が言う** —
`imgdata.makernotes.canon.Quality` (libraw_types.h に列挙のコメントがある):

```
-1 = n/a  1 = Economy  2 = Normal  3 = Fine  4 = RAW  5 = Superfine
 7 = CRAW            <- Canon C-RAW = 非可逆
130/131 = CRM (動画)
```

実測した CR3 は **`Quality = 4`** — すなわち可逆。
**そして C-RAW の実ファイルで `Quality = 7` が立つことを後に確認した (§4.9.3)。**
同一機種の可逆／非可逆の対で、**`decoder_name` と `decoder_flags` は完全に同一**、
`Quality` だけが 4 と 7 に分かれた。

同じ構造体に **`CanonLog`** もある (`0 = off`、それ以外は log カーブが
焼き込まれている)。実測は全て 0 だったが、**0 以外なら線形ではない**。

### 4.8.2 まとめ: ベンダごとに「言う / 言わない」が違う

| ベンダ | 可逆/非可逆を復号前に判定できるか | 何を見るか |
|---|---|---|
| **Nikon** | **できる** | `makernotes.nikon.NEFCompression` (1,4=非可逆 / 3=可逆 / 13,14=HE) |
| **Sony** | **できる** | `decoder_name == sony_arw2_load_raw()` / `LIBRAW_DECODER_SONYARW2` |
| **DNG** | **できる** | `lossy_dng_load_raw()` と `lossless_dng_load_raw()` が別の名前 |
| **Canon** | **できる (ただし別経路)** | `makernotes.canon.Quality`。**7 = CRAW = 非可逆、4 = 可逆**。decoder 名は**両方 `crxLoadRaw()` で完全に同一** — §4.9.3 で実測確認 |
| **Olympus** | **できない** | `olympus_load_raw()` は何も言わない |
| **Fuji / Panasonic / その他** | **未確認** | サンプルを持っていない |

**実測に使ったファイル (計 10 枚、すべて raw.pixls.us の CC0)**:
Apple DNG / Canon EOS M200 CR3 / Nikon 1 AW1 NEF / Sony DSC-HX95 ARW /
Olympus E-M5 III ORF / Nikon Z 8 (lossless・HE・HE\* の3枚) /
**Canon EOS R5 II (RAW と CRAW の対)** / **Sony ILCE-1 (compressed)**。
**このうち非可逆は 5 枚** — Nikon 1、Sony HX95、Canon C-RAW、Sony α1、
そして復号できない Nikon HE/HE\* を除いた集計である。
**半分が非可逆だった**という事実そのものが、この判定を入れる理由になっている。

> **したがって答えは「ときどき」である。**
> そして**「ときどき」は `dn` を既定にしてよい理由にならない。**

### 4.8.3 復号できないとき、LibRaw は何をするか — 実測

**恐れていたのは「成功したふりをして壊れた画素を返す」こと。** 実測ではそうならない:

| 段階 | Nikon Z 8 HE / HE* での実測 |
|---|---|
| `open_file()` | **成功する**。メタデータは読める (機種名・`NEFCompression`=13/14) |
| `get_decoder_info()` | `nikon_he_load_raw()` / flags **`0x4000 = LIBRAW_DECODER_UNSUPPORTED_FORMAT`** |
| `unpack()` | **失敗する。** `LIBRAW_FILE_UNSUPPORTED` = `"Unsupported file format or not RAW file"` |
| 画素 | **返らない。** 部分データも壊れたデータも出てこない |

**これは良い知らせである。** 場合 3 は
**(a) 復号前に旗で分かり、(b) 復号しても綺麗に落ちる**。
壊れた数字が測定値として画面に出る経路は、少なくとも HE/HE* については無い。

同じ形の「復号器はあるが中身が無い」プレースホルダが他にもあり、
どれも `LIBRAW_EXCEPTION_UNSUPPORTED_FORMAT` を投げる (ソースで確認):

| プレースホルダ | 何が要るか | 出典 |
|---|---|---|
| `jxl_dng_load_raw_placeholder()` | **Adobe DNG SDK** (`#ifndef USE_DNGSDK` で UNSUPPORTED になる) | `src/decoders/dng.cpp:29-32`、`src/utils/decoder_info.cpp:51-57` |
| `vc5_dng_load_raw_placeholder()` | **GPR SDK** (GoPro VC-5) | `src/decoders/dng.cpp:22-27` |

### 4.8.4 何を確認できて、何を確認できなかったか

**確認できたこと**:

- **LibRaw 0.22.2 は Nikon HE/HE* を復号しない** — 実測 (上の表) に加え、
  同梱の対応機種表が**自分でそう書いている**:
  `src/tables/cameralist.cpp:740-747` に
  `"Nikon Z 8 (HE/HE* formats are not supported yet)"` (Z 6III / Z 9 / Z f も同文)。
- **DNG 1.7 の JPEG-XL は「libjxl を繋ぐ」話ではない。**
  LibRaw の公式ダウンロードページが
  **"DNG 1.7 (including JPEG-XL compression) support via Adobe DNG SDK 1.7.x integration"**
  と書いている。**必要なのは Adobe の DNG SDK** であって libjxl ではない。
- LibRaw 0.21.0 の変更点は HE について
  **"read NEFCompression tag for HE/HE* files"** — **タグを読むだけ**で復号ではない。

**確認できなかったこと** (指示は「私の言を鵜呑みにせず検証せよ」だった):

- **HE/HE* が intoPIX TicoRAW であるかどうか。**
  LibRaw のソースにも配布ページにも **`tico` / `intoPIX` の語は1つも無い**。
- **それが商用アドオンとして売られているかどうか。**
  libraw.org は LGPL/CDDL と "Extended Support" に触れるが、
  **コーデック追加パックの記述は見当たらなかった**。

> **したがって「HE は TicoRAW の商用ライセンス待ちだ」とは書かない。**
> 書けるのは「**LibRaw 0.22.2 は復号しない。上流は "not supported yet" と
> 書いており、時期も理由も述べていない**」までである。
> ただし §13 の反論1は**それでも成立する** — 理由が何であれ、
> **JPEG-XL DNG は Adobe DNG SDK、VC-5 は GPR SDK という
> 「別 SDK を抱えないと開かない」形式が現に存在する**からで、
> こちらは確認済みである。

### 4.8.5 断り方の文面 (場合 3)

「サポートされていないファイル」では何も言っていない。
**コーデックを名指しし、なぜ開けないかを言う。** 復号前に旗が立つので、
`unpack()` を試す前にこれが出せる:

```
Nikon_Z8_high_efficiency.NEF は開けません
  圧縮方式: Nikon High Efficiency (HE)   [NEFCompression = 13]
  この viewer が組み込んでいる LibRaw 0.22.2 は HE / HE* を復号しません
  (上流の対応機種表が "not supported yet" と明記しています)
  [ reader を選ぶ... ]        <- アダプタへ (§7.1)
```

```
shot_0042.dng は開けません
  圧縮方式: JPEG-XL (DNG 1.7)
  復号には Adobe DNG SDK が要り、このビルドには入っていません
  [ reader を選ぶ... ]
```

正典の言い方 ([input-adapters.md](input-adapters.md) §3.2
「黙って諦めない。**形と、次にすることを言う**」) をそのまま踏襲している。

### 4.8.6 これは RAW 固有の話ではなかった — EXR にも同じ穴がある

`media-openexr` ブランチ (この判断と並行して EXR を実装している) が
**同じ問題を EXR 側で独立に踏んだ**。V23h の測定 (319f0ea):

> ZIP / PIZ / RLE / ZIPS は**可逆** → 平文ファイルと**厳密一致**を assert できた。
> **DWAB は非可逆** → 「開けること」と「12.5 に対して ±0.5 に収まること」しか
> assert していない。**非可逆コーデックに厳密性を主張するのは、
> このローダが拒否するために存在する種類の静かな嘘になる。**

**つまり `values` を決める規則は、器と圧縮の2段で考えるべきものだった**:

| 問い | 答えるもの |
|---|---|
| **1. 器は線形だと言っているか** | 形式の仕様 (EXR: 言う / PNG: チャンク次第 / RAW: センサ値) |
| **2. その数は可逆に運ばれてきたか** | **コーデック** (EXR: `header().compression()` / RAW: §4.8.2) |

**両方が yes のときだけ `dn`。** どちらかが no なら `display`、
分からなければ `unknown`。

**これは規則を単純にする発見である。** RAW のために特別扱いを足すのではなく、
**同じ2つの問いを全形式に当てる**。そして EXR 側は `header().compression()` を
読むだけなので、判定は RAW より簡単である。

## 4.9 ウェーブレットの話 — 質問の軸と、答えるべき軸がずれている

ユーザーの問い (2026-08-03):

> **キャノンもソニーもウェーブレットなコーデックあったけど、
> あっちは libraw で対応してるの？**

### 4.9.1 まず直接の答え

| | ウェーブレットか | LibRaw 0.22.2 は復号するか |
|---|---|---|
| **Canon CRX** (CR3、可逆・C-RAW とも) | **はい** | **する。両方とも。** 実ファイルで確認 |
| **Sony (stills)** | **いいえ。ウェーブレットのコーデックは無い** | する (ウェーブレットではないから) |

**Canon はウェーブレットで、LibRaw は復号する。**
ソースに逆離散ウェーブレット変換がそのまま入っている
(`src/decoders/crx.cpp`):

```
struct CrxWaveletTransform { int32_t *subband0Buf … *subband3Buf; … };
struct CrxSubband { … };
crxIdwt…()                     // 逆 DWT
int16_t subbandWidth / subbandHeight;  uint8_t subbandCount;
```

**Sony には stills のウェーブレットコーデックが無い。**
LibRaw が持つ Sony の復号器は次の6つで全部であり、
**ウェーブレットに当たるものは無い** (Sony の経路に `wavelet` / `idwt` /
`subband` の語は1つも出てこない):

```
sony_load_raw   sony_arw_load_raw   sony_arw2_load_raw
sony_arq_load_raw   sony_ljpeg_load_raw   sony_ycbcr_load_raw
```

- **`sony_arw2_load_raw`** = **11bit のデルタ + コンパンディング**。**非可逆**。
  ウェーブレットではない。
- **`sony_ljpeg_load_raw`** = **ロスレス JPEG (予測符号化)**。可逆。
  これがいわゆる「ロスレス圧縮」機の経路で、やはりウェーブレットではない。

> **つまり質問の前提は半分だけ当たっている。**
> Canon にはウェーブレットがあり、Sony には無い。
> **そして「ウェーブレットかどうか」は、この道具にとって重要な軸ではない。**

### 4.9.2 なぜウェーブレットは軸にならないか — 2×2 が全部埋まる

**ウェーブレットかどうかと、可逆かどうかは独立である。**
実例を当てはめると4象限すべてに住人がいる:

| | **可逆 (`dn` を名乗れる)** | **非可逆 (`display`)** |
|---|---|---|
| **ウェーブレット** | **Canon CRX lossless** (`Quality=4`) | **Canon C-RAW** (`Quality=7`)、GoPro VC-5 |
| **非ウェーブレット** | Sony ロスレス圧縮 (予測)、`NEFCompression=3`、lossless DNG | **Sony ARW2** (11bit デルタ)、`NEFCompression=1,4`、lossy DNG、**EXR DWAB** |

**同じ CRX が、可逆にも非可逆にもなる。**
Canon はウェーブレットのまま可逆と非可逆を切り替えており、
**変換の種類を見ても答えは出ない**。

> **形式を「変換の種類」で仕分けてはならない。
> 仕分けるべきは「その数が生き残ったかどうか」である。**

これは次に読む人のために書いている。ウェーブレットという語は強い印象を
与えるので (「JPEG のような非可逆」と結びつけたくなる)、
**そこで仕分けると Canon の可逆 CRX を不当に `display` に落とし、
Sony ARW2 の非可逆を見逃す** — ちょうど逆を2回間違えることになる。

### 4.9.3 Canon C-RAW を実ファイルで確認した (前回の宿題)

前回の版はここを **「機構はあるが証拠が無い」**として §15 に挙げていた
(`Quality = 7` が実際に立つのを見ていなかった)。**閉じた。**

raw.pixls.us の **同一機種・同一場面の対** (`Canon EOS R5m2`) を使った:

| | `RAW.CR3` | `CRAW.CR3` |
|---|---|---|
| ファイルサイズ | **54,439,072 B** | **27,527,840 B** (約 1/2) |
| `decoder_name` | `crxLoadRaw()` | **`crxLoadRaw()` — 同一** |
| `decoder_flags` | 0x00000000 | **0x00000000 — 同一** |
| **`canon.Quality`** | **4 (RAW = 可逆)** | **7 (CRAW = 非可逆)** |
| `CanonLog` | 0 | 0 |
| raw 寸法 | 8480×5650 (可視 8222×5488) | 同一 |
| black / maximum | 512 / 16383 | 同一 |
| `unpack()` | 400.9 ms | 395.6 ms |

**結論**:

- **`Quality = 7` は実在し、実際に立つ。** 判定機構は動く。
- **`decoder_name` と `decoder_flags` は両者で完全に同一。**
  §4.8.2 で「Canon は decoder 名では分からない」と書いたのは正しかった —
  **今回それが実測で確認された**。`canon.Quality` を見なければ区別できない。
- **サイズ以外、外形はすべて同じ。** 寸法も黒レベルも最大値も復号時間もほぼ同じで、
  **開いた画像を見ても非可逆だと気づく手がかりは無い**。
  §4.8 が「危険なのは 2 (非可逆だが復号できる)」と言ったのはこのことである。

### 4.9.4 Sony の現行機も確認した — 「compressed」は非可逆だった

`Sony ILCE-1` (α1、フラッグシップ) の `A1_full_compressed.ARW` (63,216,896 B):

```
decoder_name  : sony_arw2_load_raw()
decoder_flags : 0x00010070   <- SONYARW2 (非可逆 11bit デルタ)
```

**現行フラッグシップの「圧縮」設定が、そのまま非可逆の経路に入る。**
Sony 機は「非圧縮 / ロスレス圧縮 / 圧縮」を選べ、
**最後のものは名前のとおり非可逆**である。
ウェーブレットではないが**非可逆**であり、`values=display` に落ちる。

### 4.9.5 LibRaw が復号しないコーデック (ウェーブレット系を含む全一覧)

**「ベンダ RAW を native 対応する」と言えるかを決めるのはこの表である。**
すべて 0.22.2 のソースで確認した:

| コーデック | 変換 | LibRaw 0.22.2 | 必要なもの | 確認方法 |
|---|---|---|---|---|
| **Nikon HE / HE\*** | 非公開 (推定ウェーブレット系。**未確認**) | **復号しない** | 不明。上流は "not supported yet" とだけ | **実ファイルで復号を試みて確認** |
| **GoPro VC-5** | **ウェーブレット** (CineForm 系) | **復号しない** | **GPR SDK** (`USE_GPRSDK`) | ソース (`dng.cpp:21`、`dngsdk_glue.cpp`) |
| **JPEG 2000 (CinemaDNG)** | **ウェーブレット** | **復号しない。復号器が存在しない** | — | ソース: 例外コード `LIBRAW_EXCEPTION_DECODE_JPEG2000` は**定義だけあって投げる箇所が無い**。jasper / openjpeg への参照も 0.22.2 には無い |
| **JPEG-XL (DNG 1.7)** | DCT / modular (**ウェーブレットとは呼ばない**) | **復号しない** | **Adobe DNG SDK** (`USE_DNGSDK`) | ソース + LibRaw 公式ページ |
| Canon CRM (Cinema RAW Light) | — | **stills の経路に復号器は無い** | — | ソース: `Quality` の列挙に 130/131 として**名前があるだけ**。`.CRM` ファイルは**試していない** |

**この表の意味**: 「主要カメラベンダの RAW に対応したい」に対して、
**Canon / Sony / Olympus / Apple / 大半の Nikon は対応できる**。
穴は **Nikon の HE/HE\*** (現行 Z 機の主力設定) と、
**別 SDK を要する VC-5 / JPEG-XL DNG**、そして **CinemaDNG の J2K** である。

## 5. OIIO 再訪 — 「RAW もタダで付く」は誤り

初版の測定 (3回・合計 211.8 s の configure、一度も build に到達せず) は
そのまま有効。依存の連鎖は実測でこうだった:

```
ZLIB 1.3.1 → Imath 3.1.10 → OpenEXR 3.3.5 → libjpeg-turbo 3.1.2
           → pystring 1.2.0 → expat 2.6.3 → yaml-cpp 0.8.0 → (失敗)
```

失敗箇所は `build_OpenColorIO.cmake:29`。**OpenColorIO が必須依存**である。

今回のスコープで新たに重要なのは:

- **OIIO は EXR を OpenEXR で読む** (上の連鎖に OpenEXR 3.3.5 が居る)。
- **OIIO は RAW を LibRaw で読む。** 同じ構図。
- したがって **「OIIO にすれば RAW も EXR もタダで付いてくる」は成立しない。**
  付いてくるのは**同じ依存 + OIIO 自身 + OCIO 一式**であり、
  **LGPL/CDDL の義務も消えない** (むしろ LibRaw の版を OIIO が選ぶ)。

**OIIO の正味の付加価値は「1つの API」と「PNG/JPEG/TIFF/HEIF などの幅」**である。
そして §7 のとおり、**その幅の大半はこの道具が測定値として扱えない形式**である。

## 6. `values` — 画素が何であるかを名乗らせる

初版で決めた仕組み。スコープが広がったことで**より効くようになった**。

### 6.1 なぜ `note` では足りないか (実測)

`ImageDoc::note` の読み手は **Inspector 1か所 (main.cpp:11548) と selftest だけ**。
**セッションに保存されず、エクスポートにも出ない。**

永続しているものと対比すると設計指針が出る:

| 経路 | 何を保存するか |
|---|---|
| セッションの `image` 行 | npy は `npy3`、raw は **`raw3 <rawDtype> <interp> …`** (main.cpp:4980-4988) |
| エクスポートの出所行 | **`d->dtype` が載る** (main.cpp:14938 / 14943) |

**npy の dtype は保存されない** (ファイルから読み直せる)。
**raw の rawDtype は保存される** (ファイルが言わないから)。

> **ファイルが言えることは保存しない。ファイルが言えず人が宣言したことは保存する。**

### 6.2 3つの状態

| 値 | 意味 | analyzer |
|---|---|---|
| `dn` | 測定値。[DN] | **可** |
| `display` | 伝達関数か非可逆符号化を通った値 | **拒否** |
| `unknown` | **ファイルが何も言っていない** | **拒否** |

`display` と `unknown` を分けるのは、**人にとって次にすることが違う**から:
`display` は直しようがない (元の線形値が残っていない)。
`unknown` は**人が宣言すれば直る**。

### 6.3 形式ごとの既定 — 新スコープ版

| 形式 | 既定 | 根拠 |
|---|---|---|
| `.npy` / `.npz` / raw | **`dn`** | ユーザー自身の書き出し |
| **ベンダ RAW — 可逆と判定できたもの** | **`dn`** | §4.8.2 で可逆と分かる場合のみ。例: `NEFCompression=3`、`lossless_dng_load_raw()`、`canon.Quality=4` |
| **ベンダ RAW — 非可逆と判定できたもの** | **`display`** | §4.8。綺麗に開くが**センサのカウントではない**。`sony_arw2_load_raw()`、`NEFCompression=1,4`、`canon.Quality=7`、`lossy_dng_load_raw()` |
| **ベンダ RAW — 圧縮が判定できないもの** | **`unknown`** | **Olympus など。API が何も言わない** (§4.8.2)。**`dn` に倒さない** |
| **ベンダ RAW — 復号できないもの** | (開かない) | HE/HE*、JPEG-XL DNG、VC-5。**コーデック名を出して断る** (§4.8.5) |
| **EXR (NONE/ZIP/ZIPS/PIZ/RLE)** | **`dn`** | 仕様が線形を規約とし、**圧縮も可逆**。スケールは名乗らないので note に書く |
| **EXR (DWAA / DWAB)** | **`display`** | **DWA は非可逆。** `media-openexr` ブランチの V23h が実測で確認した (可逆4方式は厳密一致、**DWAB だけ 12.5 に対して ±0.5 内としか主張できない**)。**圧縮の問題は RAW 固有ではない** |
| PNG + `gAMA`=1.0 / 線形 ICC | `dn` | ファイルが線形と言っている |
| PNG + `sRGB` / sRGB な `iCCP` / `gAMA`≈0.4545 | `display` | ファイルが表示参照と言っている |
| PNG (伝達チャンク無し) | **`unknown`** | ファイルが何も言っていない |
| **TIFF** | **`unknown`** (原則) | 伝達タグが事実上無い。**ただし科学用 TIFF は実際には線形 DN のことが多い** → §8.2 |
| **JPEG** | **`display`、宣言でも覆せない** | DCT 量子化 + クロマサブサンプリングは宣言では戻らない |

**この表が今回の改訂の要点である。** 「珍しい形式」であるベンダ RAW が `dn` で、
「ありふれた形式」である PNG/JPEG が `display`/`unknown` になる。
**誠実さの順序は、普及度の順序と逆を向いている。**

### 6.4 コードで守らせる

- **`values != dn` の doc は analyzer に渡らない。** 門は analyzer の呼び出し口
  (内蔵 stats と `plugin_host` の入口) の**1か所**に置く。
- **エクスポートの出所行に `values` を出す** (main.cpp:14938 の `dtype` の隣)。
- **selftest を1本足す** (既存の E11 が montage の `NOT DN` を assert しているのと同じ形):
  `display` の fixture が (a) 開ける、(b) analyzer が理由つきで断る、
  (c) 出所行に載る、(d) 人の宣言がセッションを跨いで残る。
- 言い直しの UI は既存設計を使う — [input-adapters.md](input-adapters.md) §3.3
  「Inspector で言い直す」に欄が1つ増えるだけ。

**`values` は EXR / RAW より先に入れる。** 門が無いまま形式が増えると
「今回だけ」で通ってしまう。

## 7. 誠実さの軸で形式を並べ直す

初版で立てた軸は**「ファイルが自分の数値の意味を言えるか」**だった。
スコープが広がっても軸は変えていない。**当てはめ直すとこうなる:**

| 形式 | ファイルは何を言うか | 判定 |
|---|---|---|
| **ベンダ RAW (可逆と判定できるもの)** | **CFA・ブラック・ビット深度・露光・ISO・そして圧縮方式を言う** | **native の資格がある** |
| **ベンダ RAW (非可逆と判定できるもの)** | **同上 + 「非可逆だ」とも言う** | **native で開いてよい。ただし `display`** |
| **ベンダ RAW (圧縮を言わないもの)** | 器のことは言うが**圧縮を言わない** | **開くが `unknown`** |
| **EXR** | 線形を規約として言う (スケールは言わない) | **native の資格がある** |
| PNG | チャンクが**あれば**言う。無ければ何も言わない | 条件つき |
| TIFF | 事実上言わない | **言えない** |
| JPEG | 表示参照であることだけは確実 | **測定値ではない** |

**軸は変えていないのに、結論の形式リストが変わった。**
それは軸が形式の流行ではなく**ファイルの性質**を見ているからで、
新しい形式を足したときに自動的に正しい側へ落ちる。
初版で「native は増えない」に賭けたのは間違いだったが、
**軸そのものは賭けではなかった。**

### 7.0 ただし、軸の当て方が甘かった

**この改訂で分かったのは、軸ではなく軸の当て方の誤りである。**
初版は「ファイルが CFA とブラックとビット深度を言う」ことを見て
**「だから数値の意味を言っている」と結論した。** 違う。
あれが言っているのは**器の形**であって、**中身がどう作られたか**ではない。

> **「ファイルが自分の数値の意味を言えるか」は、
> 「どんな器に入っているか」ではなく
> 「その数がどうやって作られたか」を問わなければならない。**

非可逆圧縮はまさに「どうやって作られたか」の側にあり、
初版の当て方はそこを見ていなかった。**軸は生き残ったが、
5 枚のサンプルでは軸を正しく当てられたことの証明にならなかった。**

### 7.1 アダプタの役割も、それに合わせて言い直す

初版はアダプタを「**読めない形式のためのもの**」と書いた。
新スコープではもっと正確にこう言える:

> **アダプタは「数値の意味を人が説明しないと決まらないもの」のためのもの。**

- 伝達情報の無い PNG/TIFF → **意味を人が言う必要がある** → アダプタ
- LibRaw がまだ知らない新機種 → **読み方を人が持ってくる必要がある** → アダプタ
- ベンダ RAW / EXR → **ファイルが自分で言う** → native

この言い直しは、**native とアダプタが競合ではなく補完である**ことを
はっきりさせる。LibRaw の版が古くなったときの逃げ道が
アダプタ (`rawpy` 等) である、という関係は §13 の反論1への部分的な答えでもある。

## 8. 推奨 — C′

### 8.0 圧縮の件で C′ は変わるか — **狭まるが、生き残る**

**生き残らない形**: 「ベンダ RAW を native にする」。
**生き残る形**: **「圧縮方式を判定できたベンダ RAW を native にする」**。

正確には、C′ は「native かどうか」の1軸だったものが2軸になる:

| | 開くか | `values` |
|---|---|---|
| 可逆と判定できた | **開く** | `dn` |
| 非可逆と判定できた | **開く** | **`display`** (見るのは自由、測定は断る) |
| 圧縮を判定できない | **開く** | **`unknown`** (同上。人が宣言すれば測れる) |
| 復号できない | **開かない** | コーデック名を言って断る |

**「native = 測定に使える」ではなくなった。**
native は「**C++ が画素を取り出せる**」という意味に狭まり、
「**その数が測定値か**」は `values` が別に答える。
初版はこの2つを暗黙に同一視していて、それが §4.5 の誤りの温床だった。

**この分離のおかげで、要望には応えられる**: 非可逆 RAW も HE でない限り開いて
見られる。**断るのは測定だけ**である。

| 段 | 中身 | 根拠 |
|---|---|---|
| **0** | **`values` + analyzer の門 + selftest 1本** | §6。形式が増える前に門を作る |
| **0.5** | **LICENSE と THIRD-PARTY-NOTICES を置く** | §10。**RAW より前**。今は LICENSE 無しでバイナリを自動公開している |
| **1** | **公式 OpenEXR (v3.4.13)、client 限定、`setGlobalThreadCount()` 必須** | §3。+20.3 s / +2.98 MiB / BSD-3 |
| **2** | **LibRaw (0.22.2) をソース直コンパイル、client 限定、CDDL を選択。**ただし**圧縮の判定を loadRaw の一部として実装する** (§4.8.2)。判定できなければ `unknown` | §4。+11.8 s / +0.95 MiB |
| **2.5** | **復号できないコーデックを、コーデック名を出して断る** (§4.8.5) | §4.8.3。旗は復号前に立つ |
| **3** | RAW の EXIF を `meta` に載せる。`conditions` は**提案まで** | §9 |
| **4** | **PNG / JPEG / TIFF はアダプタ** | §7 |
| **5** | (要望が続くなら) **TIFF → PNG → JPEG** の順で native 化を再検討 | §8.2 |

### 8.2 PNG/JPEG/TIFF を native にしない、ただし優先順位はつけておく

3つは同じではない。**要望が強ければ、この順で足すべきである**:

1. **TIFF がいちばん資格がある。** 科学用・マシンビジョンの 16bit / float TIFF は
   実際には線形 DN であることが多い。`unknown` で開いて人が1度宣言すれば
   (§6.2)、以後は測定に使える。**「開くが測れない」ではなく
   「開いて、1度宣言すれば測れる」**になる形式。
2. **PNG は次。** 16bit PNG は同様に使えるが、TIFF ほど計測系で使われない。
   なお **PNG の読みは miniz (既にリンク済み) の上に書ける可能性がある** —
   deflate は既にあり、必要なのはチャンク解析と5種のフィルタと Adam7。
   EXR と違って PIZ/DWA に相当する広がりが無い。**ただし工数は測っていない。**
3. **JPEG は最後、かつ「見るだけ」と割り切る。** §6.3 のとおり測定値には
   ならない。測れない形式のために依存を足す価値は最も低い。

### 8.3 なぜ A (OIIO) でも B (全部公式 lib) でもないか

- **A**: FetchContent で建たない (§5)。しかも **RAW も EXR も結局 LibRaw と
  OpenEXR** なので、依存も義務も減らない。増えるのは OCIO 一式と OIIO 自身。
- **B**: 「形式ごとに公式 lib」は、native 集合が **EXR + RAW の2つ**である限り
  **C′ と実質同じもの**である。両者が分岐するのは PNG/JPEG/TIFF を足すかどうかで、
  そこは §7 の軸が「足さない」と答えている。
  **つまり B は C′ の上位互換ではなく、C′ が B の必要な部分集合である。**

## 9. EXIF — `conditions` の材料になるが、自動では入れない

[input-adapters.md](input-adapters.md) §4.3.2 / §4.5 が settled にしたこと:
**series は振った条件を `Values(values, name, unit)` で持ち、単位は必須。**
露光・ISO・絞りはまさにそれで、しかも**単位はファイルが言う**。

### 9.1 実測で得られた EXIF (LibRaw 経由、追加ライブラリなし)

| 機種 | shutter [s] | aperture | ISO | focal [mm] | timestamp |
|---|---|---|---|---|---|
| iPhone 8,2 | 0.000181984 | f/2.2 | 25 | 4.15 | 1482127815 |
| Canon M200 | 0.008 | f/14 | 100 | 22 | 1754713640 |
| Nikon 1 AW1 | 0.0015625 | f/7.1 | 160 | 10 | 1479266610 |
| Sony HX95 | 0.0333333 | f/3.5 | 100 | 4.25 | 1632529690 |
| **Olympus E-M5 III** | 0.001 | **f/0** ← | 200 | **0 mm** ← | 1575000465 |

**Olympus は絞りと焦点距離に 0 を返した。** 値が無いのか、この probe が
読めていないのかは区別できない。**そして正典はこの場合の答えを既に持っている**:

> 「**値は「読めなければ未設定」**。空欄・`-`・`1e`・`notanumber` はすべて
> 未設定であって **0 ではない**」 ([terminology.md](terminology.md))

**0 を条件値として series に入れてはならない。** 露光 0 s は測定値としてありえ、
linearity では暗電流点を意味しうるので、欠損が 0 として紛れ込むのは最悪である。

### 9.2 何が健全で、何が人の確認を要するか

| | 判定 |
|---|---|
| **`meta` に事実として載せる** (shutter/ISO/aperture/focal/機種/timestamp) | **健全。自動でよい。** `meta` は「viewer は運ぶだけで書き換えない」key-value (input-adapters.md §4.3.1)。単位つきで載せる (`{"value":0.008,"unit":"s"}`) |
| **`Stack.timestamps` に撮影時刻を入れる** | **概ね健全。**「ただ時間が経っただけ」に該当する (input-adapters.md §4.5)。単位は `s`。ただし EXIF の秒精度は粗く、連写では同値が並ぶ — **同値が並ぶ時刻軸は軸として使えない**ので、その場合は入れない |
| **フォルダの RAW 群を露光で `Series` にし、`conditions` を EXIF から埋める** | **提案として出す。自動で確定しない。** 理由は下 |

**なぜ series を自動生成しないか** — 正典が既にそう決めている:

> 「**series は自動で作らない**(フォルダ構造から推測すると外れたときに
> 黙って嘘の掃引ができる)」 ([terminology.md](terminology.md))

EXIF から露光が読めることは、**それが掃引であることを意味しない**。
同じ露光で 24 枚撮った stack でも EXIF には露光が入っている。
逆に露光が全部違っても、それはブラケットかもしれないし、
オートで撮れてしまっただけかもしれない。**「値が読める」と
「その値が振られた条件である」は別のことで、後者は人しか知らない。**

したがって推奨する形は:

> picker / Inspector に「**EXIF から条件を埋める**」を出し、
> **読めた値を提案列として見せて、人が確定する。**

これは既存の UI 前例と同じ — 正典が series 作成モーダルの**推定値列**について
「推定値はどこでも**提案**であって代入ではない: 画面に出たものを人が見て確定する」
と既に決めている。**新しい UI 概念を持ち込まずに済む。**

**単位は EXIF が言うので推測にならない** (s / mm)。
ただし ISO と f 値は無次元で、`unit` を空にすると正典の「空 = 未設定 = その軸は
適用されない」と衝突する。**無次元をどう綴るかは決める必要がある** → §14 問い 10。

### 9.3 JPEG/TIFF の EXIF には別ライブラリが要る — が、要らないかもしれない

**LibRaw は RAW の EXIF を既に出す** (§9.1 は追加ライブラリ**ゼロ**で得た)。
別の EXIF ライブラリが要るのは **JPEG/TIFF を native にした場合だけ**。

そして §8.2 のとおり **JPEG は `display` で測定に使えない**。
**測定に使えない画像の EXIF は `conditions` にならない** — なれるのは `meta` だけ。
**つまり JPEG のために GPL/LGPL の EXIF ライブラリを引く理由は、ほぼ無い。**

## 10. ライセンス — ここが今回いちばん危ない

### 10.1 この repo には LICENSE ファイルが無い

```
$ ls | grep -iE "licen|copying"
(無し)
```

にもかかわらず、**CI は main への push ごとに `viewer.exe` / `viewer-serve` /
plugins を `binaries` ブランチへ強制 push している** (build.yml:152-223)。
**これは配布である。** 現状は全依存が BSD/MIT/zlib 系なので実害が出ていないだけで、
**LGPL/CDDL/GPL のコードを入れるなら、先に手当てが要る。**

### 10.2 ライブラリごとの義務と、バイナリ配布への帰結

| ライブラリ | ライセンス | 静的リンクした単一バイナリを配る場合の帰結 |
|---|---|---|
| OpenEXR / Imath | **BSD-3-Clause** | 著作権表示を添えるだけ。**問題なし** |
| libdeflate (OpenEXR に vendored) | MIT | 同上 |
| miniz / glfw / imgui / pfd (現行) | zlib / MIT 系 | 同上 |
| **LibRaw** | **LGPL-2.1 か CDDL-1.0 の二者択一** (`COPYRIGHT` で確認) | **下記 §10.3** |
| **exiv2** | **GPL-2.0-or-later** | **静的リンクするとバイナリ全体が GPL になる。**この repo は現状ライセンス未定で、GPL 化は明らかに意図しない結果。**採らない** |
| libexif | LGPL-2.1 | LGPL のみ。CDDL のような逃げ道が**無い** → §10.3 の問題を丸ごと被る |

### 10.3 LibRaw は CDDL を選ぶべき

LibRaw は**こちらが選べる**:

- **LGPL-2.1 を選ぶと**: 静的リンクした配布物には、利用者が LibRaw を
  差し替えて**再リンクできる手段**を提供する義務が生じる (LGPL §6)。
  オブジェクトファイル一式を配るなどが要る。
  **「1つの自己完結した exe を GitHub Actions が自動公開する」形と噛み合わない。**
- **CDDL-1.0 を選ぶと**: 義務は主に §3.1 —
  「Executable 形式で配る Covered Software は Source Code 形式でも
  入手可能にし、そのソースは本ライセンスの下でのみ配布する」+ ライセンス写しの同梱
  (取得したソースの `LICENSE.CDDL` で確認)。
  **LibRaw を改変しなければ、固定したタグを指すだけで満たせる。**

> **推奨: CDDL-1.0 を選択し、その旨を明記する。**

必要な実務 (どれも小さいが、**RAW 対応より先**):

1. リポジトリに **LICENSE** を置く (viewer 自身の条件を決める)。
2. **THIRD-PARTY-NOTICES** を置き、LibRaw を **CDDL-1.0 で使用**と明記、
   固定タグ (0.22.2) とソース入手先 URL を書く。
3. `binaries` ブランチの成果物に**その2つを同梱する**
   (build.yml の Package ステップに 2 行)。

**これは法務作業ではなく配布物の作業**であり、忘れると
「ライセンス未定のバイナリに CDDL コードが入っている」状態になる。

### 11.1 RAW の fixture をどうするか (推奨)

1. **リポジトリに実機 RAW を置かない。** サイズと権利の両方で不適。
2. **合成 DNG を書く。** DNG は TIFF 派生なので、既知のブラックレベル・
   CFA パターン・ビット深度を持つ小さな DNG を Python (標準ライブラリのみ) で
   生成できる。**決定的で、小さく、権利問題が無く、しかも
   「ブラック/CFA/深度が正しく読めるか」という一番検証したい経路をちょうど通る。**
3. ベンダ固有のデコーダ (CRX / Olympus 圧縮など) は合成では試せない。
   **そこは selftest の対象外と明記する** — 隠すのではなく
   「ここは上流を信頼している」と書く。

**ただし合成 DNG ジェネレータは書いていないので、工数は未測定。**

## 13. 自分の推奨への、いちばん強い反論2つ

**反論1: LibRaw の版を固定することには「賞味期限」があり、
しかも一部は版を上げても開かない。**

OpenEXR を 3.4.13 に固定しても、EXR ファイルは去年と同じ形をしている。
**RAW は違う。** 新機種は毎月出て、その対応は LibRaw の新版で入る。
0.22.2 に固定した瞬間から「**去年のカメラまでしか開けない viewer**」に
なっていき、劣化が**こちらの不作為で起きる**。しかも上流に CMake が無いので
更新は「タグを上げる」だけでは済まず、§4.3 の罠 (`*_ph.cpp`、`ws2_32`、
上流のファイル移動) を毎回確認することになる。

**そして §4.8 でこの反論は一段強くなった。**
「新しい機種が開かない」だけなら、待てば版が追いつく。ところが:

> **一部の形式は「版が1つ先」ではなく「別の SDK が1つ要る」ところにある。**

- **DNG 1.7 の JPEG-XL は Adobe DNG SDK が要る** (LibRaw 公式が明記、§4.8.4)。
  LibRaw をいくら新しくしても、**その SDK を抱える判断をしない限り開かない**。
- **GoPro VC-5 は GPR SDK。** 同じ構造。
- **Nikon HE/HE* は 0.22.2 で "not supported yet"。**
  理由は上流が述べておらず、**こちらでも確認できなかった** (§4.8.4)。
  つまり**いつ開けるようになるか予測できない**。

Nikon Z 8 / Z 9 / Z f / Z 6III は**現行の主力機**であり、
HE/HE* は**それらの既定に近い記録形式**である。
「主要カメラベンダの RAW に対応したい」という要望に対して、
**最新の Nikon で最もよく使われる設定が開かない**というのは小さな穴ではない。
**そしてこれは pin を上げても直る保証が無い。**

(部分的な答え: だからこそ §7.1 のアダプタが要る。LibRaw が知らない機種も
HE も、`rawpy` / メーカー SDK を呼ぶアダプタで読める道が残る —
C++ の更新とリリースを待たずに。しかしそれは
「native の意味が薄れる」ことでもあり、反論を完全には消さない。
むしろ **HE のような穴があるほど、アダプタは「例外的な逃げ道」ではなく
「日常的に要るもの」に近づく**。)

**反論2: 「PNG は測れないから native にしない」は、ユーザーの要望への回答になっていない。**

ユーザーは **「PNG, JPEG, TIFF も対応したい」**と明示的に言った。
それに対して「アダプタで読んでください、しかも開いても測定は断ります」と
返すのは、**要望の文面には応えていない**。§8.2 で優先順位までは付けたが、
順位を付けることは実装ではない。しかもアダプタ機構は**まだ実装されていない**ので、
現時点の実質的な答えは「**読めません**」である。
「誠実さ」を理由に要望を断っているように見える危険があり、
その見え方は正しくもある — **測れないことと開けないことは別なのに、
C′ は両方を同時に断っている。**

(これへの最小の答えが §8.2 の順位で、**TIFF を先に native 化する**のが
おそらく最も費用対効果が高い。TIFF は宣言1回で測定に使えるようになる形式だから。)

## 14. 決めてほしいこと (既定案つき)

| # | 問い | 推奨する既定 |
|---|---|---|
| 1 | `values` を形式追加より先に入れるか | **入れる** (§6)。門が無いまま形式が増えるのが一番危険 |
| 2 | **RAW を native にするか** | **する** (§4)。EXR より安く、しかも `dn` を名乗れる |
| 3 | **LibRaw のライセンスはどちらを選ぶか** | **CDDL-1.0** (§10.3)。LGPL の再リンク義務は単一 exe 配布と噛み合わない |
| 4 | **LICENSE / THIRD-PARTY-NOTICES を先に置くか** | **置く。RAW 対応より前** (§10.1) |
| 5 | PNG / JPEG / TIFF をどうするか | **当面アダプタ。**要望が続くなら **TIFF → PNG → JPEG** の順 (§8.2) |
| 6 | EXR / RAW を serve にも入れるか | **入れない (client 限定)。** 20.04 コンテナの手書き g++ 行が崩れる |
| 7 | EXR のスレッド数 | **ハードウェア並列度、上限8程度** (§3.2)。背景ローダとの取り合いは**未検証** |
| 8 | **EXIF から series を自動生成するか** | **しない。提案列として見せて人が確定する** (§9.2) |
| 9 | **欠損 EXIF (Olympus の f/0) をどう扱うか** | **未設定として扱い、0 を入れない** (§9.1) |
| 10 | ISO / f 値の `unit` をどうするか | **無次元を明示する綴りを決める**。空文字は「未設定」と衝突する (§9.2) |
| 11 | RAW の selftest fixture | **合成 DNG を生成する** (§11.1)。実機 RAW はサイズと権利で不可 |
| 12 | **ブラックレベルを自動で引くか** | **引かない。ファイルが言った値として表示する** (§4.7)。5件中1件で 0 が返った |
| 13 | RAW を1枚開いたとき CFA プレーンに分けるか | **分ける** (正典「CFA プレーンは統計で混ぜない」)。既存の raw の `RI_BAYER` 経路に載る |
| **14** | **非可逆 RAW を開くか、断るか** | **開く。ただし `values=display` で測定は断る** (§8.0)。見ることと測ることを分ける |
| **15** | **圧縮を判定できないベンダ (Olympus 等) をどうするか** | **`unknown`。`dn` に倒さない** (§4.8.2)。人が Inspector で宣言すれば測れる |
| **16** | **判定表をどこに置くか** | **1つの関数に集約し、ベンダごとの分岐をそこだけに置く。**§4.8.2 の表がそのまま仕様。**新しいベンダを足したら既定は `unknown`** |
| **17** | Nikon HE/HE* をどうするか | **コーデック名を出して断り、アダプタを案内する** (§4.8.5)。**主力機の既定形式なので、アダプタの優先度を上げる理由になる** (§13 反論1) |
| **18** | Adobe DNG SDK を抱えて JPEG-XL DNG に対応するか | **当面しない。** SDK の重さとライセンスを別途評価する必要があり、**未測定** |

## 15. 測れなかったこと (と、その理由)

| 測れなかったもの | 理由 |
|---|---|
| **OIIO のビルド・サイズ・速度** | configure が3回とも通らなかった (§5)。**MinGW でのことで、MSVC/Linux で建たないとは結論していない** |
| **OIIO vs OpenEXR / LibRaw の直接比較** | 上記のため相手がいない。**片側だけの数字で勝敗を言わない** |
| **libpng / libtiff / libjpeg 単体のコスト** | 測っていない。§8.2 の順位は誠実さの議論から出したもので、コスト比較からではない。**ただし libjpeg-turbo 3.1.2 が MinGW で建つことは OIIO の probe で確認済み** |
| **MSVC でのビルド全般** | toolchain が MinGW。**LibRaw のソース直コンパイルが MSVC で通るかは未検証** |
| **CI ランナー上での増分** | ローカル 20 コアの実測のみ |
| ~~**`viewer.exe` に実際に混ぜたときのサイズ増**~~ | **EXR については測定済みになった。** `media-openexr` が実装し、`viewer.exe` **7,996,319 → 11,261,523 B (+3,265,204 B / +3.11 MiB / +41%)**、cold total 73→100 s (+27 s / +37%)。**こちらの bench 差分 +3,124,146 B との差は 4.3%** — 手法は妥当だった (向こうの数字は writer を含むぶんだけ大きい)。**LibRaw 側 (+0.95 MiB) は依然として未測定** |
| **loadExr / loadRaw の実装工数** | 実装していない |
| **合成 DNG ジェネレータの工数** | 書いていない (§11.1) |
| **PNG デコーダを miniz の上に書く工数** | 書いていない (§8.2) |
| **RAW の CFA が RGGB 以外の場合** | サンプル5件が**全部 RGGB** だった。他パターン・Quad Bayer・X-Trans (Fuji) は**未確認** |
| ~~**Canon C-RAW (`Quality = 7`) の実ファイル**~~ | **解消 — 実測した (§4.9.3)。** Canon EOS R5 II の `RAW.CR3` / `CRAW.CR3` の対で `Quality` が 4 / 7 に分かれ、`decoder_name` と `decoder_flags` は同一だった |
| **Fuji RAF / Panasonic RW2 の圧縮判定** | サンプルを取得しそこねた。**§4.8.2 の表に行が無い**のはそのため。Fuji は X-Trans という別の未確認事項も抱えている |
| **非可逆 RAW が実際どれだけ数値を歪めるか** | **依然として未測定で、しかも簡単には測れない。** R5 II の RAW/CRAW は**別々のシャッターで撮られた 2 枚**であって、同じセンサ読み出しを2通りに符号化したものではない。画素どうしを引き算しても、歪みではなくショットノイズと被写体の差を見ることになる。**正しく測るには同一フレームを両方式で符号化する必要があり、カメラはそれをしない。** σ_t への影響を言うにはリファレンス符号化器が要る |
| **Nikon HE/HE\* がウェーブレットかどうか** | **推定にとどまる。** 復号できないので変換の種類を中から確かめる手段が無く、上流も明かしていない。**§4.9.5 の表でも「推定・未確認」と書いてある** |
| **Canon CRM (.CRM) の実ファイル** | 入手していない。`Quality` の列挙に 130/131 として名前があるだけで、**stills 経路に復号器は無い**ことはソースで確認済み。**動画形式なので当面この道具の対象外** |
| **HE/HE* が TicoRAW / intoPIX かどうか、商用アドオンかどうか** | **確認できなかった** (§4.8.4)。LibRaw のソースにも配布ページにも記述が無い。**「復号しない」ことだけが確認済み** |
| **Adobe DNG SDK / GPR SDK を入れた場合のコスト** | 測っていない (§14 問い 18) |
| **Nikon のブラックレベルが本当は幾つか** | probe が `cblack[0..3]` しか見ていない (§4.7)。**0 が正しいのか読めていないのかを区別できていない** |
| **RAW のマスク領域 (オプティカルブラック)** | LibRaw は可視領域外も持つ (CR3 は raw 6288×4056 に対し可視 6024×4020) が、**OB 画素を統計に使えるかは調べていない**。IQ 用途では価値がありうる |
| **デコード用スレッドと背景ローダの干渉** | 実装していないので測れない |
